# 기능 명세: Memento 기억 구조화 파이프라인 수정

**기능 브랜치**: `012-fix-memory-structuring`  
**작성일**: 2026-04-11  
**상태**: Draft  
**입력**: `@docs/architecture/ko/memory-structuring-problem-analysis.md`

## 배경

Memento는 AI 에이전트를 위한 장기 기억 시스템이다. 원시 경험(에피소딕 기억)을 축적하고, 마치 인간의 수면 중 기억 공고화처럼 시간이 지나면서 자동으로 구조화된 지식(시맨틱 기억)으로 정제하도록 설계되어 있다.

시스템에는 에피소딕 기억을 시맨틱 지식으로 변환하는 구조화 파이프라인(Sleep Consolidation, Triple Extraction)이 존재한다. 그러나 버그와 잘못된 기본 설정이 복합적으로 작용하여, 이 파이프라인들이 실패해도 조용히 무시되거나 실질적으로 실행 자체가 차단되어 있다. 그 결과, 에이전트는 수백 개의 단편적인 에피소딕 기억을 쌓아가면서도 구조화된 지식이 좀처럼 생성되지 않는 상태에 놓여 있다.

## 명확화 (Clarifications)

### Session 2026-04-11

- Q: 유사도 임계값(0.85) 이상의 시맨틱이 이미 존재할 때 "병합"이 구체적으로 무엇을 의미하는가? → A: 기존 시맨틱 내용과 새 에피소딕들을 합쳐 재요약(re-summarize)한다 — 내용 갱신 + 소스 참조 확장.
- Q: 소프트 삭제 후 하드 삭제까지의 유예 기간은 얼마인가? → A: 설정 가능한 기본값 30일 — 운영자가 환경 변수로 조정 가능.
- Q: 기존 배포 데이터베이스에서 누락된 트리플 추출 상태 컬럼은 어떻게 처리하는가? → A: 새 마이그레이션 파일 추가 — 기존 DB도 `npm run db:migrate` 실행 시 자동 업데이트.
- Q: 소프트 삭제를 트리거하는 주체는 무엇인가? → A: TTL 만료 자동 트리거 — 망각 정책 서비스가 TTL 도달 시 소프트 삭제로 전환하며, 에이전트 `forget` 도구는 기존대로 하드 삭제를 유지한다.
- Q: 중복 경고 검사에서 ownerID가 null인 기억은 어떻게 처리하는가? → A: ownerID가 null인 기억끼리만 비교 — ownerID 없는 저장 요청은 null 소유자 기억들 사이에서만 유사도 검사를 수행한다.

## 사용자 시나리오 및 테스트

### 사용자 스토리 1 — 에피소딕 기억이 시맨틱 지식으로 공고화된다 (우선순위: P1)

AI 에이전트가 며칠 또는 몇 주에 걸쳐 회의 메모, 코드 결정, 사용자 선호도 등 관련 기억들을 저장한다. 충분히 축적되면 시스템이 이를 자동으로 압축된 시맨틱 기억으로 합성하여, 에이전트가 나중에 원시 단편이 아닌 구조화된 지식으로 검색할 수 있어야 한다.

**이 우선순위인 이유**: 이것이 Memento의 핵심 가치 명제이다. 공고화가 작동하지 않으면 구조화 파이프라인 전체가 무너진다. 다른 모든 개선은 이것이 먼저 작동해야 의미가 있다.

**독립 테스트**: 관련 에피소딕 기억 3개 이상을 저장하고, 1시간 이내에 이를 요약한 시맨틱 기억이 생성되는 것을 확인함으로써 완전히 테스트할 수 있다 — 수동 개입 없이 구조화된 검색이라는 가치를 제공한다.

**수용 시나리오**:

1. **주어진 조건**: 에이전트가 지난 90일 내에 같은 주제에 대해 2개 이상의 에피소딕 기억을 저장했을 때, **공고화 작업이 실행되면**, 시스템은 해당 클러스터를 요약한 시맨틱 기억을 최소 1개 생성하고 원본 에피소딕을 공고화 완료로 표시해야 한다.
2. **주어진 조건**: 공고화 작업이 실행되어 새 시맨틱 기억이 생성된 후, **같은 주제 클러스터가 다시 발생하여 공고화가 재실행되면**, 시스템은 중복을 생성하지 않고 새 합성 내용을 기존 시맨틱 기억에 병합해야 한다.
3. **주어진 조건**: 공고화 파이프라인과 트리플 추출 파이프라인이 모두 같은 주제로 실행된 후, **에이전트가 해당 주제로 기억을 조회하면**, 에이전트는 같은 개념에 대해 거의 동일한 시맨틱 항목을 중복으로 받아서는 안 된다.

---

### 사용자 스토리 2 — 트리플 추출이 개별 에피소딕을 처리한다 (우선순위: P1)

에이전트가 새 에피소딕 기억을 저장하면, 시스템은 1시간 이내에 자동으로 해당 기억에서 구조화된 지식 추출을 시도해야 한다. 이를 통해 클러스터 조건을 충족하지 않아도 개별 에피소딕 기억으로부터 시맨틱 기억이 생성된다.

**이 우선순위인 이유**: 트리플 추출 파이프라인이 스키마 불일치로 인해 새 설치에서 완전히 작동하지 않는다. 이를 수정하는 것이 기초 작업이다 — 이것이 없으면 어떤 개별 에피소딕 기억도 구조화된 지식을 생성하지 못한다.

**독립 테스트**: 단일 에피소딕 기억을 저장하고, 1시간 이내에 해당 기억이 처리 상태로 표시되는 것을 확인하고 — 시스템 로그에 누락된 필드 관련 오류가 없음을 확인함으로써 완전히 테스트할 수 있다.

**수용 시나리오**:

1. **주어진 조건**: 새 에피소딕 기억이 저장된 후, **1시간 이내에 트리플 추출 작업이 실행되면**, 해당 기억은 처리 상태(성공, 건너뜀, 실패)로 표시되고 시스템 로그에 누락된 스키마 필드에 대한 WARN 수준 오류가 나타나지 않아야 한다.
2. **주어진 조건**: 추출 가능한 지식을 포함한 에피소딕 기억이 있을 때, **트리플 추출이 성공하면**, 해당 시맨틱 기억이 생성되거나 기존의 관련 시맨틱 기억이 업데이트되어야 한다.
3. **주어진 조건**: 이전 마이그레이션 이력이 없는 새 데이터베이스 설치에서, **트리플 추출 작업이 실행되면**, 모든 마이그레이션이 적용된 데이터베이스와 동일하게 작동해야 한다.

---

### 사용자 스토리 3 — 삭제된 기억이 검색에서 완전히 제외된다 (우선순위: P2)

에피소딕 기억의 TTL이 만료되면 망각 정책 서비스가 해당 기억을 "소프트 삭제"로 표시한다. 소프트 삭제된 기억은 유예 기간(기본 30일) 동안 저장소에 유지되지만, 즉시 에이전트 조회 및 검색에서 나타나지 않아야 한다. 에이전트 `forget` 도구는 기존대로 즉시 하드 삭제를 수행한다.

**이 우선순위인 이유**: 현재 소프트 삭제가 작동하지 않아 복구 유예 기간 없이 기억이 완전히 보이는 상태에서 영구 삭제로 바로 전환된다. 이를 올바르게 구현하면 복구 기간이 생기고, 설계된 2단계 망각 주기(격리 후 삭제)가 의도대로 작동하게 된다.

**독립 테스트**: 알려진 기억에 소프트 삭제를 트리거하고, 검색, 검색, 기억 주입 결과에서 더 이상 나타나지 않는 것을 확인함으로써 완전히 테스트할 수 있다.

**수용 시나리오**:

1. **주어진 조건**: 기억이 소프트 삭제된 후, **에이전트가 관련 주제로 기억을 조회하면**, 소프트 삭제된 기억은 검색, 검색, 기억 주입 결과 어디에도 나타나지 않아야 한다.
2. **주어진 조건**: 소프트 삭제된 기억이 존재할 때, **시스템이 공고화 후보를 선택하면**, 소프트 삭제된 기억은 후보 풀에서 제외되어야 한다.
3. **주어진 조건**: 소프트 삭제된 기억이 있을 때, **하드 삭제 기한이 도래하면**, 해당 기억은 저장소에서 영구적으로 제거되어야 한다.

---

### 사용자 스토리 4 — 중복 기억 저장 시 에이전트에게 경고한다 (우선순위: P2)

에이전트가 이미 저장된 기억과 의미적으로 유사한 기억을 저장하려 할 때, 시스템은 이를 알려야 한다 — 에이전트가 새 기억이 진정한 가치를 추가하는지 반복인지 판단할 수 있도록.

**이 우선순위인 이유**: 저장소를 부풀리고 검색 품질을 떨어뜨리며 공고화 처리를 느리게 만드는 거의 동일한 에피소딕 기억의 점진적 축적을 방지한다.

**독립 테스트**: 기억을 저장한 후, 매우 유사한 기억을 저장하여 응답에 관련 기억 참조와 함께 유사도 경고가 포함되는 것을 확인함으로써 완전히 테스트할 수 있다 — 저장은 계속 성공해야 한다.

**수용 시나리오**:

1. **주어진 조건**: 에이전트가 같은 에이전트의 기존 기억과 높은 유사도를 가진 기억을 저장할 때, **저장 요청이 완료되면**, 응답은 유사한 기억이 몇 개인지와 해당 식별자를 포함한 경고를 포함해야 한다.
2. **주어진 조건**: 유사도 경고가 반환된 후, **에이전트가 계속해서 기억을 저장하면**, 추가 제약 없이 기억이 저장되어야 한다.
3. **주어진 조건**: 같은 에이전트가 진정으로 다른 두 기억을 순서대로 저장할 때, **두 저장 요청이 모두 완료되면**, 유사도 경고가 반환되지 않아야 한다.

### 사용자 스토리 5 — 운영자가 기억 구조화 상태를 모니터링할 수 있다 (우선순위: P3)

운영자 또는 AI 에이전트가 기억 구조화 파이프라인의 현재 상태를 조회할 수 있어야 한다 — 얼마나 많은 기억이 공고화되었는지, 트리플 추출이 성공하고 있는지, 시맨틱 기억이 시간에 따라 어떻게 증가하는지.

**이 우선순위인 이유**: 측정 가능한 결과 없이는 다른 수정 사항들이 작동하는지 확인할 수 없다. 이 스토리는 피드백 루프를 완성한다. 파이프라인이 실제로 작동하기 전에는 지표가 의미 없으므로 스토리 1~4에 의존한다.

**독립 테스트**: 텔레메트리 요약 도구 또는 어드민 통계 엔드포인트를 조회하고, 공고화 관련 지표가 존재하고, null이 아니며, 파이프라인 활동 후 변경되는 것을 확인함으로써 완전히 테스트할 수 있다.

**수용 시나리오**:

1. **주어진 조건**: 기억 구조화 파이프라인이 실행된 후, **AI 에이전트가 텔레메트리 요약 도구를 호출하면**, 응답에는 공고화 품질 블록이 포함되어야 한다: 에피소딕 공고화율, 트리플 추출 성공률, 클러스터 처리 효율성, 최근 시맨틱 기억 생성 수(최근 7일 기준), 파이프라인 오류 수(최근 7일 기준).
2. **주어진 조건**: 기억 구조화 파이프라인이 실행된 후, **운영자가 공고화 통계 어드민 엔드포인트를 호출하면**, 응답에는 주간 시맨틱 기억 생성 시계열, 트리플 추출 상태 분포, 최근 공고화 실행 요약이 포함되어야 한다.
3. **주어진 조건**: 파이프라인이 아직 실행되지 않은 새 설치에서, **지표를 조회하면**, 모든 값은 오류 없이 0 또는 null이어야 한다.

### 엣지 케이스

- 공고화 실행 시 모든 후보가 이미 공고화된 경우? → 작업이 처리된 클러스터 0개로 정상 완료되고 새 시맨틱은 생성되지 않는다.
- 트리플 추출이 지식을 추출하기에 너무 짧은 내용의 기억을 만날 경우? → 기억은 "건너뜀" 상태로 처리되어 표시된다. 오류가 나타나지 않는다.
- 고정(pinned) 기억에 소프트 삭제를 시도하면? → 고정된 기억은 소프트 삭제 대상이 아니다. 작업이 무시된다.
- 중복 경고를 위한 유사도 검사가 불가하거나 너무 느린 경우? → 기억은 경고 없이 저장된다. 중복 힌트 실패가 저장을 차단해서는 안 된다.
- 공고화 중 시맨틱 병합이 중간에 실패하면? → 새 시맨틱이 독립 항목으로 삽입된다(현재 동작으로 폴백). 오류는 공고화 결과에 기록된다. 기존 시맨틱은 손상되지 않아야 한다.
- 이전 실행이 아직 진행 중일 때 공고화 작업이 트리거되면? → 새 호출이 정상적으로 거부된다. 중복 처리가 발생하지 않는다.
- 공고화 룩백 기간이 하드 삭제 TTL보다 길게 설정된 경우? → 저장소에 아직 존재하는 기억만 처리된다. 룩백 기간이 TTL 경계를 넘어도 추가 후보는 없다.

## 요구사항

### 기능 요구사항

- **FR-001**: 시스템은 같은 주제의 에피소딕 기억 2개 이상의 클러스터에서 한 번의 공고화 주기 내에 최소 1개의 시맨틱 기억을 생성해야 한다.
- **FR-002**: 충분히 유사한 시맨틱이 이미 존재하는 경우(유사도 ≥ 0.85) 시스템은 중복 시맨틱 기억을 생성해서는 안 된다. 반드시 기존 시맨틱 내용과 새 에피소딕들을 합쳐 재요약(re-summarize)하여 내용을 갱신하고 소스 참조를 확장해야 한다.
- **FR-003**: 시스템은 모든 새 에피소딕 기억을 한 번의 예약 주기 내에 트리플 추출 파이프라인으로 처리하고 기억 레코드에 결과(성공, 건너뜀, 실패)를 기록해야 한다.
- **FR-004**: 공고화 파이프라인은 망각 정리 작업보다 높은 빈도로 실행되어야 한다 — 에피소딕 기억이 제거되기 전에 공고화될 기회가 있어야 한다.
- **FR-005**: 운영자는 코드 변경이나 재배포 없이 최소 클러스터 크기와 시맨틱 유사도 임계값을 설정할 수 있어야 한다.
- **FR-006**: 망각 정책 서비스는 에피소딕 기억의 TTL 만료 시 해당 기억을 소프트 삭제로 표시하고, 소프트 삭제 즉시 에이전트 대상 모든 조회(검색, 기억 주입, 공고화 후보 선택)에서 제외해야 한다. 에이전트 `forget` 도구는 기존대로 즉시 하드 삭제를 유지한다.
- **FR-007**: 시스템은 기억 레코드에 소프트 삭제 타임스탬프를 기록하고, 소프트 삭제 시점으로부터 설정 가능한 유예 기간(기본 30일) 동안 저장소에 유지한 후 하드 삭제해야 한다.
- **FR-008**: 시스템은 에이전트가 같은 ownerID의 기존 기억과 의미적으로 유사한 기억을 저장할 때 저장을 차단하지 않고 유사도 경고를 반환해야 한다. ownerID가 null인 경우 null 소유자 기억들 사이에서만 유사도 검사를 수행한다.
- **FR-009**: 텔레메트리 요약 도구는 에피소딕 공고화율, 트리플 추출 성공률, 클러스터 처리 효율성, 최근 시맨틱 기억 생성 수(최근 7일 기준), 파이프라인 오류 수(최근 7일 기준)를 보고하는 공고화 품질 블록을 포함해야 한다.
- **FR-010**: 어드민 통계 인터페이스는 주간 시맨틱 기억 생성 시계열, 트리플 추출 상태 분포, 최근 공고화 실행 요약을 보고하는 공고화 상태 엔드포인트를 노출해야 한다.
- **FR-011**: 새 데이터베이스 설치는 모든 마이그레이션이 적용된 데이터베이스와 동일한 스키마를 가져야 한다. 기존 배포에서도 `npm run db:migrate` 실행으로 누락된 트리플 추출 상태 필드(3개 컬럼)가 자동 추가되어야 한다 — 새 마이그레이션 파일로 관리한다.

### 핵심 엔티티

- **에피소딕 기억(Episodic Memory)**: 원시 기록된 경험. 이 기능과 관련된 속성: 내용, 생성 시간, 소유자, 고정 여부, 공고화 여부, 소프트 삭제 여부, 소프트 삭제 타임스탬프, 트리플 추출 결과.
- **시맨틱 기억(Semantic Memory)**: 하나 이상의 에피소딕 기억으로부터 합성된 정제된 구조화 지식. 속성: 내용, 생성 시간, 소유자, 원본 참조(어떤 에피소딕이 기여했는지).
- **공고화 클러스터(Consolidation Cluster)**: 함께 합성하기에 충분히 유사한 에피소딕 기억 그룹. 속성: 멤버 기억 식별자, 사용된 유사도 점수 임계값.
- **지식 트리플(Knowledge Triple)**: 에피소딕 기억에서 추출된 주어-술어-목적어 사실. 트리플 추출 경로를 통한 시맨틱 기억 생성 시 중복 제거 레지스트리로 사용된다.
- **텔레메트리 이벤트(Telemetry Event)**: 백그라운드 파이프라인 실행 결과의 구조화된 레코드. 속성: 이벤트 유형, 결과(성공/실패), 소요 시간, 클러스터 수, 오류 수.

## 성공 기준

### 측정 가능한 결과

- **SC-001**: 파이프라인 수정 배포 후 24시간 이내에, 지난 90일간 저장된 에피소딕 기억 중 클러스터 임계값을 충족하는 것들의 30% 이상이 시맨틱 기억으로 공고화된다.
- **SC-002**: 스키마 수정 배포 후 정상 운영 중 시스템 로그에 트리플 추출 필드 누락 관련 WARN 수준 오류가 0건 나타난다.
- **SC-003**: 수정 배포 후 첫 1주일 이내에 공고화 클러스터 처리율(`clusters_processed / clusters_found`)이 50%를 초과한다.
- **SC-004**: 시맨틱 병합 수정 배포 후 4주 이내에 주당 새 시맨틱 기억 생성률이 안정화된다(선형 증가 중단). 이는 중복이 축적되지 않고 병합되고 있음을 나타낸다.
- **SC-005**: 소프트 삭제된 기억의 100%가 에이전트 검색 결과에서 제외된다 — 소프트 삭제된 레코드 수와 일치하는 주제의 검색 결과를 대조하여 검증 가능.
- **SC-006**: 같은 에이전트로부터의 의미적으로 유사한 내용에 대한 저장 요청의 80% 이상에서 유사도 경고가 반환된다.
- **SC-007**: 5가지 핵심 구조화 상태 지표(공고화율, 트리플 추출율, 클러스터 효율성, 시맨틱 수 추세, 파이프라인 오류 수) 모두가 직접 데이터베이스 접근 없이 에이전트 또는 어드민 인터페이스를 통해 조회 가능하다.

## 가정

- 공고화 룩백 기간은 기본 90일(에피소딕 기억의 하드 삭제 TTL 180일 이내)로, 에피소딕 기억이 영구 삭제되기 전에 여러 번의 공고화 기회를 가진다.
- 최소 클러스터 크기 기본값은 2(기존 5에서 감소), 유사도 임계값 기본값은 0.65(기존 0.75에서 감소). 운영자는 설정을 통해 모두 조정 가능하다.
- 시맨틱 병합 유사도 임계값은 0.85로 설정한다 — 클러스터 형성 임계값(0.65)보다 의도적으로 높게 설정하여 의미적으로 다른 개념을 잘못 병합하는 것을 방지한다.
- 중복 경고 유사도 임계값은 시맨틱 병합 임계값(0.85)과 일치한다.
- 소프트 삭제된 기억은 에이전트 도구를 통해 복구할 수 없다. 복구는 유예 기간(기본 30일, 환경 변수로 조정 가능) 내에 운영자 수준 접근이 필요하다.
- 측정 개선(스토리 5)은 다른 모든 파이프라인 수정이 검증된 후에 구현된다. 공고화가 실제로 실행되기 전에는 지표가 의미 없기 때문이다.
- 트리플 추출 파이프라인과 Sleep Consolidation 파이프라인은 독립적으로 유지된다. 각각 독립적으로 시맨틱 기억을 생성하지만, 중복 축적을 방지하기 위해 서로의 출력을 인식해야 한다.
