**Feature Branch**: `jee1/chore-memory-triple-semantic-23-664-dry-run`
**Created**: 2026-08-22
**Status**: Draft

**Input**: 라이브 DB의 자동 추출 triple semantic 23,664건을 dry-run·백업·롤백 절차와 함께 격리한다

## Problem Statement

라이브 프로덕션 DB(`~/.memento/data/memory.db`)의 semantic 25,520건 중 **23,664건이 자동 추출 triple**이다. 그중 `importance ≥ 0.8`인 8,600건이 랭킹 상단을 점유해, 사람이 직접 쓴 episodic 3,241건이 **8:1로 밀린다**. 조사 세션에서 `memory_injection`을 두 번 호출한 결과 반환된 13건이 전부 자동 생성 triple 문장이었다.

| 분류 | 건수 |
|---|---:|
| triple 컬럼 보유 semantic | 23,664 |
| ├ 문법 손상 (`됨/함/음/름 + 합니다`, 중복 제거) | 15,067 |
| └ 문법 정상 템플릿 | 8,584 |
| 40자 미만 파편 | 13,977 |

```
"공통 모듈 사용률는 100%를 비율합니다"            (importance 1.00)
"하위 호환성는 완료를 유지됨합니다"                (importance 1.00)
"memento 프로젝트는 완료를 개선 작업합니다"        (importance 0.90)
```

**복구가 아니라 격리인 이유**는 네 가지다.

1. **높은 우선순위를 차지한 채 거의 쓰이지 않는다.** `importance ≥ 0.8`인 기억 9,994건 중 **8,615건(86%)**이 격리 대상이고 사람이 쓴 것은 1,007건(10%)뿐이다. 대상의 평균 importance(0.564)가 episodic(0.476)보다 **높다**. 그런데 실제로 반환된 적이 있는 대상은 **739건(3.1%)**뿐이고, `importance ≥ 0.8`이면서 **한 번도 반환된 적 없는 대상이 8,285건**이다. 길이도 평균 **39.9자**로 episodic(359.7자)·procedural(292.0자)의 9분의 1이다. 랭킹 상위를 8:1로 점유하면서 답으로는 거의 나오지 않는 것 — 이것이 코퍼스가 무거워진 형태다.
2. **지우더라도 사실은 남는다.** 구조화된 `subject/predicate/object` 조합은 `kg_triple`에 **100% 보존**된다(FR-004 (b), 실측 24,192/24,192). 다만 `kg_triple`이 보존하지 못하는 것이 둘 있다 — 자연어 서술, 그리고 `memory_relation`의 관계 54,742행(그중 출처 링크 `extracted_from` 25,069)이다. 후자는 격리 전에 리포트로 내보내 기록을 남긴다(FR-006i). 다만 "정보량 0"이라는 표현은 부정확했다 — 표본 검토에서 파일 경로·이슈 번호·설계 결정을 담은 문장이 확인됐고, object 문자열이 사람이 쓴 기억 어디에도 없는 경우가 프로브 200건 중 37%였다(형태 (1) 중 object ≥8이 16,251건이므로 약 6,000건 규모). 이 손실은 `kg_triple` 보존을 근거로 수용한다.
3. **선별 보정이 불가능하다.** `memory_item.confidence` 컬럼은 존재하지만 전 29,000행이 NULL이다. `importance × confidence` 같은 사후 일괄 보정에 쓸 데이터가 없다.
4. **기존 복구 스크립트로는 대부분 못 고친다.** #768의 dry-run은 "37행 복구 가능"이었으나 실제 손상은 15,067건이다. 스크립트가 content와 옛 템플릿이 **정확히 일치**하는 행만 다시 렌더하기 때문이며, 스크립트 자체도 현재 실행 불가하다(#811).

이 값들이 스펙에 미치는 영향:

- **`backups/` 5.0GB의 대부분은 마이그레이션 백업이다.** 총 6,899개 중 6,880개가
  `backup-manager.ts:80`이 만드는 `memory-backup-<마이그레이션버전>-<타임스탬프>.db`이고,
  `db:backup` 산출물은 19개뿐이다. 256KB짜리 파일들은 초기 마이그레이션(버전 2~10대) 시점의
  백업이라 그때 DB가 실제로 작았다면 정상 크기다. 546MB짜리는 오늘 적용된 마이그레이션 42.0의
  백업이다.
- **그럼에도 크기 대조는 필요하다.** `db:backup` 산출물 19개 중 **0바이트 파일이 실재하고**
  (`memory-backup-2026-06-15T12-41-09-792Z.db`), `-wal`·`-shm` sidecar 잔재도 남아 있다.
  스크립트에 크기 0 삭제와 sidecar 정리 로직이 모두 있는데도 그렇다 — 그 정리가 항상 동작한다고
  가정할 수 없다는 것이 FR-007c의 근거다.
- **디스크는 충분하다.** 여유 493GB로 사본 A·B(각 548MB)와 각각의 `VACUUM` 임시 공간을 모두
  수용한다.
- **대상은 점유하되 거의 반환되지 않는다.** 반환된 적이 있는 대상은 **739건(3.1%)**뿐이고
  평균 `recall_count`는 0.05다. `importance ≥ 0.8`이면서 한 번도 반환되지 않은 대상이
  **8,285건**이다. 16회차가 쓴 "밀어낸다"는 적극적 축출을 연상시키지만 실상은 **높은
  우선순위를 차지한 채 잠들어 있는 것**에 가깝다 — 논거를 그렇게 다듬었다.
- **`recall_count`는 타입 간 직접 비교가 불가능하다.** `remember` 경로는 생성 시 **1**로
  시작하고(`remember-tool-memory-item.ts:64`) `createSemanticMemory`는 컬럼을 INSERT에 넣지
  않아 **0**에서 시작한다. 그래서 episodic 3,431건이 전부 `recall_count > 0`으로 보이지만
  이는 초기값이지 반환 기록이 아니다. 이 함정을 FR-001f로 명시했다.
- **격리는 재추출까지 막는다.** episodic 3,431건 중 **2,982건이 `triple_extracted=1 / success`**
  이고 격리는 이 플래그를 건드리지 않는다. 즉 나중에 같은 episodic에서 재추출을 시도해도
  스킵된다. 되돌릴 수 없을 뿐 아니라 재생성도 막히는 것이다. 다만 23회차가 찾은
  `memory_relation.extracted_from` 25,069건이 출처를 가리키므로, FR-006i의 내보내기가 그대로
  **복구 경로**가 된다 — 필요해지면 그 목록으로 플래그를 리셋하면 된다(FR-006k·006l).
- **대상에 출처 메타데이터는 정말 없다.** `source`·`origin_source`·`tags`·`session_id`·
  `source_session_id` 모두 0건으로, 4회차의 결론이 데이터로 재확인됐다. 출처를 아는 유일한
  경로는 `memory_relation`뿐이다.
- **`memory_review_candidate`도 대량 삭제된다.** 5,300행 중 **3,609행(68%)**이 대상에 걸린다.
  10회차 CASCADE 실측에서 `memory_relation`과 함께 빠져 있던 항목이다.
- **대상은 귀속이 없는 기억뿐이다.** 24,086건 전부 `project_id` NULL, `owner_id` NULL,
  `privacy_scope` private이고 소프트 삭제 표시(`is_deleted`·`deleted_at`)도 0건이다. 코퍼스에는
  프로젝트 7개와 소유자 2명이 존재하는데 대상에는 하나도 없다 — 판별식이 별도 조건 없이
  프로젝트·소유자 귀속 기억과 `team`·`public` 기억을 자연히 제외하고 있다는 뜻이다. 귀속
  조건을 판별식에 박지 않고 분포 보고로 감시하기로 했다(FR-001d·001e).
- **폴백의 원인이 특정됐다.** 형태 (2) **116건 전부** predicate 마지막 글자가 한글이 아니다 —
  `conjugatePredicate`가 즉시 `null`을 반환하는 정확한 조건이다. 같은 8월에 형태 (1) 876건 중
  782건(89%)은 한글로 끝나므로 코드가 바뀐 것이 아니라 **predicate 데이터의 성격이 변했다**.
  형태 (2)의 predicate는 평균 8.2자·최대 25자이고 32건이 공백을 포함한다 — 단일 동사가 아니라
  정규화되지 않은 구(phrase)다(`kg_triple` 전체 평균은 4.1자).
- **`kg_triple`도 같은 오염을 받는다.** 보존율은 100%로 유지되지만(격리 대상 24,086/24,086,
  형태 (2) 116/116), 저장되는 predicate의 품질은 별개다. 현재는 24,204건 중 96%가 한글로
  끝나 지표가 양호하나, 정규화 실패분이 계속 유입되면 떨어진다. FR-004 (b)가 보장하는 것은
  **조합의 존재이지 품질이 아니라는 점**을 명시하고, 격리 시점의 지표를 스냅샷으로 남긴다.
- **재조립 실패율이 8월 들어 급증했다.** 형태 (2)의 월별 생성은 2026-05 0건(0.0%),
  06 0건(0.0%), 07 1건(0.1%), **08 115건(11.6%)**이다. 형태 (2) 총 116건 중 115건이 이번 달
  것이다. `buildTripleSentence`가 최근 계속 `null`을 반환하고 있다는 뜻이며, 격리 이후에도
  같은 속도로 쌓인다면 FR-001b의 "비중이 작아 남겨도 된다"는 근거가 오래 가지 않는다.
  원인 규명은 별도 이슈로 제기한다(#805·#811 인접).
- **판별식은 인덱스 최적화 여지가 없다.** `idx_memory_item_triple`은 `(subject, predicate,
  object)` 컬럼 인덱스라 특정 subject를 찾을 때만 유용하고, 전량을 훑는 판별식에는 쓸 수 없다.
  실행 계획은 `idx_memory_item_type`으로 semantic만 좁힌 뒤 행마다 `substr`를 평가한다.
  `predicate IS NOT NULL AND object IS NOT NULL`을 추가해도 계획이 바뀌지 않으며 대상 집합도
  동일하다(subject 보유 24,202건 전부가 predicate·object도 갖는다). semantic 26,137행을 훑어
  24,086건을 반환하므로 인덱스가 오히려 무의미하다.
- **WAL은 위험 요소가 아니다.** 현재 2.6MB이고 `wal_autocheckpoint=1000`(약 4MB),
  `journal_size_limit=1MB`다. 서버 정지 상태에서는 체크포인트를 막을 리더가 없어 격리 중
  WAL이 무한정 커지지 않는다.
- **연쇄 정리 트리거가 라이브에 실재한다.** `memory_embedding_vec_delete`와
  `memory_item_fts_delete`를 포함해 6개 트리거를 직접 확인했다. 특히 vec delete 트리거는
  provider 분기 없이 `memory_item_vec`·`_tfidf`·`_minilm`·`_openai`·`_gemini`를 모두 지우고
  `rowid = OLD.id`(= `memory_embedding.id`)를 올바르게 쓴다 — `forget-tool.ts`의
  `cleanupRelatedData`가 같은 자리에 TEXT memory id를 넘기는 것과 대비된다.
- **vec·FTS 잔재는 일반 CLI로 확인할 수 없다.** `sqlite3`에 `vec0`·`fts5` 모듈이 없어 해당
  테이블을 열지 못한다. SC-005의 검증은 확장을 로드한 경로(사본에 붙인 서버 인스턴스 등)로
  해야 한다.
- **사본 프로브가 외부 의존 없이 가능하다.** 임베딩이 minilm(로컬 ONNX) 28,427건으로 사실상
  전량이라 API 호출이 필요 없고, `db:backup`의 online backup API가 DB 페이지 전체를 복사하므로
  vec 가상 테이블도 사본에 따라온다. 필요한 것은 `DB_PATH`를 사본으로 지정한 별도 서버
  인스턴스뿐이다(FR-003d).
- **`memory_injection`은 읽기 전용이 아니다.** `knowledge-context-bundle-builder.ts:244`가
  반환된 각 기억의 `memory_item` 행을 UPDATE해 `recall_count`·`last_accessed_at`·`g_value`·

- **조회하는 동안에도 DB가 자랐다.** 읽기 전용 조회만 한 40여 분 사이 파일이 548,270,080 →
  548,519,936 바이트로 늘었다. 프로덕션 서버가 지금 이 순간에도 쓰고 있다는 직접 증거이며,
  FR-008a의 서버 정지 요구를 다시 뒷받침한다.
- **코퍼스가 계속 증가한다.** 대상이 23,664 → 24,192로 늘었다. 서버가 살아 있고 신규 산출물이
  유입된다는 뜻이므로, FR-008a(실행 전 프로덕션 서버 정지)는 이론적 우려가 아니라 실측된
  필요다. FR-004b의 ±5% 게이트도 같은 이유로 실효가 있다.

  `합니다`로 끝나는 것이 0건이라, 원문 폴백이라는 판정이 실측으로 뒷받침된다. 최대 504자는
  `FALLBACK_TEXT_MAX_LENGTH` 절단선이다.
- **형태 (2)의 정보 손실은 사실상 1건이다.** 106건 중 95건은 동일 content의 episodic이 살아

  잠시 썼던 "검색 가치 0"이라는 표현은 사실과 반대였다.

  0.726으로 procedural(292.0자, 0.745)에 가깝다. FR-001b의 제외 결정을 뒷받침한다.
- **"정보량 0"은 부정확한 표현이었다.** 표본 A 50건을 실제로 검토한 결과 오탐은 0건이었으나,

  길이 ≥8인 대상 200건을 프로브하니 **37%는 object 문자열이 사람이 쓴 기억 어디에도 없었다**
  (형태 (1) 대상 중 object ≥8이 16,251건이므로 약 6,000건 규모). 격리를 정당화하는 것은

  중 하나를 붙이므로, FR-002i의 `length(subject)+2` 위치가 공백이라는 가정이 성립한다.
  `subject`·`predicate`·`object`에 앞뒤 공백이나 개행이 있는 행도 0건이라 `trim` 유무가
  결과를 바꾸지 않았다(양쪽 다 24,086건).
- **`subject`에 `_`를 포함한 행이 941건**이다. `LIKE subject || '_ %'`로 형태 (1)을 판별하면
  이 값들이 와일드카드로 해석된다. naive LIKE·`%` 이스케이프·위치 비교 세 방식이 모두 24,086건으로
  일치해 현재 데이터에서는 오분류가 없지만, 그것은 우연이다. FR-002i가 위치 비교를 강제한다.

## Goals

- triple 추출 파이프라인이 만든 **템플릿 문장** semantic을 검색 후보에서 제거해, 상위 슬롯을 선점하던 40자 파편 대신 사람이 쓴 서술이 반환되도록 한다. 구조화된 사실은 `kg_triple`이 보존하므로 지식 손실이 아니다 (원문을 보존한 폴백 행도 남긴다)
- 파괴적 실행 **전에** 대상 규모·구성·오탐 여부를 dry-run 리포트로 확인 가능하게 한다
- 실행 실패나 오판 시 되돌릴 수 있도록 백업과 롤백 절차를 남긴다
- 격리 후 검색 인덱스·임베딩 잔재가 남지 않게 하고 저장 공간 회수를 기록한다 (지식 그래프 `kg_triple`은 보존)
- 삭제 로직을 재구현하지 않고 기존 `forget` 도구로 격리한다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 파괴 전에 격리 대상을 확인한다 (Priority: P1)

운영자가 어떤 행도 삭제하지 않는 dry-run을 먼저 돌려, 격리 대상이 정확히 무엇인지 리포트로 확인한다. 리포트에는 대상 건수, 타입별·importance 구간별 분포, 표본 A가 담기고, 판별식 결함이 없는지(FR-002j 전수 검증)와 본문 형태 분포, 코퍼스 수준 대조 결과가 함께 확인된다.

**Why this priority**: 프로덕션 DB에 대한 파괴적 작업이다. 판별식이 잘못 잡거나 대상 안에 정보량 있는 본문이 섞여 있으면 되돌릴 수 없는 손실이 된다. dry-run만으로도 "무엇을 지우게 되는가"라는 질문에 답이 나오므로 단독으로 가치가 있다.

**Independent Test**: dry-run을 실행하면 리포트가 생성되고 대상 DB의 행 수는 실행 전후로 완전히 동일하다(집계·표본은 라이브 DB 읽기 전용 질의, 소요 실측만 사본에서 수행 — FR-006c). 리포트의 대상 건수가 24,086건 근방이고 표본 A의 모든 행이 `subject`를 갖는 형태 (1) 템플릿이다.

**Acceptance Scenarios**:

1. **Given** 라이브 DB와 dry-run 모드, **When** 격리 절차를 실행하면, **Then** 대상 건수·타입 분포·importance 분포·표본 A가 리포트로 출력되고 라이브 DB는 행 수도 내용도 변경되지 않는다.
2. **Given** dry-run 리포트, **When** 운영자가 확인하면, **Then** 전수 검증 결과(오탐 0건)와 본문 세 형태의 분포, 그리고 표본 A 50건의 실제 문장을 볼 수 있다.
3. **Given** dry-run 리포트, **When** 코퍼스 대조 결과를 확인하면, **Then** 격리 대상과 episodic·procedural 집합의 교집합이 0건이고 대상의 triple 조합이 `kg_triple`에 남아 있음이 보고된다.
4. **Given** 형태 (2)(원문 폴백)가 전체 대상의 5%를 넘는 경우, **When** dry-run 집계가 이를 드러내면, **Then** "정보량 0" 전제가 깨진 것이므로 실행하지 않고 해당 부분집합의 처리를 별도로 결정한다.

### User Story 2 - 백업과 롤백 경로를 갖춘 채 격리를 실행한다 (Priority: P2)

운영자가 무결성 점검·백업·사본 리허설을 마친 뒤, 프로덕션 서버를 정지하고 라이브 격리를 실행한다. 대상 semantic이 검색 후보에서 사라지고, 연쇄적으로 임베딩·벡터 인덱스·전문 검색 인덱스의 잔재도 함께 정리된다. 실행은 배치 상한 때문에 여러 번 반복되고 전체 원자성이 없으므로, 중간에 멈추면 진행 기록을 근거로 실패 지점부터 재개한다. 판별식 자체가 틀렸을 때만 백업으로 되돌린다.

**Why this priority**: 실제 개선이 일어나는 단계지만 US1의 확인 없이는 실행할 수 없다. 백업·롤백이 함께 있어야 파괴적 작업으로서 승인 가능하다.

**Independent Test**: 사본 A 구동 검증(FR-007b)과 무결성 점검이 통과한 상태에서 라이브 격리를 실행하면 대상 semantic이 검색되지 않는다. 중단 후 재개는 사본 B 리허설에서 미리 확인되어 있다.

**Acceptance Scenarios**:

1. **Given** 격리 실행 요청, **When** 사전 무결성 점검이 실패하면, **Then** 실행이 중단되고 어떤 행도 변경되지 않는다.
2. **Given** 사본 리허설 통과, **When** 라이브 실행을 시작하면, **Then** 프로덕션 서버가 정지된 상태에서 재집계 → 격리 → 잔재 정리 → `VACUUM` 순으로 진행되고, 완료 후 재기동된다.
3. **Given** 무결성 점검 통과와 백업 완료, **When** 격리를 실행하면, **Then** 실행 직전 재집계한 FR-001 대상 전량이 검색 대상에서 제외된다.
4. **Given** 격리 실행 완료, **When** 임베딩·벡터 인덱스·전문 검색 인덱스를 조회하면, **Then** 격리된 기억에 대응하는 잔재 행이 남아 있지 않다.
5. **Given** 반복 실행이 중간에 실패해 일부만 삭제된 상태, **When** 원인을 해소하고 재실행하면, **Then** 이미 삭제된 건은 판별식에서 자연히 빠지고 남은 대상만 이어서 처리된다.
6. **Given** 반복 실행 중단, **When** 진행 기록을 확인하면, **Then** 성공한 ID·실패한 ID·실패 사유가 남아 있어 재개 지점을 판단할 수 있다.
7. **Given** 판별식 자체가 틀렸다고 판단한 경우, **When** 서버를 정지하고 사본 A를 라이브 경로로 교체하면(`-wal`·`-shm` 포함), **Then** 실행 직전 상태로 복원되고 절차가 재현 가능하게 기록되어 있다.

### User Story 3 - 격리 효과와 부수 피해 없음을 검증한다 (Priority: P3)

운영자가 dry-run 때 고정해 둔 질의 10개를 사본 A(격리 전)·사본 B(격리 후)에 각각 돌려, 사람이 쓴 기억이 실제로 상위에 올라왔는지 대조한다. 격리 대상이 아닌 기억이 사라지지 않았는지도 확인하고, 저장 공간 회수량을 기록한다.

**Why this priority**: 격리 자체가 목적이 아니라 검색 품질 회복이 목적이므로 효과 확인이 필요하다. 다만 US1·US2가 끝나야 측정할 수 있다.

**Independent Test**: dry-run 때 고정한 질의 10개를 사본 B에 돌려 사본 A 기록과 대조하면, 형태 (1) 템플릿 문장이 하나도 없고 사람이 쓴 기억의 비율이 올라갔으며, episodic·procedural 건수는 실행 직전 재집계값과 동일하다.

**Acceptance Scenarios**:

1. **Given** 사본 A의 사전 기록과 격리를 적용한 사본 B, **When** 동일한 질의 10개로 기억 주입을 호출하면, **Then** 반환된 기억 중 형태 (1) 템플릿 문장이 0건이다.
2. **Given** 격리 전후 기록, **When** 질의별 반환 구성을 비교하면, **Then** 사람이 쓴 기억의 비율이 상승했음이 수치로 확인된다.
3. **Given** 격리 완료, **When** 타입별 건수를 세면, **Then** 실행 직전 재집계한 episodic·procedural 건수가 변하지 않았다.
4. **Given** 격리와 공간 회수 작업 완료, **When** DB 파일 크기를 측정하면, **Then** 실행 전후 크기와 감소량이 기록되어 있다.

### Edge Cases

- **판별식이 `subject` 없는 행을 잡는 경우**: 조건상 불가능하지만 발생하면 판별식·인덱스 결함이므로 실행을 중단하고 원인부터 찾는다.
- **`subject`의 `_`·`%`가 LIKE 와일드카드로 해석됨**: `LIKE subject || '_ %'` 방식은 `subject` 값을 패턴에 그대로 넣으므로, `subject`가 `a_c`인 행이 `abc…`로 시작하는 content를 잘못 매칭할 수 있다. 실측상 `_` 포함 `subject`가 941건이며 현재는 우연히 오분류가 없다. FR-002i가 위치 비교를 강제해 이 경로를 차단한다.
- **본문이 원본 episodic 그대로인 행(#768 폴백)**: FR-001b로 격리에서 제외한다. 아래는 그 결정에 이르기까지의 근거다 — `buildTripleSentence` 재조립이 실패하면 사람이 쓴 원문이 content로 저장된다(`semantic-memory-scoring.ts:31-37`). 사람이 쓴 문장이지만 파이프라인 산출물이라 오탐이 아니다. 형태 기준으로 오탐을 판정했다면 여기서 잘못 멈췄을 것이다 — FR-002a가 `subject` 기준을 쓰는 이유다.
- **출처 episodic이 이미 삭제된 triple**: 건별로는 식별할 수 없다(FR-004a). 구조화된 사실 자체는 `kg_triple`에 남으므로 완전 소실은 아니지만, 자연어 서술은 사라진다. 이 손실은 정보량이 0에 가깝다는 판단(Problem Statement)을 근거로 수용한다.
- **격리 도중 중단(프로세스 종료·디스크 부족)**: 이미 처리된 건은 연쇄 정리까지 완결된 상태이고 나머지는 손대지 않은 상태다. 재실행으로 이어서 진행한다.
- **재실행 시 대상 재집계**: 판별식이 이미 삭제된 건을 제외하므로 재실행마다 대상 건수가 줄어든다. 진행 기록의 누적 성공 수를 반영한 기대값과 대조한다(FR-004b).
- **대상 건수가 예상보다 크게 늘어난 경우**: 서버를 정지했는데도 늘었다면 미확인 프로세스가 쓰고 있다는 뜻이다. ±5%를 넘으므로 실행하지 않고 원인부터 찾는다.
- **대상 건수가 예상보다 크게 줄어든 경우**: 다른 경로로 이미 삭제가 일어났을 수 있다. 마찬가지로 중단하고 무엇이 지웠는지 확인한다 — 백업 없이 진행된 삭제라면 복구 근거가 없다.
- **DB 경로가 상대 경로 또는 `~` 포함**: 확장되지 않아 엉뚱한 DB를 대상으로 삼을 수 있다. 절대 경로가 아니면 실행을 거부한다.
- **`convert_episodic_to_semantic`으로 만든 semantic**: 사람이 호출했지만 같은 파이프라인을 거쳐 subject를 가지므로 판별식에 걸리고, DB상 자동 추출물과 구분할 수 없다. FR-002a가 오탐을 `subject` 기준으로 정의하므로 이는 오탐이 아니다. 시기 분리 보고(FR-002b)로 규모를 드러내고 구간 밖 표본을 따로 검토한다.
- **표본을 OFFSET으로 뽑음**: `ORDER BY id LIMIT n OFFSET <random>`은 연속 구간을 반환한다. id가 시간순이므로 같은 작업 세션의 triple만 뽑혀 대표성이 사라진다. FR-002d가 `ORDER BY random()`을 명시하는 이유다.
- **대상이 표본 크기보다 적음**: 표본 A의 모수가 50건 미만이면 전수를 검토한다. 0건이면 격리할 것이 없으므로 실행하지 않는다.
- **일반 CLI로 vec·FTS 잔재를 확인하려 함**: `sqlite3`에 `vec0`·`fts5` 모듈이 없으면 테이블을 열 수 없어 "잔재 0행"을 확인할 수단이 없다. 확장을 로드한 경로를 쓴다(FR-006j).
- **격리 후 재추출을 시도함**: 출처 episodic의 `triple_extracted=1`이 남아 스킵된다(FR-006k). 이유를 모르면 원인을 찾느라 시간을 쓴다. 복구가 필요하면 FR-006i 내보내기의 출처 ID 목록으로 플래그를 리셋해야 하며, 그 전에 #805와 재조립 실패 원인이 해소되어야 한다(FR-006l).
- **관계 그래프가 대량으로 끊김**: `memory_relation` 62,289행 중 54,742행(88%)이 CASCADE로 사라지고, 그 전부가 생존 기억과 이어진 관계다. `kg_triple`은 이를 보존하지 않으므로 FR-006i의 내보내기가 유일한 기록이 된다.
- **앵커 슬롯이 격리 대상을 가리킴**: `anchor.memory_id`가 NULL이 되어 슬롯이 빈다. 실측상 `memory_id`가 설정된 앵커는 전체 3건이라 영향 규모는 무시할 수준이다. recall의 `auto_set_anchor`가 다음 호출에서 다시 채우므로 자가 복구되며, 별도 조치 없이 dry-run 보고로 갈음한다.
- **핀 고정된 자동 triple**: `forget`은 핀된 기억에서 예외를 던지므로 반복 루프가 같은 지점에서 계속 실패한다. FR-001a로 판별식에서 아예 제외하고 dry-run이 별도 목록으로 출력한다.
- **공간 회수 중 실패**: `VACUUM`은 DB 크기에 준하는 임시 사본 공간을 요구하므로(518MB 기준 최소 그만큼의 여유 디스크), 공간이 모자라면 실패한다. 기억은 이미 격리된 상태이므로 격리 성공 여부와 분리해 판정하고, 디스크를 확보해 재시도한다.
- **잔재 정리를 잊고 VACUUM 실행**: `event_outbox`와 `memory_forgetting_event` 고아가 남은 채로 공간을 측정해 감소량이 크게 과소 보고된다(실측 기준 37.7MB 이상). FR-010이 두 정리를 VACUUM보다 앞에 두는 이유다.
- **`PRAGMA foreign_keys`가 꺼진 세션에서 실행**: `memory_item`만 지워지고 `memory_embedding`·vec·FTS가 통째로 고아가 된다. 실행 전 pragma 상태를 확인하고, 꺼져 있으면 실행을 거부한다.
- **dry-run 시점과 실행 시점 사이에 신규 파이프라인 산출물 유입**: 실행 시 대상 건수가 리포트와 달라진다. 실행 직전 재집계로 차이를 드러낸다. 서버 정지(FR-008a)가 유입을 막고, 근본 차단은 #805다.
- **서버가 붙은 채 실행**: `SQLITE_BUSY`로 배치가 산발 실패한다. 재개로 복구되지만 진행 기록이 실패로 뒤덮여 실제 문제를 가린다. FR-008a로 사전 차단한다.
- **산출물을 저장소 안에 생성**: `.gitignore`가 `*.db`·`memory.db*`는 막지만 `.md`·`.json` 리포트는 막지 않는다. 표본 A의 기억 본문이 그대로 커밋될 수 있다. FR-006b로 `.local/` 밖 생성을 금지한다.
- **라이브에서 검증 프로브를 돌림**: `memory_injection`이 반환 기억의 `recall_count`·`g_value`·`consolidation_score`를 UPDATE하므로 FR-011이 깨지고, 랭킹 점수가 오른 채로 격리 후 측정을 하게 돼 SC-001a의 상승분이 격리 효과인지 프로브 효과인지 구분되지 않는다. FR-003a·003b가 사본을 강제한다.
- **백업이 0바이트 또는 부분 파일로 생성됨**: `db:backup` 산출물 19개 중 0바이트 파일이 실재한다. 스크립트의 크기 0 삭제 로직이 항상 동작하지는 않는다는 뜻이므로, 크기 대조(FR-007c)를 먼저 걸어 값싸게 잡는다. 부분 파일은 스키마가 온전해 서버 구동에는 성공할 수도 있어 구동 검증만으로는 부족하다.
- **사본 A가 열리지 않음**: 백업이 손상됐다는 뜻이므로 롤백 근거가 없다. FR-007b가 이를 파괴적 실행 전에 잡는다 — 서버 구동 실패 시 진행하지 않는다.
- **리허설 중 라이브가 계속 자람**: 사본 A를 뜬 뒤 리허설이 도는 동안 라이브 코퍼스는 계속 늘어난다(실측: 40분에 형태 (2) 10건 증가). 그래서 정지 시작 직후 재집계(FR-004b)로 ±5% 게이트를 다시 통과시켜야 하며, 리허설이 길수록 이 게이트에 걸릴 확률이 커진다. 걸리면 사본 A부터 다시 뜬다.
- **리허설 소요가 정지 창구를 넘김**: 사본 B 실측 결과 전체 소요가 감당 가능한 정지 시간을 넘으면, 실행을 여러 창구로 나눈다. 재개가 기본 경로(FR-005b)이므로 분할 실행 자체는 추가 설계가 필요 없다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 격리 대상은 `type='semantic' AND subject IS NOT NULL AND subject <> '' AND pinned = FALSE` **AND 본문이 형태 (1)(재조립 성공 템플릿, 판별 방법은 FR-002i)** 인 행으로 확정한다. 2026-08-22 실측으로 `subject` 보유 24,202건 중 **24,086건**이 이에 해당한다(모수는 세션 중에도 24,192 → 24,202로 늘었다 — 실행 시점 재집계가 기준이며 FR-004b가 이를 다룬다).
- **FR-001a**: 판별식에 걸리지만 `pinned = TRUE`인 항목은 격리하지 않는다. 핀은 사람이 명시한 보존 의사이므로 자동으로 해제하지 않으며, dry-run이 해당 목록을 별도로 출력해 운영자가 개별 판단한다. 2026-08-22 실측으로는 해당 항목이 0건이며, 이 조항은 실행 시점 신규 유입에 대비해 유지한다.
- **FR-001b**: 형태 (2)(원문 폴백)와 형태 (3)(`·` 조인)은 격리하지 않는다. 형태 (2)의 본문은 사람이 쓴 원문(평균 305자)이라 템플릿 파편과 달리 검색 가치가 있고, 실측 116건은 전체의 0.48%라 남겨도 랭킹을 오염시키지 않는다. **다만 이 근거는 비중이 작다는 데 기대므로, 형태 (2)가 계속 늘면 재검토해야 한다** — 2026-08의 폴백률이 11.6%로 급증했고(FR-001c), 이 추세가 이어지면 제외 대상이 수천 건이 되어 "무시 가능"이 성립하지 않는다. "정보량 0인 것만 지운다"는 Problem Statement의 원칙을 판별식에 직접 반영한 것이다. dry-run이 제외된 행의 ID 목록을 리포트에 남긴다.
- **FR-001c**: dry-run은 형태 (2)의 **월별 생성 추이**를 리포트에 남긴다. 2026-08-22 실측에서 재조립 실패율이 2026-05 0.0% → 06 0.0% → 07 0.1% → **08 11.6%**로 급증했다. 이는 격리 이후에도 형태 (2)가 계속 쌓인다는 뜻이며, FR-001b의 제외 근거(비중이 작다)가 언제까지 유효한지를 판단하는 자료다.
- **FR-001d**: dry-run은 대상의 **귀속 분포**를 보고한다 — `project_id`·`owner_id`·`privacy_scope`별 건수, 그리고 `is_deleted`·`deleted_at`이 설정된 행 수. 2026-08-22 실측은 24,086건 전부 `project_id` NULL·`owner_id` NULL·`privacy_scope` private이고 소프트 삭제 표시가 0건이다. 코퍼스에는 프로젝트 7개와 소유자 2명이 존재하므로, 대상에 NULL이 아닌 값이 나타나면 파이프라인이 귀속을 채우기 시작했다는 뜻이니 실행 전에 재검토한다.
- **FR-001e**: 판별식에 `project_id IS NULL` 같은 귀속 조건은 **넣지 않는다**. 현재 대상이 전부 NULL이라 무의미하고, 조건을 박으면 나중에 프로젝트별 파이프라인 산출물이 생겼을 때 그것만 영구히 남아 문제가 절반만 해결된다 — 시기 조건을 판별식에 넣지 않기로 한 것(FR-002c)과 같은 논리다. 대신 FR-001d의 보고로 변화를 감시한다.
- **FR-001f**: dry-run이 `recall_count`를 보고할 때는 **출발값이 타입마다 다르다는 점**을 함께 적는다. `remember`로 만든 기억은 `recall_count = 1`로 시작하고(`remember-tool-memory-item.ts:64`), `createSemanticMemory`는 이 컬럼을 INSERT에 넣지 않아 **0**에서 시작한다. 두 값을 직접 비교하면 episodic이 전부 "반환된 적 있음"으로 보이는 착시가 생긴다.
- **FR-002**: dry-run은 두 가지를 확인해 리포트에 남긴다. (a) **판별식의 정확성** — `memory_item.subject`에 값을 쓰는 코드 경로가 `createSemanticMemory` 하나뿐이라는 사실. 사람이 직접 본문을 쓰는 `remember`와 agent promotion 경로는 이 컬럼을 채우지 않는다. (b) **대상 본문의 구성** — 전체 대상의 형태별 집계(FR-002g), 오탐 전수 검증(FR-002j), 그리고 표본 A의 육안 검토.
- **FR-002a**: **오탐의 정의** — 오탐이란 판별식 자체의 결함으로 걸린 행이다. 두 종류가 있다. (i) `subject`가 비어 있는데도 걸린 행 — `subject`가 채워졌다는 것이 `createSemanticMemory`를 거쳤다는 유일하게 신뢰할 수 있는 신호이므로(FR-002 (a)), 이것이 깨지면 전제가 무너진다. (ii) 형태 (1)이 아닌데 형태 (1)로 분류돼 걸린 행 — FR-002i의 위치 비교가 잘못 매칭한 경우다. 사람이 쓴 문장이 본문이라는 사실만으로는 오탐이 아니다(형태 (2)는 애초에 대상이 아니고, 그 판정은 FR-001b가 이미 처리한다).
- **FR-002b**: `convert_episodic_to_semantic`은 사람이 명시적으로 호출하는 MCP 도구지만 `semantic-memory-update-pipeline`을 거쳐 같은 `createSemanticMemory`에 도달하므로, 그 산출물도 subject를 갖고 판별식에 걸린다. DB상 자동 추출물과 구분할 컬럼이 없다. dry-run은 대상을 백필 버스트 구간(2026-04·2026-05)과 그 밖으로 나눠 보고한다. 다만 형태 (1)끼리는 육안으로 출처를 구분할 수 없으므로, 이 보고의 용도는 구간별 편중 감시에 한정된다.
- **FR-002c**: 형태 (2)는 실측상 **전량이 백필 버스트 구간 밖**에 있다(구간 안 0.00%, 구간 밖 3.28%). 백필은 전부 재조립에 성공했고 폴백은 평상시 운영 중 생성분에만 발생했다는 뜻이다. FR-001b가 형태 (2)를 제외하므로 이 편중은 그 자체로 처리되며, dry-run은 구간별 형태 분포(전수 집계)를 계속 보고해 새로운 편중이 나타나는지 확인한다. 시기 조건은 판별식에 넣지 않는다 — 넣으면 구간 밖 템플릿 파편이 그대로 남아 문제가 절반만 해결된다.
- **FR-002d**: 표본은 **표본 A** 하나만 둔다 — 전체 대상에서 무작위 50건. 추출은 `ORDER BY random() LIMIT 50`으로 한다. `ORDER BY id LIMIT 50 OFFSET <random>` 방식은 id가 시간순이라 **연속 블록**을 뽑아 같은 세션·같은 시기의 행만 나온다(실제로 그렇게 뽑아 보니 50건 전부 한 달치였다). 역할은 오탐 판정이 아니라(그것은 FR-002j의 전수 검증이 맡는다) 운영자가 "이 문장들을 정말 지워도 되는가"를 눈으로 확인하는 것이다. 구간 밖을 별도로 뽑던 표본 B는 폐지한다. 표본 B의 목적은 형태 (2) 검출이었는데 FR-001b가 형태 (2)를 판별식에서 아예 제외해 목적이 달성됐고, 남는 목적(사람이 호출한 `convert_episodic_to_semantic` 산출물 식별)은 형태 (1)끼리 육안으로 구분할 수 없어 표본으로 달성할 수 없다. 구간별 감시는 표본이 아니라 FR-002g의 전수 집계가 맡는다.
- **FR-002e**: 구간별 건수는 실행 시점에 재집계한다. 에픽 #803의 백필 실측(2026-04 9,238건 + 2026-05 12,369건 = 21,607건)은 semantic 전체 25,520건 대비 약 85%로 서술된 값이고, 격리 대상 23,664건을 모수로 하면 비율과 구간 밖 건수가 달라진다. 스펙은 구간 밖 규모를 고정 숫자로 못박지 않는다.
- **FR-002f**: 대상의 본문은 세 형태를 가질 수 있다(`semantic-memory-scoring.ts`의 `tripleToNaturalLanguage`). (1) `buildTripleSentence` 성공 시 `~는 ~를 …합니다` 템플릿 문장, (2) 재조립 실패 + 폴백 존재 시 **원본 episodic 본문 그대로**(#768), (3) 재조립 실패 + 폴백 없음 시 `subject · predicate · object` 조인(2026-08-22 실측 0건). **형태 (2)는 사람이 쓴 문장이지만 파이프라인 산출물이므로 오탐이 아니다.** 본문 형태를 오탐 기준으로 삼으면 이 행에서 잘못된 중단이 일어난다.
- **FR-002g**: 본문 형태 분포는 표본이 아니라 **`subject`를 가진 semantic 전체를 집계**해 구한다(격리 대상뿐 아니라 제외분까지 모수에 넣어야 제외 규모를 알 수 있다). 형태 (3)은 content가 `subject · predicate · object` 조인과 정확히 일치하는 행, 형태 (1)은 content가 `subject` + 조사 1글자 + 공백으로 시작하는 행, 형태 (2)는 나머지다.
- **FR-002h**: 형태 (2)·(3)이 FR-001b로 판별식에서 제외되므로 별도의 비율 게이트는 두지 않는다. 대신 dry-run은 형태별 건수를 리포트에 남기고(FR-002g), 형태 (1)로 분류된 행 중 템플릿으로 보이지 않는 것이 표본에서 발견되면 형태 판별 자체를 재검토한다.
- **FR-002i**: 형태 (1) 판별은 **`LIKE`가 아니라 문자열 위치 비교로 수행한다** — `substr(content, 1, length(subject)) = subject AND substr(content, length(subject)+2, 1) = ' '`. `content LIKE subject || '_ %'`는 `subject` 값이 패턴에 그대로 삽입되므로 그 안의 `_`·`%`가 와일드카드로 해석된다. 2026-08-22 실측에서 `subject`에 `_`를 포함한 행이 **941건** 있었고 세 방식의 결과가 우연히 같았지만(각 24,086건), 이는 보장이 아니다. 같은 이유로 형태 (3) 판별도 `LIKE`가 아닌 등호 비교를 쓴다. `+2`가 공백 위치인 근거는 `attachParticle`이 종성 유무·한글 여부와 무관하게 조사를 **정확히 1글자**(은/는) 붙이기 때문이다. `buildTripleSentence`는 `subject.trim()`을 쓰므로 DB 값에 앞뒤 공백이 있으면 어긋나지만, 2026-08-22 실측에서 `subject`·`predicate`·`object` 모두 공백·개행이 0건이었고 raw·trim 기준 결과가 같았다(각 24,086건). 방어적으로 비교 양쪽에 `trim`을 적용한다. 표본 A에는 각 행의 형태를 표기해 육안 검토를 돕는다.
- **FR-002j**: 오탐 판정은 표본이 아니라 **전수 검증**으로 수행한다. (i)은 대상 집합에 `subject`가 비어 있는 행이 있는지 세어 0건임을 확인한다(판별식상 구조적으로 0이어야 한다). (ii)는 형태 (1) 건수를 **두 가지 독립 방식**(FR-002i의 위치 비교와, `_`·`%`를 이스케이프한 `LIKE`)으로 각각 세어 일치하는지 본다. 건수가 갈리면 오분류가 존재한다는 뜻이므로 실행하지 않는다. 표본 50건은 오탐률 6% 미만(모수 24,086 기준 최대 1,445건)만 보장하므로 이 판정의 근거로 삼지 않는다.
- **FR-003**: 파괴적 실행 이전에 dry-run을 먼저 수행해야 한다. dry-run은 대상 건수, 타입 분포, importance 분포, 표본 A를 리포트로 출력하고 DB를 변경하지 않는다.
- **FR-003a**: dry-run 단계에서 검증용 질의 10개를 확정한다. 격리 전/후 기억 주입 결과(질의별 반환 ID·타입·본문 형태)는 **라이브 DB가 아니라 사본에서** 얻는다. 절차는 다음 순서다.
  1. `npm run db:backup`으로 **사본 A**(격리 전 상태)를 만든다.
  2. 사본 A를 복사해 **사본 B**를 만든다.
  3. 사본 A에 질의 10개를 한 번씩 돌려 **before** 기록을 얻는다.
  4. 사본 B에 **전량 격리를 실행**한다 — 이것이 리허설이자 소요 실측이다(FR-006c).
  5. 사본 B에 같은 질의 10개를 한 번씩 돌려 **after** 기록을 얻는다.
  6. 리허설과 대조가 모두 통과해야 라이브 실행으로 넘어간다(FR-006g).
  이 기록이 없으면 실행 단계로 진행하지 않는다.
- **FR-003b**: 사본을 쓰는 이유는 `memory_injection`이 읽기 전용이 아니기 때문이다. `knowledge-context-bundle-builder`는 반환된 각 기억의 `memory_item` 행을 UPDATE해 `recall_count`·`last_accessed_at`·`g_value`·`consolidation_score`를 갱신한다. 라이브에서 프로브하면 (a) 사람이 쓴 기억의 내용이 변해 FR-011을 위반하고, (b) `g_value`·`consolidation_score`가 랭킹에 쓰이므로 프로브가 올린 점수 때문에 격리 후 비율이 오른 것인지 격리 덕인지 구분할 수 없어 SC-001a가 무의미해진다. 사본 A·B 모두 프로브를 정확히 1회씩 받으므로 오염이 대칭이고 대조가 공정하다.
- **FR-003c**: 진단 목적의 `recall` 호출에는 `auto_set_anchor: false`를 준다(#811). 앵커 슬롯이 프로브 때문에 바뀌면 운영 상태가 오염된다.
- **FR-003d**: 사본에 질의를 돌리려면 `DB_PATH`를 사본으로 지정한 **별도 서버 인스턴스**가 필요하다(`memory_injection`은 MCP 도구다). 프로덕션 서버는 FR-008a로 정지 상태이므로 충돌하지 않는다. 임베딩은 실측상 minilm(로컬 ONNX)이 28,427건으로 사실상 전량이라 외부 API 없이 동작하며, `db:backup`이 online backup API로 DB 페이지 전체를 복사하므로 `memory_item_vec_*` 가상 테이블도 함께 넘어간다.
- **FR-004**: 출처 episodic 대조는 코퍼스 수준으로 수행한다. dry-run이 (a) 격리 대상과 episodic·procedural 집합이 겹치지 않음, (b) 격리 대상의 subject/predicate/object 조합이 `kg_triple`에 보존됨을 각각 확인해 리포트에 남긴다. **(b)는 격리의 핵심 정당화 근거다** — 자연어 서술이 사라져도 구조화된 사실이 남는다는 것을 이 확인이 보장한다. 보존율이 100% 미만이면 그 차이만큼이 진짜 소실이므로 실행 전에 재검토한다. 다만 (b)가 보장하는 것은 **조합의 존재이지 그 품질이 아니다** — `kg_triple`도 정규화에 실패한 predicate를 그대로 받는다(FR-004d).
- **FR-004a**: `createSemanticMemory` 자체는 출처 식별자를 저장하지 않는다(`memory_link`·`source_session_id`·`origin_source` 모두 미기록). 그러나 **관계 엔진이 `memory_relation`에 `extracted_from`(Semantic→Episodic 출처)과 `supported_by`(Episodic→Semantic 지지)를 기록해 왔다** — 2026-08-22 실측으로 격리 대상에 걸린 것이 각각 25,069건이다. 즉 건별 출처 추적은 상당 부분 가능하다. 형태 (2)는 본문이 원문 사본이므로 content 일치로도 대조할 수 있다(FR-004c).
- **FR-004b**: 실행 직전 대상 건수를 재집계하고 dry-run 리포트값과 대조한다. 차이가 ±5%를 넘으면 실행하지 않고 dry-run부터 다시 수행한다. 첫 실행이 아닌 재개 시에는 직전 진행 기록의 누적 성공 수를 반영한 기대값과 대조한다.
- **FR-004c**: dry-run은 형태 (2) 각 행에 대해 동일 content 또는 앞 80자가 일치하는 episodic이 남아 있는지 대조하고, 원본이 없는 건의 ID를 리포트에 남긴다. 2026-08-22 실측으로는 106건 중 105건이 매칭되고 1건만 원본이 없다.
- **FR-004d**: dry-run은 `kg_triple`의 **predicate 정규화 지표**를 스냅샷으로 남긴다 — 한글 종결 비율, 공백 포함 비율, 평균 길이. 2026-08-22 실측은 24,204건 중 한글 종결 23,218(96%), 공백 포함 5,793(24%), 평균 4.1자다. 이는 격리 대상의 s/p/o가 보존되는 저장소가 어떤 상태였는지를 남기는 기준선이며, 정규화 실패 predicate 유입(FR-001c)이 이어지면 이 지표가 떨어진다.
- **FR-005**: 격리는 기존 `forget` 도구(`hard=true`, `confirm=true`)로 수행한다. `forget`의 배치 상한이 100건이므로 반복 호출이 필요하며, 반복을 관리하는 러너는 삭제·연쇄 정리 로직을 재구현하지 않는다.
- **FR-005a**: `POST /admin/introspection/heal`은 사용하지 않는다. 선별 기준이 저신뢰·고실패 스캔이라 본 대상(triple 보유)과 일치하지 않고, 대상 다수가 `importance ≥ 0.8`이라 soft-delete가 아닌 demote로 분류되며, soft-delete는 공간 회수·연쇄 정리를 수행하지 않는다.
- **FR-005b**: 반복 실행은 재개 가능해야 한다. 각 배치의 성공 ID·실패 ID·실패 사유를 진행 기록으로 남기고, 중단 후 재실행하면 남은 대상만 처리한다(판별식이 이미 삭제된 건을 제외하므로 별도 커서가 불필요하다).
- **FR-005c**: 부분 삭제 상태는 손상으로 취급하지 않는다. 백업 복원은 판별식 자체가 틀렸다고 판단한 경우에만 수행한다.
- **FR-005d**: 러너는 프로덕션 서버가 정지된 상태에서 `forget`을 자신이 단독으로 소유한 프로세스·DB 세션 안에서 구동한다. FR-008a의 "서버 정지"와 충돌하지 않는다 — 금지되는 것은 러너 외의 쓰기 프로세스다. 구체적 호출 메커니즘(도구를 in-process로 인스턴스화할지, 러너 전용 세션을 띄울지)은 plan에서 정한다.
- **FR-006**: 격리 시 `memory_embedding`(semantic 24,778행), `memory_item_vec_*`, `memory_item_fts`의 대응 잔재를 연쇄 정리한다. 이 정리는 FK `ON DELETE CASCADE`와 `memory_embedding_vec_delete`·`memory_item_fts_delete` 트리거가 수행하므로, 실행 세션에서 `PRAGMA foreign_keys = ON`이 켜져 있음을 확인해야 한다. 두 트리거가 라이브 DB에 실재함을 2026-08-22에 직접 확인했고, `memory_embedding_vec_delete`는 provider 분기 없이 `memory_item_vec`·`_tfidf`·`_minilm`·`_openai`·`_gemini`를 모두 지우므로 minilm 임베딩이 기본 테이블과 provider 테이블에 이중 적재된 경우도 함께 정리된다.
- **FR-006a**: `ON DELETE SET NULL`인 참조(`kg_triple.representative_memory_id`, `anchor.memory_id`, `agent_session.summary_memory_id`, `agent_memory_promotion_candidate.memory_id`·`merge_target_memory_id`)는 행이 남고 참조만 NULL이 된다. 이들은 검색 후보가 아니라 랭킹을 오염시키지 않으므로 그대로 둔다. dry-run이 NULL이 될 행 수를 참조별로 보고한다.
- **FR-006b**: (헌법 v1.2.0 Additional Constraints의 "재배포 불가 코퍼스 커밋 금지·공개 문서엔 집계만" 규칙과 같은 계열이다.) 기억 본문이 담기는 산출물(dry-run 리포트, 진행 기록, 검증용 사전/사후 기록)은 저장소 안에 만들 경우 `.local/` 아래에만 두고 커밋하지 않는다. 백업 스냅샷은 기존 `npm run db:backup`이 만드는 `<DB_PATH 디렉터리>/backups/`에 둔다 — 저장소 밖이라 커밋 대상이 아니다. 스펙·이슈·PR 등 공개 문서에는 건수·분포·ID·해시 같은 집계만 싣는다.
- **FR-006c**: 소요 시간은 추정하지 않고 **사본 B의 전량 격리 리허설로 실측**한다(FR-003a의 사본 B 생성이 곧 리허설이다). 리허설은 소요 시간뿐 아니라 연쇄 정리 결과, `VACUUM` 회수량, 그리고 **의도적 중단 후 재개**(SC-006a)까지 라이브 실행 전에 확인시켜 준다. 이 값이 서버 정지 창구(FR-008a)를 잡는 근거다.
- **FR-006d**: `memory_forgetting_event`는 `memory_id`에 FK가 없어 격리해도 행이 자동으로 정리되지 않는다. **격리된 ID를 참조하는 행을 `VACUUM` 전에 일괄 정리한다.** 참조 대상이 사라진 뒤에는 정보가 아니라 잔재이며, FR-009a가 `event_outbox`에 적용하는 것과 같은 논리다. `forget` 도구는 이 테이블에 쓰지 않으므로 이번 실행으로 새 행이 늘지는 않는다.
- **FR-006e**: `ON DELETE CASCADE` 참조는 전량 자동 정리된다 — 라이브 DB에서 직접 읽은 목록은 `memory_item_tag`, `memory_relation`(source·target 양쪽), `memory_link`(source·target 양쪽), `feedback_event`, `memory_embedding`, `meta_memory_stats`, `memory_review_candidate`, `memory_provenance`, `agent_memory_promotion_candidate.summary_memory_id`다. SC-005의 "잔재 0행"은 이 집합을 가리킨다. 2026-08-22 실측 규모는 `memory_embedding` 24,086 · `memory_relation` 54,742 · `memory_review_candidate` 3,609 · `meta_memory_stats` 66 · `feedback_event` 10이고 나머지는 0이다.
- **FR-006f**: FR-006d의 정리 범위는 **격리된 ID를 참조하는 행에 한정**한다. 살아 있는 기억의 오래된 로그나 `action='review'` 중복 누적 일반은 건드리지 않는다 — 그것은 #810의 보존 정책 범위이며, 여기서 함께 지우면 격리와 무관한 행을 삭제하게 된다.
- **FR-006g**: 리허설이 실패하거나 기대와 다른 결과를 내면 라이브를 실행하지 않는다. 사본에서 확인되지 않은 절차를 프로덕션에 적용하지 않는다는 뜻이다.
- **FR-006h**: `memory_relation`은 `source_id`·`target_id` 양쪽이 CASCADE라 격리 대상이 한쪽 끝인 관계가 전부 삭제된다 — 실측 62,289행 중 **54,742행(88%)**이며 `extracted_from` 25,069 / `supported_by` 25,069 / 나머지 4,604다. **삭제되는 관계는 예외 없이 반대쪽 끝이 살아남는 기억이다**(양쪽 다 대상인 경우 0건). 따라서 이 손실은 "지워지는 것끼리의 링크"가 아니라 생존 기억과의 연결이 끊기는 것이다.
- **FR-006i**: 격리 전에 대상이 걸린 `memory_relation` 행을 **리포트로 내보낸다** — 대상 ID, `relation_type`, 반대쪽 ID, 반대쪽 타입. 본문이 아니라 식별자만 담으므로 크기가 작고 FR-006b의 `.local/` 규칙을 따른다. `extracted_from` 25,069건은 "이 사실이 어떤 대화에서 나왔는가"의 유일한 기록이며, `kg_triple`은 이 정보를 보존하지 않는다.
- **FR-006j**: `memory_item_vec_*`의 잔재 확인은 **`sqlite-vec` 확장을 로드한 경로**로 수행한다. 일반 `sqlite3` CLI에는 `vec0` 모듈이 없어 이 테이블들을 열 수 없으므로, 사본에 붙인 서버 인스턴스(FR-003d)나 확장을 로드한 스크립트를 쓴다. FTS 잔재도 같은 제약을 받는다(CLI에 `fts5` 모듈 부재).
- **FR-006k**: 격리는 출처 episodic의 `triple_extracted` 플래그를 **건드리지 않는다**. 실측상 episodic 3,431건 중 2,982건이 `triple_extracted=1 / success`이므로, 격리 후 같은 episodic에서 재추출을 시도해도 이미 처리됨으로 스킵된다. 이는 의도된 동작이다 — #805가 유입을 막기 전에 플래그를 리셋하면 같은 파편이 다시 쌓이고, 2026-08 폴백률 11.6%(FR-001c)를 감안하면 더 나쁜 것이 생성된다.
- **FR-006l**: 다만 **복구 경로는 문서로 남긴다**. FR-006i의 관계 내보내기에 `extracted_from`의 반대편(= 출처 episodic ID)이 들어 있으므로, 나중에 재추출이 필요해지면 그 목록으로 해당 episodic의 `triple_extracted`를 리셋하면 된다. 실행 순서상 #805(재오염 차단)와 재조립 실패 원인 해소가 선행되어야 한다.
- **FR-007**: 파괴적 실행 이전에 기존 `npm run db:backup`으로 백업(= 사본 A)을 생성한다. 이 도구는 SQLite online backup API를 쓰므로 실행 중 DB에서도 일관된 사본을 만든다.
- **FR-007a**: 롤백은 **사본 A를 라이브 경로로 교체**하는 것이다. 서버 정지 상태에서 수행하며 `-wal`·`-shm` 파일 처리를 절차에 포함한다. 기존 `db:restore-from-corrupt`는 손상 DB에서 읽히는 행만 옮기는 복구 도구라 이 용도에 쓸 수 없다. 절차는 문서로 남긴다.
- **FR-007b**: 크기 게이트(FR-007c)를 통과한 뒤, 백업의 내용 무결성은 **사본 A를 실제로 구동해** 확인한다. `db:backup` 산출물이 곧 사본 A이고, 거기에 서버를 물려 질의 10개(FR-003a 3단계)가 정상 반환되면 스키마·인덱스·`memory_item_vec_*`·FTS가 모두 살아 있다는 뜻이다. 타입별 건수 대조도 함께 기록한다. 구동이나 대조가 실패하면 파괴적 실행으로 진행하지 않는다. 별도의 "임시 경로 복원 후 건수 대조"는 이 검증에 포함되므로 따로 두지 않는다.
- **FR-007c**: 백업 직후 **사본 A의 파일 크기를 라이브와 대조**하고, 남아 있는 `-wal`·`-shm` sidecar가 있으면 함께 확인한다. 크기가 현저히 작으면 즉시 중단한다. 근거는 `db:backup` 산출물 19개 중 **0바이트 파일이 실재**한다는 것이다(`memory-backup-2026-06-15T12-41-09-792Z.db`) — 스크립트에 크기 0 삭제 로직이 있는데도 남아 있으므로 그 정리가 항상 동작한다고 가정할 수 없다. sidecar 잔재도 같은 이유로 확인한다. 값싼 1차 게이트를 통과한 뒤 FR-007b의 구동 검증으로 내용을 확인한다.
- **FR-008**: 파괴적 실행 이전에 `npm run db:pre-docker-deploy` 무결성 점검을 통과해야 한다. 실패 시 실행하지 않는다.
- **FR-008a**: **라이브 격리 구간에서만** 러너 외의 프로세스가 같은 DB에 쓰지 않아야 한다. 프로덕션 MCP·HTTP 서버가 붙어 있으면 (1) `SQLITE_BUSY`로 배치가 산발적으로 실패하고, (2) 신규 파이프라인 산출물이 유입돼 대상 집합이 흔들리며, (3) 배치 스케줄러의 망각 정책(`forgetting-policy-service`)이 working TTL 등을 근거로 **격리 대상이 아닌 기억까지** 지워 SC-002·FR-011이 우리 작업과 무관한 이유로 깨진다.
- **FR-008b**: 정지 구간은 **실행 직전 재집계(FR-004b)부터 `VACUUM` 완료(FR-010)까지**다. 백업·사본 복제·프로브·전량 리허설은 사본에서 이뤄지므로 라이브 서버를 올려둔 채 진행한다 — 서비스 중단이 라이브 실행분으로 한정되고, 재집계가 정지 직후에 일어나므로 사본 A 시점과의 변동폭도 작아진다.
- **FR-008c**: 재기동은 `VACUUM`과 사후 확인(SC-002·SC-005·SC-005a·SC-005b)이 끝난 뒤에 한다. US3의 전/후 대조는 사본 A·B에서 이뤄지므로 재기동을 기다리지 않는다.
- **FR-009**: 대상 DB 경로는 절대 경로여야 한다(`~`는 확장되지 않음). 절대 경로가 아니면 실행을 거부한다.
- **FR-009a**: `forget`은 삭제 건당 `event_outbox`에 `memory.forgotten` 이벤트를 적재하며 저장소에 정리 로직이 없다. 격리 후 이번 실행분(`event_type = 'memory.forgotten'` 이면서 `created_at`이 실행 시작 시각 이후)을 일괄 정리한다. 2026-08-22 실측으로 `event_outbox`가 0행이므로, 격리 후 남는 `memory.forgotten` 행은 곧 이번 실행분 전량이다. `event_outbox` 전반의 보존 정책 수립은 #810 범위다.
- **FR-010**: 격리와 잔재 정리(`event_outbox` FR-009a, `memory_forgetting_event` FR-006d)를 모두 마친 뒤 공간 회수(`VACUUM`)를 수행하고 실행 전후 DB 크기를 기록한다.
- **FR-011**: 격리 대상이 아닌 기억(episodic, procedural, working, 그리고 FR-001 조건에 걸리지 않는 semantic)은 건수와 내용이 변하지 않아야 한다. 여기에는 프로젝트·소유자가 지정된 기억과 `privacy_scope`가 `team`·`public`인 기억이 포함된다 — 실측상 대상에는 이런 행이 0건이다. `recall_count`·`g_value`·`consolidation_score` 같은 recall 메타데이터도 포함한다 — 그래서 검증 프로브를 라이브가 아니라 사본에서 돌린다(FR-003b).

### Key Entities

- **파이프라인 산출 triple semantic**: `subject`/`predicate`/`object`가 채워진 semantic 기억. `createSemanticMemory`를 거쳐 만들어졌다. 본문은 대개 `~는 ~를 …합니다` 템플릿이지만, 재조립 실패 시 원본 episodic 본문이나 `s · p · o` 조인일 수도 있다(FR-002f). 대화에서 자동 추출된 것이 대다수지만 `convert_episodic_to_semantic` 호출로 만들어진 것도 같다(FR-002b). **격리 대상은 이 중 템플릿 형태(1)뿐이다**(FR-001b).
- **사람이 쓴 기억**: 본문을 직접 작성해 저장한 episodic(3,241) / procedural(211) / triple 컬럼이 비어 있는 semantic. 보존 대상이며 격리 후 검색 상단을 차지해야 한다.
- **파생 검색 자산**: 기억 1건에 종속된 임베딩(`memory_embedding`), 벡터 인덱스(`memory_item_vec_*`), 전문 검색 인덱스(`memory_item_fts`). 기억이 격리되면 함께 정리되어야 하는 잔재.
- **지식 그래프 triple**: `kg_triple`의 subject/predicate/object 행. semantic 기억과 별개로 존재하며 검색 후보가 아니다. 격리 후에도 보존되고 `representative_memory_id`만 NULL이 된다.

## Assumptions

- **격리 = 백업을 롤백 근거로 삼는 완전 삭제**(`forget` `hard=true`)로 해석한다. 이슈가 연쇄 잔재 정리와 `VACUUM` 후 크기 측정을 요구하므로, 플래그로 숨기는 소프트 격리로는 요구를 만족할 수 없다. `memory_item`에 `is_deleted`/`deleted_at` 컬럼이 있지만 `forget`의 soft 경로는 이 값을 설정하지 않고 핀만 해제하므로 소프트 격리 수단으로 쓸 수 없다.
- 이 스펙은 이슈 #804의 전 범위(dry-run → 실행 → 검증)를 담는다. 현재 브랜치가 dry-run 단계에 대응하지만, 어디까지 실행할지는 plan·tasks에서 정할 구현 범위 문제로 본다.
- 건수(23,664 / 15,067 / 8,584 / 3,241 / 211 / 24,778)는 이슈 작성 시점의 라이브 DB 실측치다. 2026-08-22 재조회에서 이미 달라졌으므로(실측 기준선 섹션 참조) 정확 일치가 아니라 실행 시점 재집계 후 대조로 검증한다.
- `memory_item.confidence`는 전 행 NULL이므로 신뢰도 기반 선별 격리는 선택지가 아니다. 이 값을 채우는 일은 #805 범위다.
- Problem Statement의 세 숫자가 서로 다르다 — triple 보유 23,664건, 문법 손상 15,067 + 정상 템플릿 8,584 = 23,651, 에픽의 템플릿 문장 집계 23,649건. 차이가 형태 (2)·(3)의 규모라고 단정할 근거는 없다. 이슈 표의 두 항목은 템플릿 문장 **내부** 분류이고 집계 기준도 서로 다를 수 있다. 형태별 규모는 dry-run의 전수 집계(FR-002g)로만 확정한다.
- 형태 (2)의 규모는 사전 추정이 어렵다. `buildTripleSentence`는 predicate의 마지막 글자가 한글이 아니면 즉시 `null`을 반환하는데(`triple-sentence.ts:18-19`), 에픽 예시에 `pragma('wal_checkpoint(mode)')` 같은 영문·기호 predicate가 등장한다. 사전 추정이 어려웠으나 2026-08-22 실측에서 106건(0.44%)으로 확인됐다. 실행 시점에 다시 집계해 FR-002h의 5% 게이트로 판정한다.
- 대상 판별식(FR-001)은 triple 컬럼의 존재로 대상을 정한다. `memory_item.subject`에 값을 쓰는 경로는 `semantic-memory-crud.ts`의 `createSemanticMemory` 하나뿐임을 코드로 확인했다 — `remember`와 agent promotion 경로의 INSERT 컬럼 목록에 subject가 없다.
- 판별식은 "자동 추출"이 아니라 "이 파이프라인을 거쳤음"을 판정한다. 스펙은 대상을 부를 때 "파이프라인 산출물"을 쓰고, "자동 추출"은 그중 배치 추출로 만들어진 대다수를 가리킬 때만 쓴다. `convert_episodic_to_semantic`이 사람의 호출로 같은 파이프라인에 진입하므로 그 산출물도 대상에 포함된다. 산출물의 생성 경로와 정보량이 자동 추출물과 동일하다는 점을 근거로 이를 수용하되, FR-002b의 시기 분리 보고로 규모를 드러낸다.
- 본 작업은 데이터 조작이며 프로덕션 코드 변경을 수반하지 않는다. 반복 실행 러너는 `scripts/` 수준의 운영 도구이며 `packages/` 아래 동작을 바꾸지 않는다. 헌법 v1.2.0의 graphify 게이트는 프로덕션 코드가 실제로 바뀌는 경우에만 적용된다.
- `forget`의 `cleanupRelatedData`가 수행하는 vec 삭제는 `rowid`에 memory id(TEXT)를 넘겨 실질적으로 0행을 지운다. 실제 연쇄 정리는 FK cascade와 트리거가 담당하므로 이 결함은 본 작업의 결과에 영향을 주지 않는다. 별도 수정은 이 스펙 범위 밖이다.
- 격리 실행은 운영자가 수동으로 승인·개시한다. 자동 스케줄이나 CI 트리거는 범위 밖이다.

### 2026-08-22 (4회차) — 참조 테이블 전수 조사와 판별식 재검토

3회차까지 확인하지 않은 것이 두 가지 남아 있었다. `memory_item`을 참조하는 테이블 전체의
정리 동작과, 2회차가 grep으로 내린 subject 쓰기 경로 결론의 정확성이다. 둘 다 실제로 구멍이었다.

- **2회차 결론이 틀렸다.** `convert_episodic_to_semantic`은 직접 INSERT하지 않고
  `semantic-memory-update-pipeline`을 거쳐 같은 `createSemanticMemory`에 도달한다. grep이
  이 간접 경로를 놓쳤다. 사람이 명시적으로 호출한 도구의 산출물도 subject를 갖고 판별식에
  걸리며, DB상 자동 추출물과 구분할 컬럼이 없다. 판별식이 판정하는 것은 "자동 추출 여부"가
  아니라 "이 파이프라인을 거쳤는가"다. 시기 분리 보고로 규모를 드러내되 시기 조건을 판별식에는
  넣지 않기로 했다 — 넣으면 구간 밖 자동 추출물이 남아 문제가 절반만 해결된다.
  → FR-002·002b·002c, SC-003b, Assumptions 정정.
- **참조 테이블 전수 조사.** `memory_item`을 가리키는 참조는 세 부류였다.
  CASCADE 여덟(`memory_item_tag`·`memory_relation`·`memory_link`·`feedback_event`·
  `memory_embedding`·`meta_memory_stats`·`memory_review_candidate`·`memory_provenance`)은
  자동 정리되고, SET NULL 넷(`kg_triple`·`anchor`·`agent_session`·
  `agent_memory_promotion_candidate`)은 행이 남으며, `memory_forgetting_event`는 FK 자체가 없다.
  SC-005의 "잔재 0행"이 어느 집합을 가리키는지 불명확했던 것을 세 부류로 나눠 명시했다.
  → FR-006a 확장, FR-006d·006e, SC-005 재작성.
- **`anchor` 슬롯**이 격리 대상을 가리키면 NULL이 된다. `auto_set_anchor`가 다음 recall에서
  다시 채우므로 자가 복구된다고 보고 보고만 남긴다. → Edge Case.
- **`memory_provenance`는 FR-004a를 뒤집지 않는다.** 출처를 기록하는 테이블이 실재해 확인했으나,
  쓰는 쪽이 agent-integration promotion 경로뿐이고 그 경로는 subject를 채우지 않는다. 격리
  대상에는 provenance 행이 없다.

### 2026-08-22 (5회차) — 4회차 발견의 파급 정리

4회차가 "판별식은 자동 추출이 아니라 파이프라인 통과를 판정한다"는 것을 밝혔지만, 그 결론이
스펙의 나머지에는 반영되지 않은 채였다. 대상을 부르는 표현 열두 곳이 여전히 "자동 추출"이었고,
오탐 기준 여섯 곳이 "사람이 직접 작성"이라는 이분법을 쓰고 있었다.

- **오탐의 정의가 없었다.** `convert_episodic_to_semantic` 산출물은 사람이 지시했지만 자동 생성
  문장이라 기존 이분법의 어느 쪽도 아니다. SC-003("사람이 직접 작성한 기억 0건")과

  템플릿 문장이면 누가 시켰든 대상이고, 사람이 손으로 쓴 서술이 나오면 오탐이다.

- **용어를 통일했다.** 대상은 "파이프라인 산출 triple semantic"으로 부르고, "자동 추출"은 그중

  같은 기준으로 맞췄다.
- **서버를 정지해야 하는 세 번째 이유가 빠져 있었다.** 배치 스케줄러의 망각 정책

  이건 `SQLITE_BUSY`나 신규 유입과 다른 종류의 위험으로, SC-002·FR-011이 우리 작업과 무관한
  이유로 깨진다. 아울러 정지 유지 범위를 US3 검증 완료까지로 못박았다 — 검증 도중 서버를 올리면
  전/후 대조가 오염된다. → FR-008a 보강, FR-008b 신설, Edge Case 추가.

### 2026-08-22 (7회차) — 본문 형태 분류와 오탐 정의 재교체

Problem Statement의 숫자를 검산하다 세 값이 서로 다른 것을 발견했다. triple 보유 23,664건,
문법 손상 15,067 + 정상 템플릿 8,584 = 23,651, 에픽의 템플릿 문장 집계 23,649건. 차이가
10여 건 있다는 것은 **triple을 갖되 본문이 템플릿이 아닌 행이 존재한다**는 뜻이고, 코드를
따라가 보니 실제로 그랬다.

- **#768 폴백 행이 5회차의 오탐 정의를 무너뜨린다.** `semantic-memory-scoring.ts`의
  `tripleToNaturalLanguage`는 `buildTripleSentence` 재조립이 실패하면 **원본 episodic 본문을
  그대로** content로 저장한다. 즉 격리 대상 일부의 본문은 사람이 쓴 문장이다. 5회차가 정한
  "오탐 = 사람이 본문을 직접 쓴 서술"을 그대로 적용하면 검토자가 이 행을 보고 실행을
  중단한다 — 실제로는 파이프라인 산출물인데도. **형태로 출처를 판정하려던 시도 자체가
  틀렸다.**
- **오탐을 `subject` 기준으로 다시 정의했다.** 오탐이란 `subject`가 빈 채 대상에 걸린 행,
  즉 판별식 자체의 결함이다. `subject`가 채워졌다는 것이 `createSemanticMemory`를 거쳤다는
  유일하게 신뢰할 수 있는 신호다(FR-002 (a)). → FR-002a 재작성.
- **표본 검토의 역할이 바뀌었다.** 오탐 판정이 아니라 본문 세 형태의 분포 확인이다.
  (1) 템플릿 문장, (2) 원본 episodic 폴백, (3) `s · p · o` 조인. 형태 (2)의 비중이 예상보다
  크면 격리로 잃는 정보량이 Problem Statement의 전제("정보량 0")와 다르다는 뜻이므로 실행 전
  재논의한다. → FR-002f·002g, FR-002c 재작성, SC-003·003b, US1 시나리오 2·4.
- 5·6회차가 대상을 "템플릿 문장"으로 부르던 표현들(SC-001, US3, FR-003a, Key Entities)도
  형태 (2)·(3)을 배제하므로 `subject` 기준으로 바꿨다.

### 2026-08-22 (8회차) — 폴백 규모의 미지성과 게이트 도입

7회차가 형태 (2)를 발견하고도 그 규모를 "10여 건 수준"으로 단정해 Assumptions에 넣었다.
그 단정의 근거를 따져보니 성립하지 않았고, 실제 규모는 아무도 모른다는 것이 8회차의 결론이다.

- **"차이 10여 건 = 형태 2·3"은 근거 없는 추론이었다.** 이슈 표의 15,067 / 8,584는 템플릿
  문장 **내부** 분류이고 에픽의 23,649는 또 다른 집계 기준일 수 있다. 세 숫자의 차이를
  형태 (2)·(3)의 규모로 읽을 근거가 없다. Assumptions에서 단정을 걷어냈다.
- **오히려 형태 (2)가 많을 수 있다.** `buildTripleSentence`는 predicate의 마지막 글자가
  한글이 아니면 즉시 `null`을 반환한다(`triple-sentence.ts:18-19`). 에픽 예시에
  `pragma('wal_checkpoint(mode)')` 같은 영문·기호 predicate가 등장하므로, 실패율이 낮다고
  볼 이유가 없다. subject가 비면 애초에 FR-001에 안 걸리므로 실패는 predicate·object 쪽에서만
  난다.
- **이게 왜 중요한가.** 형태 (2)의 본문은 사람이 쓴 원문이다. 비중이 크면 Problem Statement의
  "정보량 0"이라는 핵심 논거가 그 부분집합에 대해 성립하지 않는다. 격리의 정당성이 걸린
  문제인데 임계값이 없었다 — FR-002g는 "예상보다 크면 재논의"라고만 했고 예상치는 위의
  근거 없는 13건이었다.
- **5% 게이트를 넣었다.** 형태 분포를 표본이 아니라 **전체 대상 전수 집계**로 구하고, 형태

### 2026-08-22 (13회차) — 판별식의 LIKE 와일드카드 노출

11회차가 판별식에 넣은 `content LIKE subject || '_ %'`는 **`subject` 값을 패턴에 그대로
삽입한다**. 그 안의 `_`·`%`는 리터럴이 아니라 와일드카드로 해석된다.

- **`subject`에 `_`를 포함한 행이 941건이다** (`%`는 0건). `subject`가 `a_c`인 행이 `abc…`로
  시작하는 content를 매칭할 수 있다는 뜻이다.
- **현재 데이터에서는 오분류가 없다 — 그러나 우연이다.** naive LIKE, `%` 이스케이프, 문자열
  위치 비교 세 방식이 모두 24,086건으로 일치했다. content가 `subject`로 시작하는 경우 실제
  `_` 자리도 함께 매칭되기 때문이며, 다른 데이터에서는 성립하지 않는다.
- **위치 비교를 강제했다.** `substr(content,1,length(subject)) = subject AND
  substr(content,length(subject)+2,1) = ' '`. 형태 (3) 판별도 같은 이유로 등호 비교를 쓴다.
  → FR-002i 신설, FR-001·FR-002g에서 참조.
- **12회차가 놓친 파급도 정리했다.** 11회차가 판별식에 형태 조건을 추가했는데 FR-002a의 오탐
  정의는 여전히 `subject` 하나만 보고 있었다. 이제 오탐은 두 종류다 — `subject`가 빈 채 걸린
  행, 그리고 형태 (1)이 아닌데 형태 (1)로 분류된 행. 후자가 FR-002i가 막으려는 바로 그
  경로다. → FR-002a 재작성, SC-003 보강, Edge Case 추가.

12회차가 "남은 미지수는 소요 시간뿐"이라고 했는데, 정확히는 **판별식의 구현 정확성**이 하나 더
남아 있었다. 그것도 실측으로 닫혔다.

### 2026-08-22 (14회차) — 조사 규칙 검증과 오탐 판정의 전수화

13회차가 도입한 위치 비교의 전제를 코드로 확인하고, 그 과정에서 표본 검증의 보장 강도를
따져 오탐 판정을 옮겼다.

- **FR-002i의 `+2`가 검증됐다.** `attachParticle`은 종성 유무·한글 여부와 무관하게 조사를
  **정확히 1글자** 붙인다(받침 있으면 은/을, 없거나 한글이 아니면 는/를). 따라서
  `length(subject)+2` 위치가 공백이라는 가정이 성립한다.
- **`trim` 불일치 위험은 실측상 없다.** `buildTripleSentence`는 `subject.trim()`을 쓰므로 DB
  값에 앞뒤 공백이 있으면 접두사 비교가 어긋난다. 실측에서 `subject`·`predicate`·`object`
  모두 공백·개행이 0건이었고 raw·trim 기준 결과가 같았다(각 24,086건). 방어적으로 양쪽에
  `trim`을 적용하도록 명시했다.
- **표본 50건은 오탐 판정의 근거가 되기에 약했다.** 모수 24,086에서 50건을 뽑아 0건이면
  통계적으로는 오탐률 6% 미만만 보장한다 — 최대 1,445건이 숨어 있어도 표본에 안 걸린다.
  그런데 13회차가 보여줬듯 두 종류 오탐 모두 **SQL로 전수 확인이 가능하다**. (i)은 대상 중
  `subject`가 빈 행을 세면 되고, (ii)는 형태 (1) 건수를 위치 비교와 이스케이프 `LIKE` 두
  방식으로 세어 일치를 보면 된다. 통계적 추정 대신 결정적 검증을 쓸 수 있는데 표본에 맡길
  이유가 없다.
- **오탐 판정을 전수 검증으로 옮겼다.** 표본 A는 "이 문장들을 정말 지워도 되는가"를 사람이
  눈으로 보는 용도로만 남는다. → FR-002j 신설, FR-002d·FR-002 (b) 역할 재서술, SC-003
  재작성, SC-003e 신설, US1 story·시나리오 2 정렬.

12회차가 표본 B를 폐지하고 14회차가 표본 A의 판정 역할을 걷어냈다. 실측이 가능해질수록
표본의 자리가 줄어드는 것은 자연스러운 귀결이다 — 표본은 전수를 못 볼 때 쓰는 도구다.

### 2026-08-22 (15회차) — 표본 A 실제 검토와 "정보량 0" 전제의 반증

14회차까지 표본 A를 "뽑는다"고 규정만 했지 실제로 뽑아 본 적이 없었다. 15회차에 뽑아

- **그러나 "정보량 0" 전제가 반증됐다.** 표본 절반 가까이가 구체적 사실을 담고 있었다 —
  파일 경로(`docs/superpowers/plans/2026-05-04-…md`), 이슈 번호(`#348`, `pr #374`),
  수치(`경고 307개, 에러 0`), 설계 결정(`액세스 토큰은 rest 상태에서 단방향 해시를 저장 방식`).
  object 길이 ≥8인 대상 200건을 프로브하니 **37%는 object 문자열이 사람이 쓴 기억 어디에도
  없었다**. 형태 (1) 대상 중 object ≥8이 16,251건이므로 약 6,000건 규모다.
- **전제를 정확히 다시 썼다.** 격리를 정당화하는 것은 "정보량 0"이 아니라 두 가지다 —
  (1) 문법이 깨져 질의에 걸리지 않으므로 **검색 가치**가 0이고, (2) 구조화된
  `subject/predicate/object` 조합이 `kg_triple`에 **100% 보존**된다. 사라지는 것은 검색되지
  않는 자연어 서술뿐이다. 손실을 숨기지 않고 규모를 명시했다. → Problem Statement 논거 1
  재작성, Goals 보강, FR-004 (b)를 "핵심 정당화 근거"로 격상, SC-004a 신설(보존율 100% 미만이면
  삭제 0건).

문서를 열네 번 읽는 동안 아무도 대상 문장을 실제로 보지 않았다. 한 번 보니 스펙이 세 달 넘게
근거로 삼아 온 문장이 부정확했다.

### 2026-08-22 (17회차) — 측정 행위가 측정 대상을 바꾼다

FR-003a는 dry-run 단계에서 `memory_injection`으로 사전 기록을 만들라고 요구해 왔다. 그 호출이
읽기 전용인지 아무도 확인하지 않았다. 아니었다.

- **`memory_injection`은 `memory_item`을 UPDATE한다.**
  `knowledge-context-bundle-builder.ts:244`가 반환된 각 기억의 `recall_count`·
  `last_accessed_at`·`g_value`·`consolidation_score`를 갱신한다.
- **두 조항이 동시에 깨져 있었다.** (a) FR-011은 "격리 대상이 아닌 기억은 건수와 **내용이**
  변하지 않아야 한다"고 하는데, 사전 기록 생성이 사람이 쓴 episodic의 메타데이터를 바꾼다.
  (b) 더 나쁜 것은 SC-001a다 — `g_value`·`consolidation_score`는 **랭킹에 쓰인다**. 사전
  프로브가 올린 점수 때문에 격리 후 같은 질의에서 그 기억들이 더 상위에 온다. 비율 상승이
  격리 덕인지 프로브 덕인지 **원리적으로 구분할 수 없다**.
- **프로브를 사본으로 옮겼다.** 사본 A(격리 전)와 사본 B(사본 A에 격리 적용)에 질의 10개를
  각각 한 번씩 돌린다. 라이브는 읽지도 않으므로 FR-011이 유지되고, 두 사본이 프로브를 대칭적으로
  1회씩 받으므로 대조가 공정하다. FR-006c가 이미 사본을 요구하므로 절차 부담도 작다.
  → FR-003a 재작성, FR-003b·003c 신설, FR-011·SC-001a·SC-004 보강, US1 시나리오 1·US3 전반,
  Key Entities, Edge Case.
- **진단 프로브의 앵커 오염도 막았다**(#811 4번). `recall` 진단 호출에는
  `auto_set_anchor: false`를 준다. → FR-003c.

15회차는 "아무도 대상 문장을 보지 않았다"였고, 16회차는 "대체 논거가 반대 방향으로 틀렸다"였다.
17회차는 성격이 또 다르다 — **검증 절차 자체가 검증 결과를 만들어내고 있었다.** 실행했다면
SC-001a가 통과했을 것이고, 그 통과가 무엇을 뜻하는지는 아무도 몰랐을 것이다.

### 2026-08-22 (18회차) — 리허설이 곧 실측

17회차가 검증 프로브를 사본으로 옮기면서, 사본 B를 "사본 A에 격리를 적용한 것"으로 정의했다.
그 정의가 이미 **전량 격리 리허설**이라는 것을 그때는 알아채지 못했다.

- **FR-006c의 100건 배치 추정이 불필요해졌다.** 사본 B를 만들려면 어차피 전량 격리를 한 번
  돌려야 한다. 추정 대신 실측이고, 덤으로 연쇄 정리 결과·`VACUUM` 회수량·재개 동작까지 라이브
  이전에 검증된다. → FR-006c 재작성, FR-006g 신설(리허설 실패 시 라이브 미실행), SC-007a
  재작성, SC-008b 신설.
- **절차를 여섯 단계로 명시했다.** 백업 → 사본 B 복제 → A에 before 프로브 → **B에 전량 격리
  리허설** → B에 after 프로브 → 전부 통과 시 라이브. 이전에는 사본 A·B가 "있다"고만 했지
  어떤 순서로 무엇을 하는지가 흩어져 있었다. → FR-003a 재작성.
- **사본 프로브의 실행 조건을 확인했다.** `memory_injection`은 MCP 도구라 `DB_PATH`를 사본으로
  지정한 별도 서버 인스턴스가 필요하다. 프로덕션은 FR-008a로 정지 중이라 충돌하지 않는다.
  임베딩은 실측상 **minilm(로컬 ONNX) 28,427건**이 사실상 전량이라 외부 API가 필요 없고,
  `db:backup`의 online backup API가 페이지 전체를 복사하므로 `memory_item_vec_*` 가상 테이블도
  사본에 따라온다. → FR-003d 신설.

17회차가 만든 구조가 18회차에서 예상 밖의 이득을 냈다. 오염을 피하려고 도입한 사본이,
그 자체로 프로덕션 실행 전 전면 리허설을 제공한다.

### 2026-08-22 (19회차) — 서버 정지 구간의 재정의

18회차가 리허설을 사본으로 확정하면서, 서버를 언제부터 언제까지 세우는지가 정의되지 않은 채
남았다. 그리고 17회차가 검증을 사본으로 옮긴 순간 **FR-008b의 근거가 이미 사라져 있었다**.

- **FR-008b의 이유가 소멸했다.** 원래 "US3 검증이 끝날 때까지 정지 유지"의 근거는 "검증 도중
  서버를 올리면 망각 정책과 신규 쓰기가 전/후 대조를 오염시킨다"였다. 그런데 17회차가 대조를
  사본 A·B로 옮겼다. 라이브 서버를 올려도 사본 대조는 영향받지 않는다. 근거가 없는 제약이
  두 회차 동안 남아 서비스 중단을 불필요하게 늘리고 있었다.
- **정지 구간을 라이브 실행분으로 좁혔다.** 백업·사본 복제·프로브·전량 리허설은 사본에서
  이뤄지므로 서버를 올려둔 채 진행하고, **실행 직전 재집계(FR-004b)부터 `VACUUM`
  완료(FR-010)까지**만 정지한다. 재기동은 사후 확인이 끝나면 즉시 — US3 대조를 기다리지
  않는다. → FR-008a 범위 한정, FR-008b 재작성, FR-008c 신설, SC-008c, US2 story·시나리오.
- **부작용도 함께 줄었다.** 재집계가 정지 직후에 일어나므로 사본 A 시점과 라이브 실행 시점의
  변동폭이 작아진다. 반대로 리허설이 길수록 그 사이 라이브가 자라 ±5% 게이트에 걸릴 확률이
  커진다는 긴장은 남는다(실측: 40분에 형태 (2) 10건 증가) — Edge Case로 명시하고, 걸리면
  사본 A부터 다시 뜨도록 했다.

17회차와 18회차가 각각 옳은 결정을 내렸지만, 그 결정이 **이전 회차의 제약을 무효화한다는 것**은
아무도 확인하지 않았다. 새 구조를 넣을 때마다 그 구조가 무엇을 불필요하게 만드는지도 함께
봐야 한다.

### 2026-08-22 (20회차) — 사본 구조가 흡수한 조항들

19회차가 "새 구조를 넣을 때 그것이 무엇을 불필요하게 만드는지도 보라"는 교훈을 남겼다.
20회차는 그 점검을 사본 구조 전체에 전수 적용했다. 두 건이 걸렸다.

- **FR-007b의 복원 리허설이 사본 A 검증과 중복이었다.** 원래 "백업 → 임시 경로 복원 →
  타입별 건수 대조"였는데, 절차상 **사본 A가 곧 백업 파일**이고 거기에 서버를 물려 질의
  10회를 돌린다(FR-003a 3단계). 서버가 열고 검색까지 해낸다는 것은 건수 대조보다 **강한
  무결성 증명**이다 — 스키마·인덱스·`memory_item_vec_*`·FTS가 모두 살아 있어야 통과한다.
  구동 검증으로 통합하고 건수 대조는 그 안에 넣었다. → FR-007b 재작성, SC-006 재작성.
- **롤백 절차가 구체화됐다.** 사본 A가 존재하므로 롤백은 "사본 A를 라이브 경로로 교체"다

  모호했다. → FR-007a, US2 시나리오 7.
- **SC-006a의 검증 장소가 정해졌다.** 중단 후 재개는 **사본 B 리허설 중 의도적으로** 한 번
  중단해 확인한다. 라이브에서 중단 테스트를 할 이유가 없고, 정지 구간을 늘리지도 않는다.
  → SC-006a, FR-006c 보강, US2 Independent Test.
- **Key Entities에 사본 A·B를 명시했다.** 사본 A는 세 역할을 겸한다 — 롤백 근거, 무결성 검증
  대상, before 프로브 대상. 이전에는 "백업 스냅샷"이 롤백 근거로만 서술돼 있었다.

19회차가 제약 하나를 걷어냈다면, 20회차는 검증 하나를 통합하고 둘의 위치를 확정했다.
사본 구조는 오염 회피를 위해 도입됐지만 결과적으로 리허설(18회차)·무결성 검증(20회차)·
재개 검증(20회차)까지 흡수했다.

### 2026-08-22 (21회차) — 롤백 근거가 껍데기였을 뻔했다

> **정정(22회차)**: 아래의 "`db:backup` 산출물 대부분이 껍데기"라는 귀속은 틀렸다. 문제의
> 파일들은 `backup-manager.ts`가 만드는 마이그레이션 백업이었다. FR-007c는 다른 근거로
> 유지된다 — 22회차 항목 참조.

사본 구조가 확정됐으니 실행에 필요한 디스크를 확인하려다, 그보다 심각한 것을 발견했다.

- **`backups/`에 6,883개·5.0GB가 쌓여 있는데 대부분이 262,144바이트다.** 크기 분포를 보면
  546MB짜리 정상 백업은 **1개뿐**이고 나머지는 64페이지짜리 껍데기이거나 중간 크기다. 날짜가
  초 단위로 4개씩 묶여 반복 호출된 흔적을 남긴다. `backup-memory-db.mjs` 자체는
  `await source.backup()`을 제대로 하고 크기 0 검사도 하므로 도구가 망가진 것은 아니다 —
  무언가가 반복 호출하고 있고 그 산출물이 온전치 않다.
- **FR-007은 이 도구의 산출물을 롤백의 유일한 근거로 삼고 있었다.** 실행했다면 256KB짜리
  파일을 믿고 24,086건을 지웠을 수 있다. 롤백이 필요해진 순간에야 근거가 없다는 걸 알았을
  것이다.
- **크기 대조를 1차 게이트로 넣었다.** 백업 직후 사본 A 크기를 라이브와 대조해 현저히 작으면
  즉시 중단한다. 값싼 검사가 껍데기를 먼저 걸러내고, 그 뒤 FR-007b의 구동 검증이 내용을
  확인한다. → FR-007c 신설, FR-007b·SC-006 보강, Edge Case 추가.
- **20회차 결정이 실측으로 정당화됐다.** 그때 "구동 검증이 건수 대조보다 강하다"는 이유로
  FR-007b를 통합했는데, 정작 필요했던 위험이 실재했다. 다만 256KB 백업은 스키마가 온전해
  **서버 구동에는 성공할 수도** 있으므로, 구동 검증만으로는 부족하고 크기 게이트가 앞에 와야
  한다.
- **누적 정리는 범위 밖으로 명시했다.** 6,883개·5.0GB 정리와 반복 호출 원인 규명은 별도
  이슈다. 이번 작업은 자기가 만든 백업만 검증한다. 디스크 여유는 493GB로 사본 A·B와 `VACUUM`
  임시 공간에 충분하다. → Non-Goals 추가.

### 2026-08-22 (22회차) — 21회차 귀속 오류 정정

21회차가 "`db:backup` 산출물 대부분이 262,144바이트 껍데기"라고 결론지었다. 파일명을 다시
보니 그 귀속이 틀렸다.

- **문제의 파일들은 `db:backup`이 만든 게 아니다.** 파일명이 `memory-backup-9.0-...`인데
  `9.0-`은 타임스탬프가 아니라 **마이그레이션 버전**이다
  (`backup-manager.ts:80`, `memory-backup-${migrationVersion}-${timestampStr}.db`). 현재
  `db:backup`은 버전 접두 없이 `memory-backup-<ISO타임스탬프>.db`를 쓴다
  (`backup-memory-db.mjs:33`).
- **실제 분포는 이렇다.** 총 6,899개 중 **6,880개가 마이그레이션 백업**(버전당 약 207개),
  `db:backup` 산출물은 **19개**뿐이다. 그 19개는 84MB·114MB·115MB 등 당시 DB 크기에 맞고,
  546MB짜리는 오늘 적용된 마이그레이션 42.0의 백업이다. 256KB 파일들은 초기 마이그레이션
  시점의 것이라 그때 DB가 작았다면 정상 크기다.
- **따라서 "`db:backup`이 껍데기를 만든다"는 21회차 추론을 철회한다.**
- **다만 FR-007c는 다른 근거로 살아남는다.** `db:backup` 산출물 19개 중 **0바이트 파일이
  실재하고**(`memory-backup-2026-06-15T12-41-09-792Z.db`), `-wal`·`-shm` sidecar 잔재도 남아
  있다. 스크립트에 크기 0 삭제와 sidecar 정리 로직이 **둘 다 있는데도** 그렇다. 그 정리가 항상
  동작한다고 가정할 수 없으므로 크기 대조와 sidecar 확인은 유지하되, 근거를 실제 증거로
  바꿨다. → FR-007c 재작성, Edge Case·Non-Goals·실측 표 정정.

21회차는 옳은 조항(FR-007c)을 틀린 근거로 세웠다. 조항은 남지만 근거가 틀린 채로 두면
나중에 누군가 "그 전제가 사실이 아니다"를 발견하고 조항까지 걷어낼 수 있다. 실측으로 세운
스펙에서는 근거의 정확성이 조항의 생존 조건이다.

### 2026-08-22 (25회차) — 판별식 실행 계획과 파이프라인 악화 추세

실행 성능에 직결되는데 확인 안 된 둘을 쟀다. 하나는 문제가 없었고, 그 과정에서 훨씬 중요한
것이 딸려 나왔다.

- **판별식은 인덱스 최적화 여지가 없다 — 그리고 그래도 된다.** `idx_memory_item_triple`은
  `(subject, predicate, object)` 컬럼 인덱스라 특정 subject를 찾을 때만 쓸모가 있다. 우리
  판별식에는 인덱스로 좁힐 등가·범위 조건이 없어 `idx_memory_item_type`으로 semantic만 좁힌
  뒤 행마다 `substr`를 평가한다. `predicate IS NOT NULL AND object IS NOT NULL`을 추가해도
  계획이 바뀌지 않고 대상 집합도 그대로다(subject 보유 24,202건 **전부**가 predicate·object를
  갖는다). 26,137행을 훑어 24,086건을 반환하는 쿼리라 인덱스가 오히려 무의미하다.
- **WAL도 위험이 아니다.** 현재 2.6MB, `wal_autocheckpoint=1000`(약 4MB). 서버 정지 상태에서는
  체크포인트를 막을 리더가 없다.
- **그런데 부수 숫자가 이상했다.** subject 보유 행이 24,202건인데 9~23회차 내내 24,192였다.
  형태 (1)은 24,086으로 그대로이므로 늘어난 것은 형태 (2)뿐이다.
- **파이프라인이 8월 들어 망가지고 있다.** 형태 (2)의 월별 생성은 2026-05 **0.0%**,
  06 **0.0%**, 07 **0.1%**, **08 11.6%**(115/991)다. 형태 (2) 총 116건 중 **115건이 이번 달**
  것이다. `buildTripleSentence`가 최근 계속 `null`을 반환한다는 뜻이다.
- **이것이 11회차 결정의 근거를 흔든다.** FR-001b가 형태 (2)를 제외한 근거는 "106건, 0.44%라
  무시 가능"이었다. 이 속도면 곧 수천 건이 되어 그 근거가 성립하지 않는다. 제외 조항에 재검토
  조건을 달고, dry-run이 월별 추이를 보고하도록 했다. → FR-001b 보강, FR-001c 신설.
- **원인 규명은 별도 이슈로 넘겼다.** 격리는 기존 24,086건을 치우는 작업이고 유입 차단은
  #805의 몫이다. 다만 "재조립 실패율 8월 급증"은 #805·#811과 인접한 별개 결함이므로 이슈로
  제기한다. → Non-Goals 추가.

성능을 확인하러 갔다가 파이프라인 악화를 발견했다. 문제 없음을 확인하는 작업도 옆에 있는
문제를 드러낸다.

### 2026-08-22 (27회차) — 판별식이 보지 않는 컬럼들

FR-001은 `type`·`subject`·`pinned`·본문 형태만 본다. `memory_item`에는 `is_deleted`·
`deleted_at`·`project_id`·`owner_id`·`privacy_scope`도 있는데, 대상에 어떤 값이 들어 있는지
확인한 적이 없었다.

- **대상은 점유하되 거의 반환되지 않는다.** 반환된 적이 있는 대상은 **739건(3.1%)**뿐이고
  평균 `recall_count`는 0.05다. `importance ≥ 0.8`이면서 한 번도 반환되지 않은 대상이
  **8,285건**이다. 16회차가 쓴 "밀어낸다"는 적극적 축출을 연상시키지만 실상은 **높은
  우선순위를 차지한 채 잠들어 있는 것**에 가깝다 — 논거를 그렇게 다듬었다.
- **`recall_count`는 타입 간 직접 비교가 불가능하다.** `remember` 경로는 생성 시 **1**로
  시작하고(`remember-tool-memory-item.ts:64`) `createSemanticMemory`는 컬럼을 INSERT에 넣지
  않아 **0**에서 시작한다. 그래서 episodic 3,431건이 전부 `recall_count > 0`으로 보이지만
  이는 초기값이지 반환 기록이 아니다. 이 함정을 FR-001f로 명시했다.
- **격리는 재추출까지 막는다.** episodic 3,431건 중 **2,982건이 `triple_extracted=1 / success`**
  이고 격리는 이 플래그를 건드리지 않는다. 즉 나중에 같은 episodic에서 재추출을 시도해도
  스킵된다. 되돌릴 수 없을 뿐 아니라 재생성도 막히는 것이다. 다만 23회차가 찾은
  `memory_relation.extracted_from` 25,069건이 출처를 가리키므로, FR-006i의 내보내기가 그대로
  **복구 경로**가 된다 — 필요해지면 그 목록으로 플래그를 리셋하면 된다(FR-006k·006l).
- **대상에 출처 메타데이터는 정말 없다.** `source`·`origin_source`·`tags`·`session_id`·
  `source_session_id` 모두 0건으로, 4회차의 결론이 데이터로 재확인됐다. 출처를 아는 유일한
  경로는 `memory_relation`뿐이다.
- **`memory_review_candidate`도 대량 삭제된다.** 5,300행 중 **3,609행(68%)**이 대상에 걸린다.
  10회차 CASCADE 실측에서 `memory_relation`과 함께 빠져 있던 항목이다.
- **대상은 귀속이 없는 기억뿐이다.** 24,086건 **전부** `project_id` NULL, `owner_id` NULL,

  나중에 프로젝트별 파이프라인 산출물이 생겼을 때 그것만 영구히 남아 문제가 절반만 해결된다 —
  시기 조건을 넣지 않기로 한 것(FR-002c)과 같은 논리다. 대신 dry-run이 귀속 분포를 보고해
  변화를 감시한다. → FR-001d·001e 신설, SC-003f, FR-011 보강, Edge Case 추가.

이번 회차는 "확인해서 문제 없음"에 가깝지만, 그 결과가 **판별식이 왜 안전한지에 대한 근거**가
됐다. 조건이 없어서 안전한 것이 아니라, 데이터가 그렇게 생겨서 안전하다는 것을 알고 쓰는 것과
모르고 쓰는 것은 다르다.

### 2026-08-22 (28회차) — 재추출 차단과 남은 컬럼들

FR-001이 보지 않는 컬럼을 27회차에 이어 마저 확인했다. 하나가 컸다.

- **대상은 점유하되 거의 반환되지 않는다.** 반환된 적이 있는 대상은 **739건(3.1%)**뿐이고
  평균 `recall_count`는 0.05다. `importance ≥ 0.8`이면서 한 번도 반환되지 않은 대상이
  **8,285건**이다. 16회차가 쓴 "밀어낸다"는 적극적 축출을 연상시키지만 실상은 **높은
  우선순위를 차지한 채 잠들어 있는 것**에 가깝다 — 논거를 그렇게 다듬었다.
- **`recall_count`는 타입 간 직접 비교가 불가능하다.** `remember` 경로는 생성 시 **1**로
  시작하고(`remember-tool-memory-item.ts:64`) `createSemanticMemory`는 컬럼을 INSERT에 넣지
  않아 **0**에서 시작한다. 그래서 episodic 3,431건이 전부 `recall_count > 0`으로 보이지만
  이는 초기값이지 반환 기록이 아니다. 이 함정을 FR-001f로 명시했다.
- **격리는 재추출까지 막는다.** episodic 3,431건 중 **2,982건이 `triple_extracted=1 / success`**
  이고, 격리는 이 플래그를 건드리지 않는다. 나중에 같은 episodic에서 재추출을 시도해도
  스킵된다 — 되돌릴 수 없을 뿐 아니라 **재생성도 막힌다**.
- **그런데 복구 경로가 이미 있다.** 23회차가 찾은 `memory_relation.extracted_from` 25,069건이
  출처 episodic을 가리키므로, FR-006i의 관계 내보내기가 그대로 복구 목록이 된다. 필요해지면
  그 ID들의 플래그를 리셋해 재추출할 수 있다.
- **리셋은 하지 않기로 했다.** 재추출은 원하지 않는 동작이다 — #805가 유입을 막기 전에
  리셋하면 같은 파편이 다시 쌓이고, 2026-08 폴백률 11.6%를 감안하면 더 나쁜 것이 생성된다.
  경로만 문서로 남긴다. → FR-006k·006l 신설, Edge Case 추가.
- **대상에 출처 메타데이터는 정말 없다.** `source`·`origin_source`·`tags`·`session_id`·
  `source_session_id` 모두 **0건**이다. 4회차 결론이 데이터로 재확인됐고, 출처를 아는 유일한
  경로가 `memory_relation`뿐임이 확정됐다.
- **`memory_review_candidate`도 대량 삭제된다.** 5,300행 중 **3,609행(68%)**. 10회차 CASCADE
  실측에서 `memory_relation`과 함께 빠져 있던 항목이다. → FR-006e에 실측 규모 명시.

### 2026-08-22 (29회차) — 실제 반환 기록과 지표의 함정

16회차가 "랭킹 상단을 점유해 사람이 쓴 기억을 밀어낸다"고 논거를 세웠는데, **실제로 반환돼
왔는지**는 확인한 적이 없었다.

- **대상의 96.9%는 한 번도 반환된 적이 없다.** 반환 기록이 있는 것은 739건(3.1%), 평균
  `recall_count` 0.05다. `importance ≥ 0.8`이면서 한 번도 반환되지 않은 대상이 **8,285건**이다.
- **그러나 지표를 그대로 믿을 뻔했다.** episodic 3,431건이 **전부** `recall_count > 0`으로
  나왔는데, 통계적으로 부자연스러워 코드를 확인했다. `remember-tool-memory-item.ts:64`가
  생성 시 `recall_count = 1`을 넣는다 — `createSemanticMemory`는 이 컬럼을 INSERT에 넣지 않아
  **0**에서 시작한다. **출발값이 달라 직접 비교가 불가능한 지표였다.** 16회차가 검증 없이
  논거를 바꿨다가 반전된 전례가 있어 이번에는 먼저 확인했다. → FR-001f 신설.
- **논거는 무너지지 않고 더 정확해졌다.** "밀어낸다"는 적극적 축출을 연상시키지만, 실상은
  **높은 우선순위를 차지한 채 3.1%만 반환되는 것**이다. importance 86% 점유는 그대로 사실이고,
  거기에 "그런데 실제로는 거의 안 나온다"가 더해지면 코퍼스가 왜 무거운지가 더 분명해진다.
  → Problem Statement 논거 1 재작성.

지표를 보기 전에 그 지표가 무엇을 세는지 확인해야 한다. `recall_count`라는 이름만 보고
비교했다면 "대상은 안 쓰이고 episodic은 다 쓰인다"는 과장된 결론을 냈을 것이다.

### 2026-08-22 (30회차) — 구조 점검과 실행 절차 색인

스펙이 1,100줄·FR 58블록이 됐다. 템플릿 정합성과 사용성을 점검했다.

- **템플릿 필수 섹션은 전부 충족한다.** User Scenarios & Testing · Edge Cases · Requirements ·
  Functional Requirements · Key Entities · Success Criteria · Measurable Outcomes가 모두 있고,
  User Story 3개 각각에 Independent Test가 붙어 있다.
- **헌법 연계 하나가 빠져 있었다.** FR-006b의 `.local/` 규칙은 헌법 v1.2.0 Additional
  Constraints의 "재배포 불가 코퍼스 커밋 금지·공개 문서엔 집계만"과 같은 계열인데 그 연결이
  적혀 있지 않았다. 명시했다.
- **plan 작성자가 필요한 것이 58개 조항에 흩어져 있었다.** 판별식·절차 순서·중단 게이트·정지
  구간은 실행의 뼈대인데, 근거 서술과 예외 조항 사이에 섞여 있어 한눈에 잡히지 않는다.
  Problem Statement 뒤에 **「실행 절차 요약」**을 넣었다 — 판별식 SQL, 6단계 절차 표, 중단
  게이트 8개 목록, 정지 구간, 격리 전 필수 내보내기. 각 항목은 FR 번호를 가리키므로 중복
  서술이 아니라 색인이다.

29회차까지가 "무엇이 맞는가"를 다뤘다면, 30회차는 "그것을 어떻게 읽게 할 것인가"를 다뤘다.
1,100줄짜리 스펙은 정확해도 쓰이지 않으면 소용이 없다.

### 2026-08-22 (31회차) — 성공 기준의 검증 장소 감사

17~20회차가 검증을 사본 A·B와 라이브로 나눴는데, 각 성공 기준이 **어디서** 판정되는지는
조항마다 제각각이었다. 26개를 전수 감사했다.

- **검증 장소가 적혀 있지 않은 것이 7건이었다** — SC-003·003e·004a·005c·007·007b·008.
  읽는 사람이 "이걸 사본에서 보나 라이브에서 보나"를 매번 추론해야 했다. 각각에 판정 시점을
  괄호로 달았다(dry-run / 사본 / 라이브 / 상시).
- **순서가 어긋나 있었다.** SC-003e가 SC-003a 앞에, SC-004a가 SC-005a 뒤에, SC-005c가
  SC-005b 앞에 있었다. FR은 회차마다 정렬했지만 SC는 하지 않았다. 26개를 정렬했다.
- **중복처럼 보인 것은 오탐이었다.** `- **SC-…**` 패턴이 30번 잡혔는데 4개는 Brainstorm Log
  안의 과거 인용이다. 본문 성공 기준은 26개다.

이번 회차는 새 사실을 발견하지 않았다. 다만 26개 기준 중 7개가 "언제 판정하는가"에 답하지
않고 있었고, 그것은 실행자가 스펙을 들고 작업할 때 매번 걸리는 종류의 공백이다.

### 2026-08-22 (32회차) — 요약 대조와 브레인스토밍 종료

30회차에 넣은 「실행 절차 요약」이 본문과 어긋나면 최악이므로 대조했다.

- **요약은 본문과 일치한다.** 판별식 SQL이 FR-001과 동일하고, 중단 게이트 8개가 모두 실재하는
  조항을 가리키며, 절차 6단계가 FR-003a와 같다. 핵심 수치(24,086 · 54,742 · 25,069)도 문서
  전체에서 일관되게 쓰인다.
- **FR-001의 모수만 낡아 있었다.** "24,192건 중 24,086건"이라 적혀 있었는데 25회차 실측에서
  `subject` 보유가 24,202건으로 늘었다. 모수가 세션 중에도 변한다는 사실 자체가 실행 시점
  재집계(FR-004b)의 근거이므로, 그 점을 함께 적었다.
