## User Scenarios & Testing *(mandatory)*

### User Story 1 - Maintainer locates recall behavior quickly (Priority: P1)

A maintainer needs to change or audit how "memory recall" works for agents (filters, ranking options, anchors). Today this requires navigating an overly large, intertwined implementation. After this work, they can find the right place to edit or review within a short, predictable path.

**Why this priority**: Memory recall is on the critical path for product value; confusion here causes the highest cost and risk.

**Independent Test**: A maintainer unfamiliar with the area can, using only written guidance produced as part of this effort, identify where recall-specific rules live and complete a mock "add one new filter option" walkthrough without opening unrelated subsystems.

**Acceptance Scenarios**:

1. **Given** documented capability boundaries for memory recall, **When** a maintainer follows them, **Then** they can name the owning area for recall-specific behavior without searching the entire codebase at random.
2. **Given** a planned refactor increment for recall, **When** it is delivered, **Then** existing recall scenarios for agents continue to behave as before (verified by an agreed regression checklist).

---

### User Story 2 - Security reviewer can assess admin surface efficiently (Priority: P2)

A security or operations reviewer must understand what administrative actions exist over HTTP and how they are gated. A monolithic registration of many routes in one place makes review slow and error-prone.

**Why this priority**: Administrative capabilities carry elevated risk; reviewability directly affects trust and incident response time.

**Independent Test**: A reviewer can complete a time-boxed review session covering all administrative endpoints using a structured outline that maps capabilities to review notes, without relying on tribal knowledge.

**Acceptance Scenarios**:

1. **Given** the proposed structure for administrative capabilities, **When** a reviewer walks the outline, **Then** they can record authorization expectations per capability area in one pass.
2. **Given** a refactor increment that splits administrative registration, **When** it ships, **Then** no administrative capability disappears or moves to an unauthenticated path relative to prior behavior.

---

### User Story 3 - Contributor extends search without duplicating logic (Priority: P3)

A contributor adds or adjusts ranking or provider behavior for search. They should not copy-paste logic across layers or create parallel implementations because boundaries are unclear.

**Why this priority**: Search quality and performance compound over time; duplication creates drift and defects.

**Independent Test**: A contributor can describe where ranking composition lives versus provider execution versus result merging, using project documentation, and complete a small hypothetical extension without conflicting guidance.

**Acceptance Scenarios**:

1. **Given** documented boundaries for hybrid search, **When** a contributor proposes an additive change, **Then** the change touches at most the documented owning areas for that concern.
2. **Given** refactor increments for search, **When** each increment completes, **Then** agreed search scenarios (retrieval plus ranking outcomes for representative queries) remain stable versus baseline.

---

### Edge Cases

- **Partial rollout**: One increment ships while others wait; behavior must not depend on unfinished increments except where explicitly documented as temporary.
- **Rollback**: A bad increment can be reverted without undoing unrelated improvements, within the granularity promised per increment.
- **Concurrent teams**: Two contributors work on recall versus search; merge conflicts and ownership disputes are minimized by clear boundaries.
- **Emergency fix**: A production hotfix can still land without completing the full refactor program—process must not block urgent patches. **Whether the FR-013 manual regression gate must be satisfied before merge for such hotfixes** (or may be abbreviated, waived, or completed post-merge) is **not prescribed here**; follow **organization release/incident policy** (see **FR-019**).
- **Behavioral parity breach**: If a change inadvertently alters visible behavior, it MUST be rolled back or followed immediately by a parity-restoring fix; intentional behavior changes belong outside this program unless separately approved.
- **Persistence change deferred**: Schema migrations, storage format changes, or on-disk layout changes required for clarity MUST be scheduled **outside the first wave** (or as a separately approved program), not bundled silently into structural refactors.
- **Performance not a program goal**: Throughput, latency, or resource-efficiency targets are **not** part of this program’s success definition; incidental changes may occur but are not acceptance criteria. Severe production-impacting regressions remain subject to normal release and rollback policy outside this spec.
- **Follow-on waves out of scope**: A second wave (e.g., persistence changes, performance initiatives, expanded refactors) is **not specified here**; it will be decided after the first wave outcomes and should use a **new or amended specification** if pursued.
- **Regression gate by risk (clarified 2026-04-12)**: For **routine** increments, those that **directly change** memory recall, hybrid search, or administrative HTTP **runtime behavior or request-handling paths** require **both** passing CI **and** completion of the **agreed manual regression** for touched areas before merge (per FR-013, **FR-026**). **Documentation-only** increments without such changes require **CI**; manual regression is **recommended** but **not** a merge gate per **FR-026**. **Type-only** or **emit-equivalent** changes in those areas that **do not** alter runtime behavior or request-handling paths are treated like **documentation-only** for the **mandatory** manual gate (**FR-026**); **build/compiler/bundler** changes that **can** change emitted code or runtime wiring may still trigger **FR-013**. Increments that **only** touch other capability areas (e.g., **embedding pipeline**, **scheduled background coordination**, **relationship extraction**) **without** **direct** changes to those three surfaces’ behavior or paths **do not** become **mandatory** FR-013 solely because of **indirect** effects on recall/search outcomes—**CI** is required; manual regression is **recommended**. Other increments require **CI only**; manual regression remains **recommended** where helpful. **Production emergency hotfixes** follow **FR-019**.
- **Multi-channel defect reports (clarified 2026-04-12)**: If customer-reported defects may appear in **more than one** system, **`plan.md`** MUST record **merge, deduplication, and precedence** per **FR-023** so **SC-002** comparisons are not inflated or inconsistent.
- **Thin automated coverage (clarified 2026-04-12)**: A touched capability area may lack sufficient **automated** tests to catch regressions on its own. **FR-024** applies: parity is still required via **CI + agreed manual steps** where **FR-013** mandates them; **adding automated tests** is **not** a program-level merge gate, though teams **may** do so and **may** track gaps as debt.
- **First wave incomplete coverage**: If a listed capability area has **no** qualifying increment by the time stakeholders intend to close the wave, the first wave MUST be treated as **incomplete** until the gap is closed **or** stakeholders explicitly supersede this requirement in a **new or amended specification** (see FR-014).
- **External doc drift (clarified 2026-04-12)**: **Wikis or external tools** that **mirror** **FR-007/FR-017** or **FR-020** content MUST **not** be mistaken for the **authoritative** copy; **in-repo** paths per **FR-025** and **FR-020** govern.
- **Multiple `plan.md` files (clarified 2026-04-12)**: This specification’s **`plan.md`** references mean **only** the file **co-located** with **`spec.md`** per **FR-027**—not other `plan.md` files elsewhere in the repository unless the **authoritative** file **explicitly** points to them.

## Assumptions

- The refactor program targets previously identified high-complexity areas: agent memory recall, hybrid search execution, scheduled background coordination, relationship extraction from text, administrative HTTP capabilities, and the embedding pipeline—without prescribing implementation mechanics here.
- **First wave completion (clarified 2026-04-12)**: The **first wave** ends when **each** of those capability areas has received **at least one** independently releasable refactor increment merged to the **integration line** (per FR-001, FR-014, **FR-018**)—not merely when documentation exists or partial subsets ship.
- **First wave constraint (clarified 2026-04-12)**: Deliveries prioritize **behavioral parity**—no new product features and no intentional change to agent- or operator-visible behavior; outputs are clearer structure, boundaries, and documentation, with equivalence demonstrated by regression.
- **First wave excludes persistence changes (clarified 2026-04-12)**: No database schema migrations, no changes to stored data formats, and no on-disk persistence layout changes in the first wave—only code organization and documentation unless escalated as a separate approved effort.
- **Regression gates (clarified 2026-04-12)**: "Behavior preservation" uses the project's **standard automated checks (CI) for every increment**. The **agreed short manual regression list** is **mandatory before merge** only for increments that **directly change** memory recall, hybrid search, or administrative HTTP **runtime behavior or request-handling paths** (**FR-026** excludes **documentation-only** changes and **type-only / emit-equivalent** changes that preserve those paths from this **mandatory** gate). **Potential indirect** effects on recall/search from work in **other** capability areas (e.g., **embedding pipeline**, **background scheduling**) **do not** by themselves elevate an increment to **mandatory** FR-013 if those three surfaces are **not directly** changed—**CI** still applies; manual regression remains **recommended**. For other increments, manual checks are **recommended** and documented but **not** a merge gate unless release policy says otherwise. The **authoritative checklist location** MUST be recorded per **FR-020**. **Production emergency hotfixes** MAY follow **different** gates per **FR-019** and org policy—not overridden by this spec.
- **Automated test expansion vs merge gate (clarified 2026-04-12)**: This program does **not** require increments to **add or extend automated tests** solely because coverage for a touched area is incomplete; see **FR-024**. Parity uses **CI + manual regression** where applicable; stronger automation **may** be adopted under team practice or **`plan.md`** encouragement without becoming a **program-level** mandatory merge condition.
- Stakeholders accept incremental delivery; perfection is not required in the first increment.
- **No performance SLOs in scope (clarified 2026-04-12)**: This program does not commit to improving or preserving specific latency/throughput metrics as **program-level** outcomes; those belong to separate initiatives unless release policy requires a hotfix.
- **Operational touchpoints per increment (clarified 2026-04-12)**: Each shipped increment includes a **brief note** naming relevant logs, metrics, or alerts for the touched areas, or explicitly states that none apply—without requiring a full observability redesign.
- **Second wave TBD (clarified 2026-04-12)**: Any program after the first wave (including persistence, performance, or broader rewrites) is **outside this document’s scope** until stakeholders open a new specification cycle.
- **Heuristic quality signals (clarified 2026-04-12)**: Automated **heuristic or static quality indicators** (e.g., complexity- or deficit-style scores) may **inform** prioritization and code review but are **not** mandatory merge gates **at the program level** unless a **separate engineering policy** (outside this spec) mandates them.
- **SC-002 defect trend definition (clarified 2026-04-12)**: What constitutes a **“statistically meaningful increase”** in recall/search–related customer-reported defects (including **severity filters**, **labeling rules**, and **baseline comparison method**) is **not** numerically fixed in this specification; it MUST be written in the **implementation plan** or **release verification** materials per **FR-016** so SC-002 can be assessed consistently.
- **SC-002 defect data authority (clarified 2026-04-12)**: The **primary** system or channel for **customer-reported defects** used in **SC-002** trend comparisons MUST be **explicitly named in `plan.md`** per **FR-023**. **Secondary** sources MAY be used only with **merge, deduplication, and precedence rules** recorded there so defects are not double-counted or inconsistently classified.
- **Maintainer documentation shape (clarified 2026-04-12)**: **Capability boundaries** and the **increment map** MUST live in **one primary maintainer-facing document** updated in place as increments land (**FR-007**, **FR-017**), with **authoritative** content **in-repo** per **FR-025**. **Per-increment-only** documentation without a **single authoritative map** is **not** an acceptable substitute unless stakeholders explicitly approve an exception.
- **Integration line (clarified 2026-04-12)**: The **integration line** (merge target used for **FR-013** and **FR-014**) is **not** named in this specification; it **MUST** be **explicitly recorded** in the program’s **`plan.md`** (per **FR-027**) at program setup (or updated there if policy changes) per **FR-018** so “merge to the integration line” is unambiguous for all stakeholders.
- **Emergency hotfix vs FR-013 (clarified 2026-04-12)**: **Production emergency hotfixes** that touch recall, search, or administrative HTTP surfaces are **not** governed exclusively by this specification’s merge rules; **whether FR-013’s manual checklist applies before merge** in those situations MUST follow **organization release and incident-response policy** per **FR-019**. Routine refactor increments still use **FR-013** as the default gate.
- **Manual regression checklist location (clarified 2026-04-12)**: The **authoritative** text of the **FR-013** manual regression checklist MUST **not** be ambiguous across wikis or ad-hoc copies; its **canonical location** MUST be **recorded in `plan.md`** per **FR-020**. If the checklist is **not** embedded in the **FR-007/FR-017** primary document, its **authoritative** copy MUST still be **in-repo** under version control (**FR-025** alignment); **`plan.md`** records the **path**.
- **SC-004 contributor sample (clarified 2026-04-12)**: When **five or more** contributors are available, **SC-004** uses a sample of **at least five**; when **fewer than five** exist, **all who volunteer** are included, with **at least three** responses required to assess the **30%** target for that period—**counts and limitations** recorded in the **quarterly retrospective** per **FR-021**.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The program MUST deliver a **prioritized sequence of refactor increments**, each independently releasable, with stated intent (which **capability area’s maintainability** is addressed—without implying new user-facing features in this program).
- **FR-002**: Each increment MUST include **explicit verification** that previously working scenarios for memory recall and hybrid search remain acceptable, using the agreed regression approach **and the merge/release gating rules in FR-013** (including **FR-020** for where the manual checklist is authoritatively recorded, **FR-026** for **documentation-only** increments and **type-only / emit-equivalent** increments where applicable, and **FR-013**’s rule that **indirect-only** changes from **other** capability areas do **not** by themselves mandate the manual gate). **For avoidance of doubt**: “remain acceptable” is **not** interpreted to require full recall/search manual regression on **every** increment regardless of scope; it is met by the **same** evidence required by **FR-013**—**all** increments pass **CI**; **mandatory** manual checklist steps for memory recall, hybrid search, and administrative HTTP apply **only** when **FR-013** requires them for that increment; increments that do **not** directly change those surfaces per **FR-013** still satisfy **FR-002** by passing **CI** (and any **recommended** manual steps), without implying extra mandatory recall/search verification beyond **FR-013**.
- **FR-003**: Administrative HTTP capabilities MUST remain **organized so that review and onboarding** do not require understanding one oversized registration block for the entire surface.
- **FR-004**: Background scheduling and batch work MUST expose **clear ownership boundaries** between configuration, execution, and failure handling so changes do not require editing unrelated concerns for typical tasks.
- **FR-005**: The embedding pipeline MUST reduce **unsafe generic handling of untyped values** where those values cross module boundaries (without mandating a specific type system here).
- **FR-006**: Relationship extraction flows MUST separate **provider selection, extraction orchestration, and persistence** enough that changes to one layer do not routinely force edits across all three.
- **FR-007**: The program MUST produce **maintainer-facing documentation** of capability boundaries and the increment map, kept current as increments land **as one primary living document** per **FR-017** (clarified 2026-04-12).
- **FR-008**: Each increment MUST preserve **behavioral equivalence** for scenarios covered by the agreed regression approach **(including manual coverage where FR-013 requires it)**; intentional user- or operator-visible behavior changes are **out of scope** for this program unless tracked as a separate approved change. **New or extended automated tests** are **not** required as a **program-level merge gate** solely for coverage gaps—see **FR-024**.
- **FR-009**: The **first wave** of increments MUST NOT introduce database schema migrations, stored-data format changes, or on-disk persistence layout changes; such work is **out of scope** for the first wave and MUST be planned separately if needed.
- **FR-010**: This program MUST **not** treat latency, throughput, or resource utilization as **success targets** or mandatory acceptance metrics; success is defined by maintainability outcomes and behavioral parity per FR-001–FR-027 and Success Criteria.
- **FR-011**: Each **refactor increment** MUST ship with a short **operational touchpoint summary**: which logs, metrics, or alerts operators should use when investigating failures in the changed areas, or an explicit **“none applicable”** statement when none exist.
- **FR-012**: This specification governs the **first wave** only; **follow-on waves** (including persistence, performance, or scope expansion) MUST be captured in a **separate or amended specification** after first-wave review—this document MUST NOT be interpreted as committing to those outcomes.
- **FR-013**: **Regression merge gate (clarified 2026-04-12)**: Every increment MUST pass the project’s **standard automated CI checks** before merge to the **integration line** named per **FR-018**. **Additionally**, any increment that **directly changes behavior or code paths** in **memory recall**, **hybrid search**, or **administrative HTTP** MUST complete the **agreed manual regression checklist** (see **FR-020** for its **authoritative location**) for the touched areas **before that merge**, **except** where **FR-019** applies (production emergency hotfixes governed by org policy) **or** where **FR-026** applies (**documentation-only** increments **or** **type-only / emit-equivalent** changes that **do not** alter **runtime behavior** or **request-handling paths** on those surfaces). **Indirect** influence on recall/search outcomes from changes **confined to other** capability areas (e.g., **embedding pipeline**, **scheduled background coordination**, **relationship extraction**) **does not** by itself trigger this **mandatory** manual gate; such increments MUST still pass **CI**, and manual regression is **recommended**. Increments that do **not** touch those surfaces still MUST pass CI; manual regression is **recommended** and may be noted as waived when not applicable.
- **FR-014**: **First wave completion (clarified 2026-04-12)**: The first wave of this program is **complete** only when **each** capability area listed in the program assumptions—**agent memory recall**, **hybrid search execution**, **scheduled background coordination**, **relationship extraction from text**, **administrative HTTP capabilities**, and the **embedding pipeline**—has at least **one** **independently releasable** refactor increment (per FR-001) **merged** to the **integration line** named per **FR-018**. Missing any area means the first wave is **not** complete unless superseded by a newer specification.
- **FR-015**: **Heuristic/static quality metrics (clarified 2026-04-12)**: **Heuristic or static quality signals** (e.g., complexity- or deficit-style scores from tooling) MAY **inform** prioritization and review for this program but MUST **not** be treated as **mandatory merge gates** for refactor increments **under this specification**; a **separate engineering or CI policy** may impose additional gates **outside** this document.
- **FR-016**: **SC-002 operational definition (clarified 2026-04-12)**: The **procedure for measuring SC-002**—including **which customer-reported defects count as recall/search–related**, **severity or priority filters**, **baseline window** (e.g., prior three-release interpretation), and **how “meaningful worsening” is judged** versus noise—MUST be documented in the **implementation plan** (`plan.md` per **FR-027**) or an equivalent **release verification checklist** tied to this program. The **primary defect data source** (and any **secondary** sources with merge/dedup rules) MUST satisfy **FR-023**. This specification retains only the **intent**: **no meaningful worsening** in that defect trend versus baseline.
- **FR-017**: **Maintainer documentation structure (clarified 2026-04-12)**: **FR-007** deliverables MUST use **one primary maintainer-facing document** that is **updated in place** to reflect both **capability boundaries** and the **increment map** as increments merge. That **primary** document MUST satisfy **FR-025** (authoritative content **in-repo**). **Optional** per-increment addenda MAY be used **only if** they are **linked from** and remain **subordinate to** that primary document—there MUST remain **one authoritative entry point** for onboarding and structured review (supporting **SC-001** and **SC-003**).
- **FR-018**: **Integration line (clarified 2026-04-12)**: The **integration line**—the branch or equivalent **merge target** to which refactor increments are merged for purposes of **FR-013** and **FR-014**—MUST **not** be inferred from this specification alone. It MUST be **explicitly named** in the program’s **`plan.md`** (per **FR-027**) when the program is established (and **updated** there if the merge policy changes). All references in this specification to **“the integration line”** mean **that named target**.
- **FR-019**: **Emergency hotfix vs FR-013 (clarified 2026-04-12)**: For **production emergency hotfixes** that change **memory recall**, **hybrid search**, or **administrative HTTP**, whether the **FR-013** manual regression checklist must be completed **before merge**, or may be **abbreviated**, **waived**, or **completed post-merge** per incident severity, is **not** defined in this specification—it MUST follow the organization’s **release and incident-response** policies. **`plan.md`** MAY **link to or briefly summarize** those policies for this program. For **routine** refactor increments (non-emergency), **FR-013** applies as stated.

That location MUST be **explicitly recorded in `plan.md`** when the program is established (and **updated in `plan.md`** if the checklist moves). **External** URLs alone MUST **not** be the **sole** authority for the checklist under this program. **PR or issue templates** MAY mirror checklist items for convenience but MUST **not** be the **sole** definition without the **`plan.md`** entry point.

When **fewer than five** active contributors exist, **all who volunteer** MUST be included, and **at least three** responses are required to treat the **30% perceived-time reduction** target as assessed for that period. **Participant count**, **volunteer rate**, and **pool size limitations** MUST be recorded in the **quarterly retrospective** (or equivalent). ## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In a facilitated onboarding exercise, at least **80% of participants** can correctly identify the owning capability area for a recall change versus a search change on the first attempt, using only the delivered documentation. **Participant sizing** for teams that cannot schedule five people, and **retrospective recording** alongside **SC-004**, MUST follow **FR-022**. **How to run and score the exercise** is specified in **Measurement procedures — SC-001** below.
- **SC-002**: For **two consecutive releases** after the program starts, there is **no statistically meaningful increase** in customer-reported defects tied to recall or search versus the prior three-release baseline. **Which channel(s) supply defect counts**, including the **primary authoritative source** and any **secondary** sources with merge/dedup rules, MUST follow **FR-023** (recorded in **`plan.md`** per **FR-027**). **Exact counting rules for recall/search relevance and the operational meaning of “statistically meaningful”** MUST follow **FR-016** (documented in the implementation plan or release verification artifacts—not fixed numerically in this spec). **How to take each release snapshot and compare to baseline** is specified in **Measurement procedures — SC-002** below.
- **SC-003**: Security or operations reviewers can complete an **administrative capability review session in 60 minutes or less** using the structured outline (time-boxed session, recorded pass/fail). **How to run the session and record the outcome** is specified in **Measurement procedures — SC-003** below.
- **SC-004**: Contributors report **at least a 30% reduction** in perceived time to locate the correct ownership area for a typical recall or search tweak (measured by a short quarterly survey or retrospective sample). **Contributor sample sizing**, including teams with **fewer than five** active contributors, MUST follow **FR-021**. **Survey cadence, instrument, and aggregation** are specified in **Measurement procedures — SC-004** below.

### Measurement procedures (SC-001–SC-004)

These procedures operationalize the success criteria without changing their thresholds. Numeric parameters delegated to **FR-016** (e.g. **N** for σ-style rules) MUST be fixed in **`maintainer-map.md`** or **`research.md`** before the first assessment period and reused for comparable snapshots.

**Task traceability (`tasks.md`)**: Executable hooks align with this section as follows — **T014** (SC-003, with User Story 2 admin HTTP), **T027** (SC-001), **T028** (SC-004), **T029** (SC-002). Final quality gates (`npm run lint` / `type-check` / `test`) remain **T030**.

#### Measurement procedures — SC-001 (facilitated onboarding exercise)

| Step | Action |
|------|--------|
| 1. Schedule | Schedule **one** facilitated session per assessment wave (e.g. first-wave close, or quarterly if the team repeats the measure). The facilitator **guides** the session but is **not** part of the scored participant cohort. |
| 2. Materials | Participants may use **only** the authoritative maintainer documentation path named in **`plan.md`** for **FR-007/FR-017** (in-repo per **FR-025**). No IDE-wide search, no corrective hints beyond that document set. |
| 3. Prompts | Prepare a **fixed** short list of scenario prompts in advance—at minimum one **recall**-oriented and one **search**-oriented (e.g. “add a recall filter option” vs “adjust hybrid ranking weights”). **First attempt** means the participant’s **first** answer (written or spoken) before any corrective hint. |
| 4. Score | For each prompt, mark **correct** if the stated **capability area** matches the owning area in **`maintainer-map.md`**. Compute the **80%** target as: (correct first-attempt responses) ÷ (total scored responses), across participants in the cohort. |
| 5. FR-022 sizing | When **five or more** participants can be scheduled, include **at least five**. When **fewer than five**, include **all** who participate; require **at least three** for the **80%** outcome to be treated as measured. If **fewer than three**, record **why** in the quarterly retrospective; the target is **not** assessable for that wave (does not by itself invalidate other outcomes). |
| 6. Record | Log cohort size, prompts version, per-participant outcomes (or anonymized aggregates), and pool limitations in the **same quarterly retrospective** used for **FR-021/FR-022** and, where practical, alongside **SC-004** timing. |

#### Measurement procedures — SC-002 (defect trend vs baseline)

| Step | Action |
|------|--------|
| 1. Authority | Use the **primary** defect source and any **secondary** sources with merge/dedup rules exactly as in **`plan.md`** (**FR-023**) and **`research.md`**. |
| 2. Define “in population” | An issue counts as recall/search–related per the **label/title/query rules** documented in **`maintainer-map.md`** (or equivalent) per **FR-016**—not ad hoc per release. |
| 3. Baseline window | Establish the **prior three releases** (tags or semver boundaries) **before** the first post-program counted release; record tag names and date bounds in **`maintainer-map.md`** or release notes. |
| 4. Post-program releases | Identify **two consecutive** releases **after** program start (per the team’s release naming). For **each**, compute the same defect metric (counts and/or severity mix per **FR-016**) using the **same** rules as the baseline window. |
| 5. Meaningful worsening | Apply the **documented rule** for “statistically meaningful” or programmatic worsening from **FR-016** (e.g. median + **N**σ, or P0/P1 threshold)—with **N** and filters **fixed** for the program in **`maintainer-map.md`**, not chosen after seeing results. |
| 6. Pass | **Pass** if **neither** of the two consecutive releases meets the **worsening** condition relative to baseline under the fixed rule. |
| 7. Record | For each snapshot, add a row to an **SC-002** table (in **`maintainer-map.md`** or **`research.md`**): release id, counts, baseline reference, rule applied, pass/fail. |

#### Measurement procedures — SC-003 (administrative review time box)

| Step | Action |
|------|--------|
| 1. Outline | Use the **structured administrative HTTP outline** in **`maintainer-map.md`** (route group → capability → authorization expectation). |
| 2. Reviewer | **One** primary reviewer (or the minimum your security policy requires) walks **all** groups in the outline **without** skipping a capability area. |
| 3. Time box | **60 minutes** wall-clock from start of walkthrough. **Pass** if every group is covered within 60 minutes. **Fail** if time expires with uncovered groups, or if the outline is missing entries needed to complete the review. |
| 4. Record | Log **actual duration**, **pass/fail**, and optional non-sensitive notes (e.g. doc gaps) in the PR for the admin refactor, **`maintainer-map.md`**, or a short program appendix. |

#### Measurement procedures — SC-004 (perceived time — quarterly)

| Step | Action |
|------|--------|
| 1. Cadence | Run **once per quarter** (or aligned with the team’s retrospective), using the **same** survey instrument unless you version it (then record the version id). |
| 2. Instrument | Use a **short** survey: e.g. Likert on “time to find the right place for a recall tweak” and “for a search tweak,” or estimated minutes **before vs after** the program, or a single **% improvement** estimate—pick **one** primary scale and document it in **`maintainer-map.md`** or **`research.md`**. |
| 3. Metric | **Pass** for a period if aggregated responses show **≥30%** improvement on the agreed primary measure (e.g. median perceived time down ≥30%, or ≥30% of respondents reporting “meaningful improvement,” consistent with the chosen scale). |
| 4. FR-021 sizing | If **≥5** active contributors exist, sample **≥5**; if **&lt;5**, include **all** volunteers. Require **≥3** responses to treat the **30%** target as **assessed** for that quarter. If **&lt;3**, record **why**; the target is **not** assessable for that period. |
| 5. Record | Store response counts (and anonymity stance), aggregated results, and limitations in the **quarterly retrospective** per **FR-021**, ideally **alongside SC-001** results for the same quarter. |
