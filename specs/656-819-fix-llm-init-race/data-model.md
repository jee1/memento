# Phase 1 Data Model: Relation extractor LLM init race

**Feature**: 656-819-fix-llm-init-race | **Date**: 2026-08-25

## 영속 데이터

**변경 없음.** DB 스키마·마이그레이션·타입 정의 변경이 없다(헌법 III 해당 없음). `memory_relation` 에 저장되는 관계 후보의 형태도 그대로다 — 이번 수정은 그 관계가 **생성되기 시작**하게 만들 뿐이다.

## 기존 엔터티 (참조용, 변경 없음)

### 관계 후보 (Relation Candidate)

| 필드 | 의미 | 이번 변경 |
|------|------|-----------|
| `source_id` / `target_id` | 연결되는 두 기억 | 없음 |
| `relation_type` | 관계 유형 | 없음 |

## 새로 도입되는 것: 폴백 사유 어휘

지속되는 데이터가 아니라 **구조화 로그 필드**다. 별도 타입·API 로 노출하지 않는다(FR-005, Key Entities 주석).

| 사유 값 | 발생 조건 | 관측 지점 |
|---------|-----------|-----------|
| `llm_unavailable` | 초기화가 끝났는데 사용 가능한 프로바이더가 없음 | 하이브리드 폴백 로그 |
| `init_failed` | 초기화가 **예외로** 끝나 프로바이더가 정해지지 않음 | 생성자 `LLM 클라이언트 초기화 실패` 로그 |
| `llm_call_failed` | 가용 판정은 통과했으나 추출 호출이 실패 | 기존 `LLM fallback 실패` 로그 |

**폴백 지점이 "미설정"과 "연결 실패"를 구분하지 않는 이유** (2026-08-26 리뷰 반영): `LLMClientInitializer.initialize()` 는 키 부재도 연결 점검 실패도 모두 `warnings` 로 흡수하고 `preferredProvider: null` 로 **정상 resolve** 한다. 즉 폴백 지점이 볼 수 있는 것은 "프로바이더가 없다"는 사실뿐이며, 원인을 여기서 단정하면 틀린 라벨이 된다. 구분에 필요한 구체적 원인은 초기화 시점에 이미 `LLM 초기화 경고`(`logger.warn`, warning 문자열 포함) 로그로 남으므로, 운영자는 그 줄과 대조해 판별한다. 원인을 폴백 지점까지 끌고 오려면 공유 initializer 에 구조화된 실패 종류를 도입해야 하는데, 이는 Non-Goal("가용성 상태를 구조화된 값·타입·진단 API 로 노출")에 걸린다.

**제약**: 사유 값에 API 키·토큰 등 자격 증명 값을 포함하지 않는다(FR-005).

## 상태 전이

추출기 인스턴스의 가용성은 다음 순서를 따른다. 요청마다 새 인스턴스가 만들어지므로 이 전이는 **인스턴스 단위**다(FR-001).

```text
생성
  └─ 초기화 진행 중 ──┬─→ 사용 가능           (프로바이더 확정)
                      ├─→ 사용 불가(미설정)   (초기화 완료, 프로바이더 없음)
                      └─→ 사용 불가(초기화 실패)
```

수정 전에는 "초기화 진행 중" 이 곧바로 "사용 불가" 로 읽혔다. 수정 후에는 이 상태에서 판정하지 않고 전이가 끝나기를 기다린다.
