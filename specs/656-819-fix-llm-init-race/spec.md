# Feature Specification: Relation extractor silently falls back to rule-based

**Feature Branch**: `656-819-fix-llm-init-race`
**Created**: 2026-08-25
**Status**: Draft
**Input**: User description: "https://github.com/jee1/memento/issues/819"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새 프로세스에서도 기억 저장 시 LLM 관계 추출이 실제로 동작한다 (Priority: P1)

에이전트가 서버를 새로 띄운 직후 기억을 저장한다. 규칙 기반 추출이 관계를 찾지 못하거나 신뢰도가 낮으면, 시스템은 설정된 LLM 으로 관계 추출을 시도해 의미 기반 관계를 만들어 준다. 현재는 LLM 이 정상 설정돼 있어도 이 시도가 한 번도 일어나지 않고 규칙 기반 결과만 조용히 반환된다.

**Why this priority**: 관계 그래프 품질의 핵심 경로다. 이 흐름이 죽어 있으면 LLM 을 설정한 모든 사용자가 비용은 0 이지만 관계 품질도 0 인 상태로 운영된다. 사용자에게는 실패로 보이지 않아 발견도 늦다.

**Independent Test**: LLM 자격 증명이 설정된 새 프로세스에서 규칙 기반으로는 관계가 안 나오는 기억을 저장하고, LLM 추출이 시도되었는지와 LLM 기반 관계가 영속화되었는지로 단독 검증 가능하다. 저장 경로의 관계 추출은 저장 응답과 분리된 백그라운드 작업이므로, 검증 대상은 저장 응답 본문이 아니라 남은 관계와 시도 로그다.

**Acceptance Scenarios**:

1. **Given** LLM 프로바이더가 정상 설정된 갓 시작한 프로세스, **When** 규칙 기반 신뢰도가 임계값 미만인 기억을 저장하면, **Then** LLM 관계 추출이 시도되고 LLM 이 만든 관계가 영속화된다(저장 응답 본문이 아니라 저장된 관계와 시도 로그로 확인).
2. **Given** 동일 상태, **When** 첫 번째 저장 요청이 처리되면, **Then** "LLM 서비스가 사용 불가능하여 규칙 기반 결과 반환" 로그는 남지 않는다.
3. **Given** 첫 저장 이후 이어지는 저장 요청들, **When** 같은 조건으로 저장하면, **Then** 첫 요청과 동일하게 LLM 추출이 시도된다(첫 호출만 성공하고 이후가 달라지는 일이 없다).
4. **Given** 프로바이더를 자동 선택하도록 두고 클라우드 자격 증명 없이 로컬 프로바이더만 기동된 환경, **When** 규칙 기반 신뢰도가 임계값 미만인 기억을 저장하면, **Then** 그 로컬 프로바이더로 LLM 추출이 수행되고, 자격 증명 설정을 요구하는 실패 로그는 남지 않는다.

---

### User Story 2 - LLM 전용 추출 요청이 초기화 타이밍 때문에 실패하지 않는다 (Priority: P2)

사용자가 관계 추출을 LLM 전용 방식으로 명시해 요청한다. LLM 이 정상 설정돼 있다면 요청 시점이 프로세스 기동 직후인지 여부와 무관하게 추출이 수행돼야 한다.

**Why this priority**: 명시적 LLM 요청은 실패가 사용자에게 즉시 보이므로 P1 보다 발견은 쉽지만, 현재는 정상 설정에서도 "LLM 서비스가 사용 불가능합니다" 오류가 반환되어 기능 자체를 쓸 수 없다.

**Independent Test**: 새 프로세스에서 LLM 전용 방식으로 관계 추출을 요청해 오류 없이 결과가 오는지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** LLM 프로바이더가 정상 설정된 갓 시작한 프로세스, **When** LLM 전용 방식으로 관계 추출을 요청하면, **Then** 오류 없이 LLM 기반 관계가 반환된다.
2. **Given** LLM 프로바이더가 전혀 설정되지 않은 프로세스, **When** LLM 전용 방식으로 요청하면, **Then** 설정이 없음을 알리는 명확한 오류가 반환된다.

---

### User Story 3 - LLM 이 정말 없을 때는 이유를 알 수 있게 폴백한다 (Priority: P3)

LLM 자격 증명이 없거나 초기화에 실패한 환경에서는 규칙 기반 결과로 폴백하되, 운영자가 로그만 보고 "설정이 없어서"인지 "초기화가 실패해서"인지 구분할 수 있어야 한다.

**Why this priority**: 폴백 자체는 이미 동작한다. 이번 결함이 오래 숨어 있던 이유가 폴백 로그가 두 상황을 구분하지 못했기 때문이므로, 재발 시 진단 시간을 줄이는 가치가 있다.

**Independent Test**: 자격 증명 없는 환경과 잘못된 자격 증명 환경에서 각각 저장을 수행해 로그가 서로 다른 사유를 남기는지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** LLM 자격 증명이 설정되지 않은 환경, **When** 기억을 저장하면, **Then** 규칙 기반 결과가 반환되고 "설정 없음" 사유가 로그에 남는다.
2. **Given** 자격 증명은 있으나 초기화가 실패하는 환경, **When** 기억을 저장하면, **Then** 규칙 기반 결과가 반환되고 초기화 실패 사유가 로그에 남으며 저장 자체는 성공한다.

---

### Edge Cases

- 한 추출기 인스턴스가 초기화 중인데 그 인스턴스로 여러 추출이 동시에 들어오면? → 모두 동일한 초기화 결과를 보고 판정해야 하며, 일부만 LLM 을 쓰고 일부는 규칙 기반으로 갈리지 않아야 한다. 서로 다른 인스턴스 사이의 판정 일치는 이번 범위 밖이다 — 요청별 인스턴스 생성을 유지하므로(Non-Goals) 인스턴스마다 초기화가 독립적으로 일어난다.
- 원격 엔드포인트가 느려 초기화가 수 초 걸리면? → 저장은 실패하지 않고, 지연은 초기화 재시도 정책의 상한 안에서만 발생한다.
- 초기화가 실패로 끝난 경우 이후 요청은? → 매 요청마다 예외가 새어 나가지 않고 규칙 기반 폴백으로 처리된다.
- 규칙 기반 결과가 이미 충분히 신뢰도가 높은 경우? → LLM 을 부르지 않으며, 초기화 대기 때문에 응답이 느려지지도 않는다.
- 로컬 프로바이더(연결 점검을 동반하는 경우)로 설정된 환경? → 연결 점검 결과가 나온 뒤 가용성이 판정된다. 점검 자체는 수정 전에도 수행되던 작업이지만 아무도 기다리지 않았으므로 **대기는 새로 생기는 비용**이다. 다만 착지점이 경로마다 다르다: 기억 저장 경로의 관계 추출은 저장 응답과 분리된 백그라운드 작업이라 **저장 응답 시간은 변하지 않고**, 지연은 같은 기억의 후속 백그라운드 작업으로 넘어간다. 동기 대기를 실제로 부담하는 곳은 명시적 관계 추출 도구 호출 하나뿐이다. 흔한 오설정(로컬 프로바이더 미기동 → 연결 즉시 거부)은 재시도가 즉시 실패해 수백 ms 수준이고, 응답하지 않는 호스트(방화벽 드롭 등)라야 재시도 상한만큼 걸린다. 상한은 기존 초기화 재시도 정책이 정하며(FR-008), 이 비용은 범위 결정 시 수용하기로 한 사항이다.
- 여러 기억을 한 번에 처리하는 배치 추출은? → 배치 안의 항목들이 병렬로 처리되더라도 모두 동일한 초기화 결과를 보고 판정해야 하며, 일부 항목만 LLM 추출을 받는 결과가 나오지 않아야 한다. 배치는 한 인스턴스가 처리하므로 FR-001 의 인스턴스 내 일관성으로 충족된다.
- 초기화가 진행 중인 동안 LLM 이 실제로는 사용 가능한 상태로 밝혀졌지만, 그 사이 규칙 기반 폴백 결과가 캐시에 저장되면? → 미가용 판정으로 인한 규칙 기반 폴백 결과는 캐시에 저장하지 않는다(현재 동작 유지).
- 짧은 시간에 저장이 몰리면? → 저장마다 백그라운드 추출기가 새로 생기므로 초기화 점검도 저장 수만큼 동시에 발생한다. 사용자 응답에는 영향이 없지만, 로컬 프로바이더가 응답하지 않는 환경에서는 대기 중인 백그라운드 작업이 함께 쌓인다. 이번 범위에서는 수용하고, 추출기 재사용 후속 이슈의 근거로 남긴다.
- 폴백 사유 로그에 자격 증명이 섞이면? → 사유는 분류값과 기존 초기화 경고 메시지 범위로 한정하고, API 키·토큰 값은 로그에 남기지 않는다(FR-005).
- 프로바이더를 자동 선택하도록 두고 클라우드 자격 증명 없이 로컬 프로바이더만 떠 있는 환경? → 가용으로 판정되고 실제 추출도 그 프로바이더로 수행돼야 한다. 현재는 가용성 판정과 실행 경로의 프로바이더 판정이 서로 다른 기준을 써서 어긋나 있고, 레이스만 고치면 이 어긋남이 드러나 저장마다 "자격 증명을 설정하라"는 잘못된 실패 로그가 남는다(FR-010).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 가용성 판정이 필요한 경로에서, 시스템은 LLM 가용 여부를 판정하기 전에 진행 중인 LLM 초기화가 끝나기를 기다려야 한다(MUST). 초기화 완료 전 판정으로 "사용 불가"를 단정해서는 안 된다. 한 추출기 인스턴스의 초기화 완료를 동시에 기다리는 추출들은 모두 동일한 초기화 결과를 보고 판정해야 한다(MUST) — 같은 인스턴스를 쓰는 동시 추출이 서로 다른 경로로 갈라져서는 안 된다. 인스턴스 간 판정 일치는 요구하지 않는다: 요청별 인스턴스 생성을 유지하기로 했으므로(Non-Goals) 인스턴스마다 초기화가 독립적이다.
- **FR-002**: 하이브리드 추출에서 규칙 기반 결과가 없거나 신뢰도 임계값 미만이고 LLM 이 사용 가능하면, 시스템은 LLM 추출을 시도해야 한다(MUST) — 프로세스 기동 후 경과 시간과 무관하게.
- **FR-003**: LLM 전용 추출 요청은 초기화가 아직 완료되지 않았다는 이유만으로 실패해서는 안 된다(MUST NOT). 초기화 완료 후에도 사용 가능한 프로바이더가 없을 때만 실패해야 한다.
- **FR-004**: 초기화가 실패해도 기억 저장과 하이브리드 추출은 성공해야 하며(MUST), 규칙 기반 결과를 반환해야 한다.
- **FR-005**: 규칙 기반으로 폴백할 때 로그는 사유를 구분할 수 있어야 한다(MUST): 프로바이더 미설정 / 초기화 실패 / LLM 호출 실패. 구분은 기존 폴백 로그 지점의 메시지 분기와 사유 필드로 충족하며, 새로운 상태 타입이나 진단 API 를 도입하지 않는다(MUST NOT). 사유 값에 API 키·토큰 등 자격 증명 값을 포함해서는 안 된다(MUST NOT).
- **FR-006**: 기존 공개 계약(관계 추출 도구의 요청·응답 형태, 기존 옵션 의미)은 변경 없이 유지되어야 한다(MUST).
- **FR-007**: 규칙 기반 결과가 이미 신뢰도 임계값을 만족하는 경우, 시스템은 LLM 초기화 완료를 기다리지 않아야 한다(MUST NOT wait) — 기존 빠른 경로의 지연이 늘어나선 안 된다. 이 경로는 가용성 판정 자체를 수행하지 않으므로 FR-001 의 대기 의무 대상이 아니다.
- **FR-008**: 초기화 대기 시간은 기존 초기화 재시도 정책이 정하는 상한을 넘지 않아야 한다(MUST). 별도의 새 대기 상한 설정값은 도입하지 않는다.
- **FR-009**: 가용성 판정의 공개 경로는 초기화 완료를 보장하는 비동기 판정 하나여야 한다(MUST). 초기화 완료를 보장하지 않는 판정 수단은 외부 호출자에게 노출되지 않아야 하며(MUST NOT), 남겨 둘 경우 "초기화 완료 이후에만 유효"함이 명시되어야 한다. 근거: 이번 결함은 그 판정 수단이 공개돼 있었기 때문에 발생했고, 그대로 두면 신규 호출자가 같은 방식으로 다시 밟는다.

- **FR-010**: 가용성 판정 결과와 실제 추출 실행 경로의 프로바이더 판정은 일치해야 한다(MUST). "사용 가능"으로 판정된 뒤 실행 단계에서 "사용 가능한 프로바이더 없음"으로 실패하는 조합이 있어서는 안 된다(MUST NOT). 특히 프로바이더 자동 선택으로 로컬 프로바이더가 선택된 환경도 두 판정 모두에서 사용 가능으로 취급해야 한다.

### Key Entities

- **관계 후보(Relation Candidate)**: 두 기억 사이의 관계 제안. 출처(규칙 기반/LLM)와 신뢰도를 가진다.
- **추출기 가용성 상태(Extractor Availability)**: LLM 추출을 지금 쓸 수 있는지 여부. "초기화 진행 중", "사용 가능", "사용 불가(미설정)", "사용 불가(초기화 실패)" 를 구분한다. 이번 범위에서는 로그 사유를 구분하기 위한 개념이며(FR-005), 별도 타입이나 노출 API 로 구현하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: LLM 이 정상 설정된 환경에서, 프로세스 기동 후 첫 번째 저장부터 LLM 관계 추출 시도율이 100% 가 된다(현재 0%). 여기에는 프로바이더 자동 선택으로 로컬 프로바이더가 쓰이는 환경도 포함된다.
- **SC-002**: LLM 이 정상 설정된 환경에서 "LLM 서비스가 사용 불가능하여 규칙 기반 결과 반환" 로그 발생 건수가 0 이 된다.
- **SC-003**: LLM 이 설정되지 않은 환경에서 기억 저장 성공률은 변경 전과 동일하게 100% 를 유지하고, 규칙 기반 관계 결과도 변경 전과 동일하다.
- **SC-004**: 규칙 기반 결과가 신뢰도 임계값을 만족하는 명시적 관계 추출 요청의 응답 시간이 변경 전 대비 증가하지 않는다(측정 가능한 회귀 0). 기억 저장 응답 시간은 관계 추출이 백그라운드로 수행되므로 어느 경우에도 영향받지 않는다.
- **SC-005**: 폴백 로그만 보고 세 가지 사유(미설정 / 초기화 실패 / 호출 실패)를 구분할 수 있어, 동일 유형 결함의 원인 파악에 코드 열람이 필요하지 않다.

## Assumptions

- 이슈 보고자가 확인한 증상(매 저장마다 폴백, 네트워크 호출 0회)은 저장 경로가 요청마다 추출기를 새로 만들기 때문에 재현된다. 이 구조 자체(요청별 생성)는 이번 범위에서 바꾸지 않는다.
- 초기화 실패는 이미 내부적으로 흡수되어 예외가 밖으로 새지 않는다고 가정한다. 대기 도입이 이 성질을 깨지 않아야 한다.
- 원격 프로바이더 초기화는 대부분 클라이언트 준비만 수행하므로 대기 비용이 사실상 0 이다. 연결 점검을 수행하는 로컬 프로바이더만 실제 대기가 발생한다.
- 기억 저장 경로의 관계 추출은 저장 응답과 분리된 백그라운드 작업으로 수행된다(코드 확인). 따라서 대기 도입이 저장 응답 시간을 늘리지 않으며, 동기 대기를 부담하는 경로는 명시적 관계 추출 도구뿐이다.
- 프로바이더 자동 선택 환경에서 클라우드 자격 증명이 하나도 없으면 로컬 프로바이더 연결 점검이 수행된다. 즉 "LLM 미설정" 기본 환경도 백그라운드에서 이 점검 비용을 낸다.
- 이슈에 함께 적힌 패키징 메모(helmet·umap-js 의존성 선언, 내부 패키지 동봉)는 현재 main 기준 이미 반영되어 있어 이번 범위에서 제외한다.

## Non-Goals

- 추출기 인스턴스 재사용/싱글턴화 등 초기화 비용 자체를 줄이는 구조 변경. (브레인스토밍 2026-08-25 결정: 후속 이슈로 분리)
- 관계 추출 품질(프롬프트, 신뢰도 임계값, 병합 규칙) 개선.
- 새로운 설정값·환경 변수 추가. 초기화 대기 상한 설정값도 여기에 포함된다.
- 가용성 상태를 구조화된 값·타입·진단 API 로 노출하는 것.
- 배포 tarball 의 의존성 검증(별도 확인 항목).
