# Phase 0 Research: 벡터 유사도 절대 척도 복원 (#806)

**Date**: 2026-08-29 | **Plan**: [plan.md](./plan.md)

Technical Context에 `NEEDS CLARIFICATION` 항목은 없다. 명세 단계의 brainstorm 6세션에서 20개 미결 질문이 모두 코드 실측으로 해소됐기 때문이다. 이 문서는 그 결론을 구현 결정으로 옮기고, 계획 수립 중 확인한 사실을 기록한다.

---

## D1. 거리→유사도 변환의 단일 정의 위치

**Decision**: `packages/memento-core/src/shared/utils/vector-similarity.ts`를 신설하고 `cosineDistanceToSimilarity(distance)`를 옮긴다. 현재 정의가 있는 `domains/search/repositories/vector-search/vector-search-result-mapper.ts`는 이 함수를 가져다 쓰고 그대로 재노출한다.

**Rationale**: 변환이 필요한 지점은 검색 도메인(저장소 매퍼)과 기억 도메인(임베딩 서비스) 양쪽이다. 한쪽 도메인에 정의를 두면 다른 도메인이 도메인 간 의존을 새로 만들어야 한다. `shared/utils`에는 이미 `clamp01`이 있고 모든 도메인이 의존해도 되는 위치다. 재노출을 유지하면 기존 매퍼 검증(`vector-search-result-mapper.spec.ts`)이 그대로 green baseline 역할을 한다.

**Alternatives considered**:
- 임베딩 서비스가 검색 도메인의 매퍼를 직접 import — 도메인 간 결합을 늘린다. 아키텍처 경계 테스트가 지금 이 방향을 금지하지는 않지만, 결함의 원인이 "정의가 흩어져 있는 것"이었으므로 결합을 늘리는 방향은 목적에 어긋난다.
- 임베딩 서비스에 같은 변환을 다시 구현 — 재발 조건을 그대로 남긴다. FR-020이 명시적으로 금지한다.

---

## D2. 대체 경로의 방향 통일 방식

**Decision**: `memory-embedding-service.ts`의 `buildVecSimilarityQuery`가 만드는 SQL에서 근접도 컬럼을 원시 거리값 하나로만 노출하고(`v.distance as distance`), `mapSimilaritySearchRows`가 D1의 공용 변환을 적용해 `similarity`를 만든다. 로컬 `VectorSearchResult`에서 `score` 필드를 제거한다.

**Rationale**: 현재 SQL은 `v.distance as similarity, (1 - v.distance) as score`로 같은 양을 방향이 다른 두 필드에 담고 있고, 하류는 거리값이 들어간 `similarity`를 읽는다. 값 자체는 이미 계산되어 있으므로 부족한 것은 계산이 아니라 방향 일관성이다(FR-024). `score`를 남긴 채 값만 맞추면 이름으로 방향을 알 수 없는 상태가 유지되므로 필드를 없애는 편이 계약이 명확하다.

**확인한 사실**: 이 타입의 `score` 필드를 읽는 생산 코드는 없다. 대체 경로 결과를 소비하는 지점(임계값 필터, 보충, 결합기)은 모두 `similarity`만 읽는다. 따라서 필드 제거는 하류 영향이 없다.

**Alternatives considered**:
- SQL에서 `(1 - v.distance) as similarity`로 바꾸고 매퍼는 그대로 — 변환이 다시 SQL에 흩어진다. 부동소수 오차로 인한 음수 distance나 비유한값 처리도 SQL에서는 표현하기 어렵다. FR-020의 "단일 정의" 요건을 만족하지 못한다.
- `score`를 유지하고 `similarity`와 같은 값으로 채움 — 중복 필드가 남아 FR-024를 만족하지 못한다.

---

## D3. 제공자별 최소·최대 재조정 제거 방식

**Decision**: `hybrid-vector-search-executor.ts`의 `normalizeResultsByProvider`를 제거한다. 중복 제거는 절대 `similarity`의 최댓값 기준으로 수행하고, 순위 산출도 `similarity`를 그대로 사용한다.

**Rationale**: 삭제가 가장 짧은 교정이며 재발 여지를 남기지 않는다. 항등 변환으로 남겨 두면 "정규화 단계가 존재한다"는 구조가 유지되어 나중에 다시 채워질 수 있다. 중복 제거의 최댓값 규칙은 FR-007이 이미 요구하고 있으므로 기준만 재조정값에서 절대값으로 바꾸면 된다.

**확인한 사실**: 임계값 필터(`filterByVectorThreshold`)와 보충(`fillUnderfilledVectorResults`)은 이미 재조정보다 **앞서** 실행된다. 따라서 임계값 0.38의 의미는 지금도 절대 기준이며, 이번 교정으로 임계값의 해석이 바뀌지 않는다. 이 순서는 코드에 계약으로 고정되어 있지 않으므로 검증으로 못박는다(FR-005, SC-006).

**Alternatives considered**:
- 재조정을 유지하되 제공자 간 고정 계수 보정으로 대체 — 보정이 필요한지는 절대 척도가 복원된 뒤에야 측정할 수 있다. 명세가 이번 범위에서 제외했다(FR-008은 도입 시의 제약만 규정).

## D4. 범위·유한성 보장의 유지 수단

**Decision**: D1의 공용 변환이 `clamp01`과 비유한값 처리(0 반환)를 포함하므로, 두 경로 모두 이 변환을 통과하는 것으로 0~1 보장이 성립한다. 하이브리드 실행 지점에서는 반환 직전 값이 이 계약을 만족하는지 검증으로 고정한다.

**Rationale**: 최소·최대 재조정은 의도와 무관하게 반환값을 0~1로 묶는 역할도 하고 있었다. 제거만 하면 FR-012가 우연에 기대게 된다(FR-017). 보장을 변환 함수 한 곳에 두면 새 방어 코드를 추가하지 않고도 계약이 유지된다.

**Alternatives considered**:
- 반환 직전에 별도의 clamp 단계를 추가 — 같은 보장을 두 곳에서 하게 되고, 그 자체가 D1이 없애려는 중복이다.

---

## D5. 랭킹 버전 식별자에 척도 반영

**Decision**: `shared/config/ranking-weights-loader.ts`의 `getRankingVersionPayload()`에 점수 척도 규정을 나타내는 항목을 추가한다(예: 척도 식별 문자열 상수). 임계값·가중치·프리페치 배수·보충 활성 여부의 **값은 건드리지 않는다**.

**Rationale**: 현재 payload는 가중치 + 임계값 + 프리페치 배수 + 보충 활성 여부 네 가지만 해시한다. FR-015가 그 네 값을 동결하므로, 척도를 바꿔도 식별자가 그대로 유지되어 교정 전후 검색 기록이 같은 실험 단위로 섞인다. 식별자는 비교 가능한 체제를 구분하려고 존재하는 기계 판독 수단이므로, 문서 기록으로 대체되지 않는다(FR-023). 값이 아니라 payload 구성 항목을 늘리는 변경이므로 FR-015와 충돌하지 않는다.

**Alternatives considered**:
- 문서 기록만으로 처리 — 시계열 분석 도구가 식별자로 기록을 묶으므로 사람이 읽는 기록은 대체 수단이 되지 못한다.
- 임계값 숫자를 미세 조정해 해시를 바꾸기 — 동결 원칙 위반이며 의미 없는 값 변경이다.

---

## D6. 대체 경로 회귀 검증의 도달 방법

**Decision**: `HybridVectorSearchExecutor` 생성자에 주입되는 벡터 검색 엔진의 `getIndexStatus()`가 `available: false`를 반환하도록 스텁해 대체 경로를 실행시킨다.

**Rationale**: 실행 지점은 진입 시 인덱스 가용 여부를 확인하고, 사용할 수 없으면 **예외 없이** 대체 경로를 선택한다. 따라서 오류를 인위적으로 발생시키지 않고도 대체 경로를 결정적으로 재현할 수 있다. 구조 변경이 필요 없다.

**부수 확인**: 이 사실은 대체 경로가 드문 오류 경로가 아니라 벡터 인덱스를 쓸 수 없는 실행 환경의 상시 동작 모드라는 뜻이기도 하다. 그런 환경에서는 모든 벡터 검색이 반전된 점수로 동작해 왔다.

---

## D7. 두 경로 비교 시 제공자 정렬

**Decision**: 경로 간 점수 일치 검증은 **제공자를 맞춘 뒤** 비교한다.

**Rationale**: 정상 경로는 저장된 모든 제공자를 병렬 조회한 뒤 같은 기억에 대해 제공자 중 최댓값을 남기고, 대체 경로는 쿼리 임베딩이 사용한 제공자 하나만 조회한다. 제공자를 맞추지 않으면 정상 동작을 결함으로 오판한다. 두 경로는 제공자별로 같은 벡터 저장소를 같은 방식으로 지정하므로, 제공자를 맞추면 비교 대상 자체는 동일하다.

---

## D8. 표시 문구는 코드 변경이 필요 없다

**Decision**: 결합 경로의 설명 문구 선택 로직은 그대로 두고 검증만 추가한다.

**Rationale**: 이 로직은 이미 절대 기준 임계값으로 문구를 고른다. 문제는 입력으로 들어오던 값이 재조정된 점수라 최상위가 항상 최댓값이었다는 것이다. Phase 3에서 입력이 절대값으로 바뀌면 문구 선택은 자동으로 의미를 갖는다. 문구 임계값 자체는 동결 대상이다(FR-015).

---

## D9. 검증 픽스처 원칙

**Decision**: 커밋되는 검증 데이터는 합성 픽스처로 구성한다. 재배포가 허용되지 않는 외부 코퍼스와 그 파생물은 커밋하지 않고, 그런 코퍼스를 사용하는 측정은 로컬 실행에 두고 집계·식별자·해시만 남긴다.

**Rationale**: 프로젝트 규약(Additional Constraints)이 요구하는 방식이며, SC-001·SC-003의 측정 방식이 여기에 구속된다. 절대 척도 검증은 "관련 있는 쌍"과 "무관한 쌍"을 합성으로 구성해도 충분히 판정할 수 있다.

---

## 확인했으나 변경 대상이 아닌 것

계획 단계가 다시 조사하지 않도록 기록한다.

| 대상 | 확인 결과 |
|------|-----------|
| 이웃 기억 조회(임계값 0.8), 앵커 다단계 확장 | 저장소 매퍼를 통과하는 다른 경로. 이미 절대 유사도를 받는다 |
| 시맨틱 중복 판정(0.9), 프로시저럴 병합(0.7/0.9), 기억 통합 클러스터링(0.65) | 검색 결과가 아니라 임베딩·문자열에서 직접 유사도를 계산한다 |
| 결합 이후의 `normalizeScores` | 이름만 정규화다. 결과별 특징 계산과 융합 관련성 산출만 하고 결과셋 기준 재조정을 하지 않는다 |
| 텍스트 채널 관련성 변환 | BM25 포화 함수와 전문 검색 순위 시그모이드로 결과 하나만 보고 절대값을 만든다. 결과셋 기반 재조정이 없다 |
| 제공자 통계 캐시 | 제공자 통계만 담고 결과 점수를 담지 않는다 |
| 적응형 가중치 | 쿼리 형태로만 결정되며 점수를 입력으로 쓰지 않는다 |
| 랭킹의 피드백 항 | 저장된 점수 스냅샷이 아니라 별도 입력을 사용한다. 척도 변경의 소급 영향이 없다 |
| 프로덕션 호출자가 없는 통합 검색 표면의 동종 재조정 | 사용자 검색 경로에 닿지 않는다. 후속 추적 대상 |
| 프라이버시 범위 필터의 채널 간 비대칭 | 텍스트 채널에만 적용되고 벡터 채널에는 전달되지 않는다. 보안·권한 범위 변경이므로 별도 명세가 필요하다. 이번 작업은 구성을 바꾸지 않고 무변경을 검증으로 고정한다 |
