# Feature Specification: relation 도메인 spec 2개의 config 모킹이 실제로 적용되지 않는다

**Feature Branch**: `657-821-fix-vi-mock-config-path`
**Created**: 2026-08-26
**Status**: Draft
**Input**: User description: "https://github.com/jee1/memento/issues/821"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - config 를 모킹한 테스트가 실제로 그 config 조건에서 돈다 (Priority: P1)

개발자가 relation 도메인의 관계 추출기 테스트에서 "LLM 프로바이더가 X 인 상황"을 모킹으로 만든다. 지금은 그 모킹이 소스가 실제로 읽는 설정 모듈이 아니라 존재하지 않는 모듈에 걸려 있어, 소스는 여전히 실제 설정을 본다. 개발자가 모킹으로 지정한 값과 테스트가 실제로 검증하는 조건이 서로 다르다.

**Why this priority**: 이 스펙들의 config 의존 단언이 전부 위양성이다. 통과해도 아무것도 보장하지 못하고, 결함이 있어도 잡히지 않는다. #819 작업 중 T005 의 RED 가 수정 없이 통과한 사례로 이미 실제 피해가 관측됐다. 나머지 모든 스토리가 이 교정 위에 얹힌다.

**Independent Test**: 모킹된 설정 값을 서로 다른 값으로 바꿔가며 같은 테스트를 실행해, 결과가 그 값에 따라 달라지는지로 단독 검증 가능하다. 값을 바꿔도 결과가 동일하면 모킹이 여전히 적용되지 않은 것이다.

**Acceptance Scenarios**:

1. **Given** 관계 추출기 테스트가 설정 모듈을 모킹한 상태, **When** 테스트를 실행하면, **Then** 소스 코드가 읽는 설정 값은 모킹된 값이다(실제 설정 값이 아니다).
2. **Given** 동일 상태, **When** 모킹된 프로바이더 값을 테스트가 기대하는 값과 다른 값으로 바꾸면, **Then** 해당 단언은 실패한다(값 변경이 결과에 반영된다).
3. **Given** 로컬 환경 변수에 `LLM_PROVIDER` 가 임의의 값으로 설정된 상태, **When** 두 스펙을 실행하면, **Then** 그 값과 무관하게 결과가 동일하다.
4. **Given** 환경 변수 `LLM_PROVIDER` 가 아예 없는 상태, **When** 두 스펙을 실행하면, **Then** 값이 설정된 경우와 동일한 결과가 나온다.

### User Story 2 - 모킹이 살아난 뒤에도 두 스펙 전체가 통과한다 (Priority: P1)

모킹이 처음으로 실제 동작하기 시작하면 config 에 의존하던 테스트들이 지금까지와 다른 조건에서 돈다. 개발자는 그 시점에 드러나는 실패를 전수 확인하고, 각 테스트가 의도한 설정 조건을 스스로 명시하게 정리한다.

**Why this priority**: 경로만 고치고 끝내면 스위트가 깨진 채로 남거나, 더 나쁘게는 "그냥 통과하도록" 단언을 약화시키게 된다. 경로 교정과 영향 정리는 같은 작업 단위로 묶여야 하므로 P1 이다.

**Independent Test**: 교정 후 두 스펙을 전부 실행해 통과 여부와, 각 실패 케이스가 "테스트가 의도한 조건을 명시하지 않아서"인지 "소스 결함이라서"인지 분류한 결과로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 모킹 경로가 교정된 상태, **When** 두 스펙을 실행하면, **Then** 전체 테스트가 통과한다.
2. **Given** 교정 과정에서 실패가 발생한 테스트, **When** 그 테스트를 수정하면, **Then** 수정은 단언을 약화시키는 것이 아니라 필요한 설정 조건을 명시하는 방향이다.
3. **Given** 교정 전에는 전량 통과하던 스위트, **When** 교정 후 실행하면, **Then** 통과 여부와 무관하게 각 테스트가 어떤 설정 조건에서 도는지가 코드상 드러난다.

### User Story 3 - 각 테스트가 자신의 설정 조건을 스스로 지정하고 되돌린다 (Priority: P1)

모킹이 처음으로 실효를 갖는 순간, 지금까지 아무 데도 닿지 않던 설정 값 대입들이 살아있는 쓰기로 바뀐다. 대체 값 객체는 스펙 파일 전체가 공유하는 하나의 가변 상태이므로, 한 테스트가 바꾼 값은 되돌리지 않는 한 뒤따르는 모든 테스트에 남는다. 개발자는 각 테스트가 자신이 전제하는 설정 값을 스스로 지정하고, 끝난 뒤 기준 상태로 되돌아가게 만든다.

**Why this priority**: 순서 무관성(FR-006)과 반복 실행 동일성(SC-003)이 전적으로 이 규율에 달렸다. 교정만 하고 이걸 빼면 스위트가 실행 순서에 따라 통과·실패를 오가게 되고, 이는 지금의 위양성보다 진단하기 어렵다. 경로 교정과 분리해 미룰 수 없어 P1 이다.

**Independent Test**: 설정에 의존하는 테스트들을 서로 다른 순서로 여러 번 실행해 결과가 매번 같은지, 그리고 각 테스트 직후 대체 값 객체가 기준 상태인지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 설정 값을 바꾸는 테스트가 실행을 마친 상태, **When** 대체 값 객체를 조회하면, **Then** 그 테스트 실행 전의 기준 상태와 같다.
2. **Given** 설정에 의존하는 테스트 두 개, **When** 순서를 바꿔 실행하면, **Then** 두 순서 모두에서 동일하게 통과한다.
3. **Given** 기준 상태 복원이 자동으로 적용되는 상태, **When** 어떤 테스트가 명시하지 않은 설정 항목을 소스가 조회하면, **Then** 항상 같은 기준 값을 본다.
4. **Given** 실제 전역 설정을 직접 바꾸던 잔존 지점, **When** 그 지점을 모킹 기반으로 옮기면, **Then** 해당 테스트는 원래 의도한 조건을 그대로 검증하며 통과하고, 실행 전후 실제 전역 설정 값은 변하지 않는다.

---

### User Story 4 - 같은 종류의 잘못된 모킹 경로가 다시 들어오지 못한다 (Priority: P3)

개발자가 존재하지 않는 모듈을 가리키는 모킹을 추가하면, 리뷰나 CI 단계에서 그 사실이 드러난다.

**Why this priority**: 이번 결함은 조용히 통과하기 때문에 발견까지 오래 걸렸다. 재발 방지 장치가 없으면 같은 실수가 다른 도메인에서 반복된다. 다만 결함 자체 해소보다는 후순위다.

**Independent Test**: 존재하지 않는 모듈을 가리키는 모킹을 일부러 하나 추가하고 검사를 돌려, 그 지점이 보고되는지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 재발 방지 검사가 도입된 상태, **When** 존재하지 않는 상대 경로 모듈을 모킹하는 테스트가 추가되면, **Then** 검사가 해당 위치를 실패로 보고한다.
2. **Given** 동일 검사, **When** 저장소의 현재 테스트 전체에 대해 실행하면, **Then** 정상적인 모킹은 하나도 오탐으로 보고되지 않는다.

---

### Edge Cases

- 패키지 이름으로 지정하는 모킹(외부 라이브러리 모킹)은 상대 경로가 아니므로 이번 교정 대상이 아니다. 재발 방지 검사도 이들을 실패로 보고해서는 안 된다.
- 모킹된 설정 객체가 실제 설정 객체보다 적은 항목만 제공할 때, 소스가 모킹에 없는 항목을 읽으면 어떻게 되는가? 모킹이 처음 동작하는 순간 드러나므로, 소스가 읽는 항목을 모두 제공해야 한다.
- 한 테스트가 모킹된 설정 값을 바꾸고 복원하지 않으면 뒤따르는 테스트가 영향을 받는다. 각 테스트는 실행 전 상태에 의존하지 않아야 한다.
- 테스트 대상이 설정을 직접 읽지 않고, 내부적으로 위임하는 다른 구성 요소가 읽는 경우가 있다. 이때도 모킹은 그 구성 요소가 읽는 실제 설정 모듈에 적용되어야 하며, 모킹 값 집합은 위임 대상이 조회하는 항목까지 포함해야 한다.
- 대상 소스가 직접으로도 위임으로도 읽지 않는 모듈을 모킹하고 있다면, 올바른 해소는 경로 교정이 아니라 그 모킹의 제거다.
- 모킹 선언의 대상 경로와, 테스트가 같은 모듈을 실행 중에 다시 가져오는 경로는 짝을 이룬다. 둘이 똑같이 존재하지 않는 곳을 가리키면 모킹 등록이 모듈 해석을 가로채므로 대상 부재가 드러나지 않고, 테스트는 자기가 만든 대체 값만 주고받으며 통과한다. 교정은 두 지점을 함께 바꿔야 한다. 한쪽만 바꾸면 방향에 따라 결과가 갈리는데, 선언만 고치면 남은 재가져오기가 해석에 실패해 요란하게 드러나지만, 재가져오기만 고치면 그쪽이 실제 설정 모듈을 받아 모킹 없이 실 전역을 조작하는 상태로 조용히 되돌아간다. 뒤쪽이 더 위험하다.
- 대체 값 객체를 모듈 최상위에 두고 모킹 선언이 그것을 참조하는 경우, 교정 전에는 대체 값이 실행 중 처음 요구되므로 문제가 없다. 교정 후에는 대상 모듈이 로드 시점에 요구되어 대체 값이 아직 만들어지기 전에 참조될 수 있고, 그러면 단언이 아니라 스펙 파일 로드 자체가 실패한다.
- 모킹 선언이 있어도 그 모듈을 아무도 가져오지 않으면 대체 값 생성조차 실행되지 않는다. 이런 선언은 실패로 드러나지도, 효과를 내지도 않는다. 따라서 짝을 잃은 모킹 선언은 오류를 내지 않고 그냥 무력해진다.
- 교정 후 실패한 테스트가 사실은 소스의 실제 결함을 드러낸 것이라면, 테스트를 고칠 것이 아니라 별도 이슈로 분리한다.
- 두 스펙 밖에도 동일한 잘못된 모킹 경로가 실재한다(실측 확인). 재발 방지 검사를 차단 방식으로 켜면 이번 범위 밖 위반 때문에 즉시 전체가 막힌다. 따라서 검사 도입과 기존 위반 예외 처리는 같은 작업 단위여야 한다.
- 예외 목록은 방치되면 그 자체가 새로운 조용한 통과 경로가 된다. 등재 항목이 해소됐는데도 목록에 남아 있으면 검사가 이를 알려야 한다.
- 설정 항목 중에는 대체 값보다 **환경 변수를 먼저 보는** 것이 있다. 이런 항목은 대체 값만 지정해서는 조건이 만들어지지 않는다. 즉 한 테스트의 조건이 두 경로로 갈라지고, 둘이 어긋나면 테스트가 의도한 조건과 소스가 보는 조건이 달라진다. 테스트는 두 경로를 함께 고정해야 한다.
- 환경 변수를 바꿔 조건을 만드는 테스트가 원래 값을 담아두기만 하고 되돌리지 않으면, 그 변경은 테스트가 끝난 뒤에도 남는다. 고정한 환경 변수는 실행 전 상태로 복원되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 관계 추출기 테스트가 선언한 설정 모킹은 대상 소스 코드가 실제로 읽는 설정 모듈에 적용되어야 한다.
- **FR-002**: 설정 모킹이 적용된 상태에서, 소스 코드가 조회하는 설정 값은 테스트가 지정한 값과 일치해야 한다.
- **FR-003**: 두 스펙의 실행 결과는 실행 환경의 LLM 프로바이더 관련 환경 변수 값(미설정 포함)과 무관하게 동일해야 한다.
- **FR-004**: 모킹 교정 후 두 스펙의 모든 테스트가 통과해야 한다.
- **FR-005**: 교정 과정에서 실패한 테스트는 단언을 약화시키지 않고, 해당 테스트가 전제하는 설정 조건을 테스트 안에서 명시하는 방식으로 수정되어야 한다.
- **FR-006**: config 에 의존하는 각 테스트는 다른 테스트의 실행 여부·순서와 무관하게 동일한 결과를 내야 한다.
- **FR-007**: 각 테스트는 자신이 전제하는 설정 값을 스스로 지정해야 하고, 테스트 종료 시 대체 값 객체는 기준 상태로 되돌아가야 한다. 기준 상태는 스펙 전체에서 하나로 정의된다.
- **FR-007a**: 테스트는 실제 전역 설정 객체를 변경해 조건을 만들지 않아야 하며, 실행 전후로 실제 전역 설정 값이 달라지지 않아야 한다.
- **FR-008**: 모킹된 설정 객체는 대상 소스 코드와 그것이 위임하는 구성 요소가 조회하는 모든 설정 항목을 제공해야 한다.
- **FR-009**: 저장소는 상대 경로로 지정된 모듈 모킹이 실재하는 모듈을 가리키는지 검사할 수단을 갖추어야 하며, 위반 지점을 위치와 함께 보고해야 한다.
- **FR-010**: FR-009 의 검사는 패키지 이름으로 지정된 모킹을 위반으로 보고하지 않아야 한다.
- **FR-011**: 교정 후 드러난 실패가 테스트 결함이 아니라 소스 결함으로 판명되면, 이번 범위에서 수정하지 않고 별도 항목으로 기록해야 한다.
- **FR-012**: 아무도 가져오지 않아 한 번도 평가되지 않는 모킹 선언은 제거되어야 하며, 이를 실제로 동작하는 모킹으로 대체하지 않는다. 제거로 인해 해당 스펙의 기존 단언이 달라져서는 안 된다.
- **FR-013**: FR-009 의 검사는 새 위반을 통과시키지 않아야 한다(차단). 이번 범위 밖의 기존 위반은 명시적 예외 목록으로 등재해 통과시키되, 목록은 항목별로 사유와 후속 추적 대상을 가져야 하고 새 항목 추가는 예외로 취급된다.
- **FR-014**: 예외 목록에 등재된 항목이 해소되면 목록에서 제거되어야 하며, 목록에 있으나 실제로는 위반이 아닌 항목은 검사가 그 사실을 보고해야 한다.
- **FR-015**: 환경 변수가 대체 값보다 우선하는 설정 항목에 대해, 테스트는 두 경로를 함께 고정해 조건을 만들어야 하고, 고정한 환경 변수는 테스트 종료 시 실행 전 상태로 되돌아가야 한다.

### Key Entities

- **설정 모킹 선언**: 테스트가 "이 모듈 대신 이 값을 쓰라"고 지정하는 대상 모듈과 대체 값의 쌍. 대상 모듈이 소스가 읽는 모듈과 일치해야만 의미가 있다.
- **모킹된 설정 객체**: 테스트가 제공하는 설정 값 집합. 소스가 조회하는 항목을 모두 포함해야 하며, 테스트별로 값을 지정할 수 있어야 한다.
- **실제 전역 설정**: 프로세스 환경에서 읽어온 실 설정. 테스트는 이 값을 읽지도, 바꾸지도 않아야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 대상 두 스펙에서 설정에 의존하는 단언 중, 모킹 값을 바꿔도 결과가 변하지 않는 위양성 단언이 0 건이다.
- **SC-002**: LLM 프로바이더 환경 변수를 미설정·정상값·다른 값 3 가지로 바꿔 실행했을 때, 두 스펙의 통과/실패 결과가 3 회 모두 동일하다.
- **SC-003**: 두 스펙을 반복 실행 및 개별 실행했을 때 결과가 100% 동일하다(순서 의존 0 건).

- **SC-006**: 교정 이후 전체 테스트 스위트가 통과하며, 이번 작업으로 새로 깨진 다른 스펙이 0 건이다.
- **SC-007**: 검사 도입 시점에 저장소 전체 위반은 이번 범위 2건 + 예외 목록 등재분으로 전부 설명되며, 설명되지 않는 위반이 0 건이다. 예외 목록의 모든 항목은 후속 추적 대상을 가진다.
- **SC-008**: 두 스펙 실행 전후로 프로세스 환경 변수 값의 차이가 0 건이며, 대체 값과 환경 변수가 서로 다른 조건을 가리키는 테스트가 0 건이다.
