# Feature Specification: Fix CPU Monitoring Bug and Reduce MCP Process Overhead

**Feature Branch**: `002-fix-mcp-monitoring-overhead`
**Created**: 2026-03-19
**Status**: Draft
**Input**: User description: "MCP 프로세스 배치/모니터링에서 메모리·CPU 경고 과다 발생. DB_PATH·배치 간격·동시 MCP 인스턴스 수 점검 및 개선"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - CPU 경고 오탐이 사라진다 (Priority: P1)

운영자/개발자가 MCP 서버를 시작한 뒤 장시간 실행해도 CPU 관련 성능 경고가 불필요하게 쏟아지지 않는다. 실제 CPU 사용량이 높을 때만 경고가 발생하고, 평상시에는 조용하다.

**Why this priority**: 현재 CPU 계산이 프로세스 시작부터의 누적값을 사용하여 1초 이상 실행된 프로세스에서 항상 100%로 오인해 경고를 발생시킨다. 이것이 "경고가 많이 찍힌다"는 핵심 원인이다.

**Independent Test**: MCP 서버를 5분간 유휴(idle) 상태로 실행 후 로그를 확인한다. CPU 관련 성능 경고가 0건이면 통과.

**Acceptance Scenarios**:

1. **Given** MCP 서버가 방금 시작된 상태, **When** 추가 요청 없이 5분 경과, **Then** CPU 관련 성능 경고 로그가 발생하지 않는다.
2. **Given** MCP 서버가 실행 중, **When** 대량 임베딩 처리 등 CPU 집약 작업 진행, **Then** CPU 경고 로그가 정상 발생한다.
3. **Given** MCP 서버가 30분 이상 실행된 상태, **When** 유휴 상태 유지, **Then** 이전에 없던 CPU 경고가 새로 발생하지 않는다.

---

### User Story 2 - 에디터가 MCP를 사용하는 동안 반응이 빠르다 (Priority: P2)

개발자가 에디터(VS Code, Cursor 등)에서 MCP 도구를 호출할 때, 배경에서 실행되는 배치·헬스체크 폴링이 에디터 응답성에 영향을 주지 않는다.

**Why this priority**: 헬스체크가 30초마다, 작업 큐 폴링이 100ms마다 실행되어 CPU 사이클을 낭비한다. 간격을 늘리면 도구 호출 응답 시간이 개선된다.

**Independent Test**: 헬스체크·폴링 간격을 늘린 뒤 MCP 도구 10회 연속 호출 시 응답 시간이 이전과 동등하거나 개선되면 통과.

**Acceptance Scenarios**:

1. **Given** 조정된 헬스체크 간격 설정, **When** MCP 도구(recall, remember 등)를 연속 호출, **Then** 헬스체크 로그가 도구 응답 중간에 끼어들어 지연을 유발하는 현상이 없다.
2. **Given** 배치 스케줄러가 실행 중, **When** 배치 작업이 없는 대기 상태, **Then** 큐 폴링이 과도하게 빈번하지 않아 유휴 CPU 사용률이 낮다.
3. **Given** MCP 프로세스가 실행 중, **When** 외부 도구로 프로세스 CPU를 관찰, **Then** 유휴 상태 평균 CPU 사용률이 이전 대비 의미 있게 감소한다.

---

### User Story 3 - DB 경로가 MCP 실행 위치와 무관하게 일관된다 (Priority: P3)

운영자가 어느 디렉터리에서 MCP 서버를 실행하더라도 항상 동일한 데이터베이스에 접근한다. 에디터와 CLI 등 여러 MCP 클라이언트가 동일한 영구 메모리를 공유한다.

**Why this priority**: 상대 경로 기본값은 실행 위치마다 다른 DB를 생성해 메모리가 분산된다. 데이터 일관성 문제이므로 P1·P2 이후에 처리한다.

**Independent Test**: 서로 다른 두 디렉터리에서 MCP 서버를 각각 실행하고 동일한 DB 파일을 가리키는지, 한쪽에서 저장한 기억이 다른 쪽에서 조회되는지 확인.

**Acceptance Scenarios**:

1. **Given** `DB_PATH`가 절대 경로로 설정된 상태, **When** 서로 다른 두 디렉터리에서 MCP 서버를 실행, **Then** 두 프로세스가 동일한 DB 파일에 접근한다.
2. **Given** `DB_PATH`가 절대 경로로 설정, **When** 인스턴스 A에서 `remember`로 기억 저장, **Then** 인스턴스 B에서 `recall`로 동일 기억 조회 가능.
3. **Given** 환경 변수 `DB_PATH` 미설정, **When** MCP 서버 시작, **Then** 기본값으로 사용자 홈 디렉터리 하위의 절대 경로가 사용된다.

---

### User Story 4 - 성능 경고 임계값을 상황에 맞게 조정할 수 있다 (Priority: P4)

운영자가 환경 변수를 통해 메모리·CPU 경고 임계값을 조정해, 로컬 개발 환경과 서버 환경에 각각 적합한 민감도를 설정할 수 있다.

**Why this priority**: 하드코딩된 임계값이 소형 로컬 환경에서 오탐을 일으킨다. 설정 가능하게 하면 운영 환경별로 적합한 알림만 받을 수 있다.

**Independent Test**: 환경 변수로 메모리 임계값을 변경한 뒤, 해당 임계값 미만에서 경고 미발생 / 초과 시 경고 발생 여부를 확인.

**Acceptance Scenarios**:

1. **Given** 메모리 경고 임계값을 높게 설정, **When** 실제 메모리 사용이 이전 기본 임계값을 초과하지만 새 임계값 미만, **Then** 경고가 발생하지 않는다.
2. **Given** 메모리 경고 임계값 설정, **When** 실제 메모리 사용이 설정 임계값 초과, **Then** 경고가 발생한다.
3. **Given** 임계값 관련 환경 변수 미설정, **When** MCP 서버 시작, **Then** 정상 운영 범위에서는 경고가 발생하지 않는 적절한 기본값이 적용된다.

---

### Edge Cases

- 실제 CPU가 임계값을 초과할 때(임베딩 배치 실행 중)도 경고가 정상 발생하는가?
- 헬스체크 간격을 늘렸을 때 DB 연결 장애 감지 지연(최대 2분)이 허용 가능한가?
- MCP 인스턴스 여러 개가 같은 SQLite DB에 동시에 쓰기를 시도하면 WAL 락 충돌이 발생하는가?
- `DB_PATH`의 기본 절대 경로 디렉터리가 존재하지 않을 때 자동 생성되며, 생성 실패 시 오류 메시지와 함께 서버 시작이 중단된다.
- CPU delta 계산에서 첫 번째 측정 시(기준점 없음)에는 어떻게 처리하는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 CPU 사용률을 프로세스 시작부터의 누적값이 아닌, 연속된 두 측정 시점 사이의 변화량(delta) 기반으로 계산해야 한다.
- **FR-002**: CPU 사용률 첫 번째 측정(기준점 없음) 시에는 경고를 발생시키지 않거나 0%로 처리해야 한다.
- **FR-003**: 헬스체크 기본 실행 간격은 **5분(300,000ms)**이어야 한다(현재 30초에서 변경).
- **FR-004**: 작업 큐 폴링 기본 간격은 **100ms**로 유지한다. `BATCH_JOB_PROCESSOR_INTERVAL_MS` 환경 변수로 재정의 가능하다(최솟값 100ms). 헬스체크 간격(FR-003)이 주요 CPU 절감원이며, 폴링 간격을 늘리면 재시도·초기 실행 지연 등 정확성 회귀가 발생한다.
- **FR-005**: `DB_PATH` 환경 변수의 기본값은 사용자 홈 디렉터리 하위의 절대 경로이어야 한다.
- **FR-006**: `DB_PATH`가 가리키는 디렉터리가 없을 경우 서버 시작 시 자동으로 생성해야 한다. 디렉터리 생성이 실패할 경우(권한 없음, 디스크 꽉 참 등), 실패 경로와 원인을 포함한 오류 메시지를 출력하고 서버 시작을 즉시 중단해야 한다.
- **FR-007**: 메모리 사용률 경고 임계값은 환경 변수로 설정 가능해야 한다.
- **FR-008**: CPU 사용률 경고 임계값은 환경 변수로 설정 가능해야 한다.
- **FR-009**: 헬스체크 간격과 모니터링 수집 간격은 각각 환경 변수로 재정의 가능해야 한다.
- **FR-010**: 모든 기본값 변경은 환경 변수를 통해 이전 값으로 되돌릴 수 있어야 한다(하위 호환).
- **FR-011**: FR-007~FR-009에 해당하는 환경 변수에 유효하지 않은 값(음수, 0, 숫자 아닌 문자열 등)이 설정된 경우, 어떤 변수에 어떤 값이 입력됐는지를 포함한 경고 로그를 출력하고 해당 항목만 기본값으로 대체하여 서버를 정상 기동해야 한다.

### Key Entities

- **PerformanceMonitor**: CPU 및 메모리 지표를 수집하고 알림을 생성하는 서비스. CPU 측정 시 이전 측정 기준점을 내부적으로 유지해야 한다.
- **BatchScheduler**: 배치 작업 스케줄러. 헬스체크·모니터링·큐 폴링의 기본 간격 설정을 보유한다.
- **AlertThreshold**: 경고 임계값 설정. 환경 변수에서 주입 가능해야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: MCP 서버를 유휴 상태로 10분간 실행했을 때 CPU 관련 성능 경고 로그가 0건이어야 한다.
- **SC-002**: 배치 간격 조정 후 유휴 상태에서 MCP 프로세스의 CPU 사이클 소비가 이전 대비 50% 이상 감소해야 한다.
- **SC-003**: 동일 환경에서 MCP 도구 연속 호출 10회의 평균 응답 시간이 변경 전 대비 동등하거나 개선되어야 한다.
- **SC-004**: 서로 다른 두 디렉터리에서 시작한 MCP 인스턴스가 동일한 DB에서 데이터를 공유하는 것을 단일 테스트로 검증할 수 있어야 한다.
- **SC-005**: 실제 CPU 부하가 높은 상황에서 CPU 경고가 정상적으로 발생해야 한다(오탐 제거가 정탐 제거로 이어지지 않아야 한다).
- **SC-006**: 모든 변경 사항이 기존 유닛 테스트를 통과해야 한다.

## Clarifications

### Session 2026-03-19

- Q: DB 디렉터리 자동 생성 실패 시(권한 없음, 디스크 꽉 참 등) 서버는 어떻게 동작해야 하는가? → A: 실패 경로와 원인을 포함한 오류 메시지를 출력하고 서버 시작을 즉시 중단한다.
- Q: 헬스체크와 작업 큐 폴링의 정확한 기본 간격은 무엇인가? → A: 헬스체크 5분(300,000ms). 폴링은 100ms 유지(1,000ms로 늘리면 재시도·초기 실행 지연 회귀 발생 확인, 코드 리뷰 반영).
- Q: 환경 변수에 유효하지 않은 값(음수, 0, 비숫자 등)이 설정된 경우 어떻게 처리해야 하는가? → A: 경고 로그(변수명·입력값 포함)를 출력하고 해당 항목만 기본값으로 대체하여 서버를 정상 기동한다.

## Assumptions

- CPU 사용률 delta 계산의 기준점은 `collectMetrics()` 직전 호출 시점으로 한다.
- 헬스체크 간격을 2분으로 늘렸을 때 DB 장애 감지 지연(최대 2분)은 허용 가능하다.
- `DB_PATH` 기본 절대 경로는 `~/.memento/memory.db`로 가정한다.
- 여러 MCP 인스턴스의 동일 DB 동시 접근에 대한 WAL 락 처리는 기존 SQLite WAL 설정에 의존한다.
- 메모리 경고 기본 임계값은 85%, CPU 경고 기본 임계값은 75%로 가정한다.

## Out of Scope

- 여러 MCP 인스턴스 간 배치 작업 코디네이션(리더 선출 등)
- HTTP 서버 모드로의 전환 권고
- `metricsHistory` 크기 조정
