## 관계 유형 개요

Memento는 다음 6가지 관계 유형을 지원합니다:

| 관계 유형 | 설명 | 카테고리 |
|---------|------|---------|
| `CAUSES` | 인과 관계 (원인-결과) | Causal |
| `DEPENDS_ON` | 의존 관계 (필수 조건) | Structural |
| `FOLLOWS` | 시간적 순서 (시간적 연속성) | Temporal |
| `CONTRASTS_WITH` | 대조 관계 (반대/대립) | Semantic |
| `REFERENCES` | 참조 관계 (언급/인용) | Semantic |
| `BELONGS_TO` | 포함 관계 (소속/포함) | Structural |

## 관계 유형별 판단 기준

### 1. CAUSES (인과 관계)

**정의**: 한 기억이 다른 기억의 원인이 되는 관계

**판단 기준**:
- 소스 기억이 타겟 기억의 직접적인 원인을 설명하는가?
- "때문에", "로 인해", "결과로", "따라서" 등의 인과 표현이 있는가?
- 시간적 순서가 명확한가? (원인이 결과보다 먼저 발생)

**신뢰도 범위**:
- **높음 (0.8-1.0)**: 명확한 인과 관계, 직접적인 원인-결과
- **중간 (0.6-0.79)**: 간접적인 인과 관계, 추론이 필요한 경우
- **낮음 (0.5-0.59)**: 약한 인과 관계, 다른 해석 가능성

**예시**:
- 높음: "비가 와서" → "우산을 샀다" (0.9)
- 중간: "프로젝트 지연" → "일정 조정" (0.7)
- 낮음: "회의 참석" → "결정 사항 기록" (0.55)

### 2. DEPENDS_ON (의존 관계)

**정의**: 한 기억이 다른 기억에 의존하는 관계 (필수 조건)

**판단 기준**:
- 소스 기억이 타겟 기억 없이는 존재하거나 실행될 수 없는가?
- "필요하다", "의존한다", "기반으로", "전제 조건" 등의 표현이 있는가?
- 기술적 의존성 또는 논리적 의존성이 있는가?

**신뢰도 범위**:
- **높음 (0.8-1.0)**: 필수 의존성, 명확한 전제 조건
- **중간 (0.6-0.79)**: 선택적 의존성, 부분적 필요
- **낮음 (0.5-0.59)**: 약한 의존성, 간접적 연관

**예시**:
- 높음: "데이터베이스 스키마" → "애플리케이션 개발" (0.9)
- 중간: "API 문서" → "클라이언트 구현" (0.7)
- 낮음: "디자인 가이드" → "UI 개발" (0.6)

### 3. FOLLOWS (시간적 순서)

**정의**: 시간적 순서를 따르는 관계 (시간적 연속성)

**판단 기준**:
- 소스 기억이 타겟 기억보다 시간적으로 먼저 발생하는가?
- "이후", "다음에", "그 다음", "연속해서" 등의 시간 표현이 있는가?
- 순차적인 프로세스나 워크플로우의 일부인가?

**신뢰도 범위**:
- **높음 (0.8-1.0)**: 명확한 시간적 순서, 필수 순서
- **중간 (0.6-0.79)**: 일반적인 순서, 유연한 순서
- **낮음 (0.5-0.59)**: 약한 시간적 연관, 동시 발생 가능

**예시**:
- 높음: "요구사항 분석" → "시스템 설계" (0.9)
- 중간: "코드 리뷰" → "병합" (0.75)
- 낮음: "회의 준비" → "회의 참석" (0.6)

### 4. CONTRASTS_WITH (대조 관계)

**정의**: 서로 대조되거나 반대되는 관계

**판단 기준**:
- 두 기억이 서로 반대되는 개념이나 접근 방식을 나타내는가?
- "하지만", "반면에", "대조적으로", "다르게" 등의 대조 표현이 있는가?
- 선택지나 대안을 제시하는가?

**신뢰도 범위**:
- **높음 (0.8-1.0)**: 명확한 대조, 직접적인 반대
- **중간 (0.6-0.79)**: 부분적 대조, 다른 관점
- **낮음 (0.5-0.59)**: 약한 대조, 단순한 차이

**예시**:
- 높음: "마이크로서비스 아키텍처" → "모놀리식 아키텍처" (0.85)
- 중간: "애자일 방법론" → "폭포수 방법론" (0.7)
- 낮음: "React" → "Vue" (0.6)

### 5. REFERENCES (참조 관계)

**정의**: 한 기억이 다른 기억을 참조하거나 언급하는 관계

**판단 기준**:
- 소스 기억이 타겟 기억을 명시적으로 언급하거나 참조하는가?
- "참고", "언급", "인용", "기반으로" 등의 참조 표현이 있는가?
- 문서나 자료를 참조하는가?

**신뢰도 범위**:
- **높음 (0.8-1.0)**: 명시적 참조, 직접 언급
- **중간 (0.6-0.79)**: 간접적 참조, 관련 자료
- **낮음 (0.5-0.59)**: 약한 참조, 일반적 연관

**예시**:
- 높음: "API 문서 참고" → "API 문서" (0.9)
- 중간: "이전 논의 기반" → "이전 회의록" (0.7)
- 낮음: "관련 자료" → "참고 문서" (0.6)

### 6. BELONGS_TO (포함 관계)

**정의**: 한 기억이 다른 기억에 소속되거나 포함되는 관계

**판단 기준**:
- 소스 기억이 타겟 기억의 일부이거나 소속되는가?
- "포함", "소속", "일부", "멤버" 등의 포함 표현이 있는가?
- 계층적 구조나 그룹 관계인가?

**신뢰도 범위**:
- **높음 (0.8-1.0)**: 명확한 포함 관계, 직접 소속
- **중간 (0.6-0.79)**: 부분적 포함, 관련 항목
- **낮음 (0.5-0.59)**: 약한 포함, 간접적 연관

**예시**:
- 높음: "로그인 기능" → "인증 모듈" (0.9)
- 중간: "버그 리포트" → "프로젝트 이슈" (0.75)
- 낮음: "개발 문서" → "프로젝트 문서" (0.6)

## 신뢰도 범위 설정 가이드

### 신뢰도 점수 분류

| 범위 | 의미 | 사용 시나리오 |
|-----|------|-------------|
| **0.9-1.0** | 매우 높음 | 명확하고 확실한 관계, 의심의 여지 없음 |
| **0.8-0.89** | 높음 | 명확한 관계, 높은 확신 |
| **0.7-0.79** | 중간-높음 | 일반적으로 맞는 관계, 약간의 불확실성 |
| **0.6-0.69** | 중간 | 합리적인 관계, 일부 불확실성 |
| **0.5-0.59** | 중간-낮음 | 약한 관계, 상당한 불확실성 |
| **0.0-0.49** | 낮음 | 관계가 의심스러움, 제외 고려 |

### 신뢰도 설정 원칙

1. **보수적 접근**: 불확실한 경우 낮은 신뢰도 할당
2. **명시적 증거 우선**: 명시적 표현이 있으면 높은 신뢰도
3. **맥락 고려**: 전체 맥락을 고려하여 신뢰도 조정
4. **관계 유형별 차이**: 관계 유형에 따라 기본 신뢰도 범위가 다름

### 신뢰도 조정 요소

**신뢰도 증가 요인**:
- 명시적 키워드나 표현 존재
- 시간적/공간적 근접성
- 반복적인 언급
- 전문가 검증

**신뢰도 감소 요인**:
- 추론이 필요한 경우
- 모호한 표현
- 다른 해석 가능성
- 시간적 간격이 큰 경우

## 라벨링 예시

### 예시 1: 프로젝트 관리 시나리오

**메모리 1**: "프로젝트 계획서 작성 완료"
**메모리 2**: "개발 환경 설정 시작"
**관계**: `FOLLOWS`
**신뢰도**: 0.85
**근거**: "완료" 후 "시작"이라는 시간적 순서가 명확함

---

**메모리 1**: "데이터베이스 스키마 설계"
**메모리 2**: "백엔드 API 개발"
**관계**: `DEPENDS_ON`
**신뢰도**: 0.9
**근거**: API 개발은 스키마 설계가 필수 전제 조건

---

**메모리 1**: "프로젝트 일정 지연"
**메모리 2**: "추가 개발자 투입 결정"
**관계**: `CAUSES`
**신뢰도**: 0.8
**근거**: 일정 지연이 추가 인력 투입의 직접적인 원인

### 예시 2: 기술 문서 시나리오

**메모리 1**: "React 컴포넌트 설계 문서"
**메모리 2**: "컴포넌트 구현 가이드"
**관계**: `REFERENCES`
**신뢰도**: 0.75
**근거**: 구현 가이드가 설계 문서를 참조하는 관계

---

**메모리 1**: "마이크로서비스 아키텍처 채택"
**메모리 2**: "모놀리식 아키텍처 검토"
**관계**: `CONTRASTS_WITH`
**신뢰도**: 0.85
**근거**: 두 아키텍처는 서로 대조되는 접근 방식

---

**메모리 1**: "인증 모듈"
**메모리 2**: "로그인 기능"
**관계**: `BELONGS_TO`
**신뢰도**: 0.9
**근거**: 로그인 기능이 인증 모듈에 포함됨

### 예시 3: 회의록 시나리오

**메모리 1**: "요구사항 변경 사항 논의"
**메모리 2**: "요구사항 문서 업데이트"
**관계**: `FOLLOWS`
**신뢰도**: 0.8
**근거**: 논의 후 문서 업데이트라는 시간적 순서

---

**메모리 1**: "성능 테스트 결과"
**메모리 2**: "최적화 작업 계획"
**관계**: `CAUSES`
**신뢰도**: 0.75
**근거**: 테스트 결과가 최적화 계획의 원인

---

**메모리 1**: "API 문서 작성"
**메모리 2**: "프론트엔드 개발"
**관계**: `DEPENDS_ON`
**신뢰도**: 0.7
**근거**: 프론트엔드 개발이 API 문서에 의존 (선택적 의존성)

## 라벨링 체크리스트

라벨링 시 다음 사항을 확인하세요:

### 기본 확인 사항
- [ ] 관계 유형이 적절한가?
- [ ] 신뢰도 점수가 합리적인가?
- [ ] 관계의 방향이 올바른가? (source → target)
- [ ] 자기 자신에 대한 관계는 아닌가?

### 관계 유형별 확인 사항
- [ ] **CAUSES**: 원인-결과 관계가 명확한가?
- [ ] **DEPENDS_ON**: 의존성이 필수적인가?
- [ ] **FOLLOWS**: 시간적 순서가 명확한가?
- [ ] **CONTRASTS_WITH**: 대조 관계가 명확한가?
- [ ] **REFERENCES**: 참조가 명시적인가?
- [ ] **BELONGS_TO**: 포함 관계가 명확한가?

### 신뢰도 확인 사항
- [ ] 명시적 증거가 있으면 0.8 이상
- [ ] 추론이 필요하면 0.6-0.79
- [ ] 모호한 경우 0.5-0.59
- [ ] 관계가 의심스러우면 0.5 미만 또는 제외

### 품질 확인 사항
- [ ] 맥락을 충분히 고려했는가?
- [ ] 다른 해석 가능성을 검토했는가?
- [ ] 일관성 있는 라벨링인가?
- [ ] 문서화된 근거가 있는가?
