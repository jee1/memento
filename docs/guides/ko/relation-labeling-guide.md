# 관계 라벨링 가이드

## 관계 추출의 역할

Memento는 기억을 저장할 때 새 기억과 기존 기억들 사이의 의미적 연결을 자동으로 추출합니다. 이 연결 정보는 검색 랭킹을 높이고, 연관된 기억들을 함께 떠올릴 수 있도록 합니다. 관계 추출에는 규칙 기반 엔진과 LLM 기반 엔진이 병용되며, 추출된 관계에는 유형과 신뢰도 점수가 함께 저장됩니다.

이 가이드는 각 관계 유형이 언제 적용되는지, 신뢰도를 어떻게 판단하는지를 설명합니다.

## 관계 유형

Memento의 공개 타입 시스템은 다음 일곱 가지 관계 유형을 정의합니다. 각 유형은 카테고리로 분류되며, 검색 랭킹에서 서로 다른 가중치를 가집니다. 방향과 레거시 별칭은 [관계 타입 표준](../../reference/ko/relation-type-vocabulary.md)을 따릅니다.

| 유형 | 카테고리 | 의미 | 랭킹 가중치 |
|-----|---------|------|-----------|
| `CAUSES` | Causal | 인과 관계 | 1.2 |
| `DEPENDS_ON` | Structural | 의존 관계 | 1.1 |
| `FOLLOWS` | Temporal | 시간적 순서 | 1.0 |
| `BELONGS_TO` | Structural | 포함 관계 | 1.0 |
| `CONTRASTS_WITH` | Semantic | 대조 관계 | 0.9 |
| `REFERENCES` | Semantic | 참조 관계 | 0.8 |
| `VERSION_OF` | Structural | 새 절차 기억이 이전 절차 기억을 대체 | 1.0 |

`extracted_from`과 `supported_by`는 내부 provenance 에지이며 MCP 입력이나 수동 라벨에 사용하지 않습니다. LLM 기반 추출도 위 공개 유형 또는 내부 provenance 유형만 저장해야 하며 자유 형식 관계 유형을 만들지 않습니다.

## 각 관계 유형의 판단 기준

### CAUSES (인과 관계)

한 기억이 다른 기억의 직접적 원인이 되는 경우에 사용합니다. "때문에", "로 인해", "결과로", "따라서"와 같은 인과 표현이 있을 때, 그리고 원인이 결과보다 시간적으로 먼저 발생했을 때 이 유형이 적합합니다.

예를 들어 "프로젝트 일정 지연"과 "추가 개발자 투입 결정"은 전자가 후자의 직접 원인이 되므로 `CAUSES`로 라벨링됩니다.

### DEPENDS_ON (의존 관계)

한 기억이 다른 기억을 전제 조건으로 필요로 할 때 사용합니다. 소스가 타겟 없이는 존재하거나 실행될 수 없는 관계입니다. 기술적 의존성(라이브러리 의존, 스키마 전제)이나 논리적 의존성(전제 지식, 선행 결정)이 모두 해당합니다.

"데이터베이스 스키마 설계"와 "백엔드 API 개발"의 경우, API 개발은 스키마 없이는 불가능하므로 `DEPENDS_ON`입니다.

### FOLLOWS (시간적 순서)

두 기억이 시간적 순서를 갖는 경우에 사용합니다. 인과 관계와 다르게, FOLLOWS는 단순히 "이전에 일어난 일"과 "이후에 일어난 일"의 순서를 표현합니다. 반드시 원인-결과일 필요는 없습니다. "이후", "다음에", "그 다음", "연속해서" 같은 표현이 지표가 됩니다.

### BELONGS_TO (포함 관계)

한 기억이 다른 기억의 일부이거나 소속된 경우에 사용합니다. 계층 구조나 집합-원소 관계를 나타냅니다. "로그인 기능"이 "인증 모듈"에 속하는 경우가 전형적인 예입니다.

### CONTRASTS_WITH (대조 관계)

두 기억이 서로 반대되거나 대조되는 개념을 표현할 때 사용합니다. "하지만", "반면에", "대조적으로" 같은 표현이 지표입니다. 선택지를 비교하거나 서로 다른 접근 방식을 다루는 기억들 사이에 적합합니다.

### REFERENCES (참조 관계)

한 기억이 다른 기억을 명시적으로 언급하거나 인용하는 경우에 사용합니다. "참고", "언급", "인용", "기반으로"와 같은 표현이 있을 때 적합합니다. 다른 관계 유형에 맞지 않는 느슨한 연관도 여기에 해당합니다.

## 신뢰도 점수

신뢰도(confidence)는 0.0에서 1.0 사이의 값으로, 추출된 관계의 확실성을 나타냅니다.

| 범위 | 의미 |
|-----|------|
| 0.9 - 1.0 | 명확하고 확실한 관계. 의심의 여지 없음 |
| 0.8 - 0.89 | 높은 신뢰도. 명시적 표현 존재 |
| 0.7 - 0.79 | 보통 이상. 대체로 맞지만 약간의 불확실성 |
| 0.6 - 0.69 | 합리적. 일부 추론 필요 |
| 0.5 - 0.59 | 약함. 상당한 불확실성 |
| 0.0 - 0.49 | 관계가 의심스러움. 제외 고려 |

신뢰도를 높이는 요인은 명시적 키워드나 표현의 존재, 시간적·공간적 근접성, 반복적 언급, 전문가 검증 등입니다.

신뢰도를 낮추는 요인은 추론이 필요한 경우, 모호한 표현, 다른 해석 가능성, 시간적 간격이 큰 경우 등입니다.

신뢰도 설정의 기본 원칙은 보수적 접근입니다. 불확실한 경우에는 낮게 설정하고, 명시적 증거가 있을 때만 높게 설정합니다.

## 라벨링 예시

### 프로젝트 관리 시나리오

"프로젝트 계획서 작성 완료"와 "개발 환경 설정 시작" 사이에는 "완료" 후 "시작"이라는 시간적 순서가 명확하므로 `FOLLOWS`(신뢰도 0.85)가 적합합니다.

"프로젝트 일정 지연"과 "추가 개발자 투입 결정"은 전자가 후자의 직접 원인이므로 `CAUSES`(신뢰도 0.8)입니다.

"데이터베이스 스키마 설계"와 "백엔드 API 개발"은 개발이 스키마에 의존하므로 `DEPENDS_ON`(신뢰도 0.9)입니다.

### 기술 문서 시나리오

"마이크로서비스 아키텍처 채택"과 "모놀리식 아키텍처 검토"는 서로 대조되는 접근 방식이므로 `CONTRASTS_WITH`(신뢰도 0.85)입니다.

"React 컴포넌트 설계 문서"와 "컴포넌트 구현 가이드"는 구현 가이드가 설계 문서를 참조하므로 `REFERENCES`(신뢰도 0.75)입니다.

"로그인 기능"과 "인증 모듈"은 전자가 후자에 포함되므로 `BELONGS_TO`(신뢰도 0.9)입니다.

## 라벨링 체크리스트

관계를 할당하기 전에 다음 사항을 확인하면 품질을 높일 수 있습니다.

- 관계의 방향이 올바른가? source에서 target으로 향하는 관계인가.
- 다른 관계 유형으로 더 잘 표현될 여지는 없는가.
- 신뢰도 점수가 실제 확실성을 반영하는가.
- 자기 자신에 대한 관계(동일 기억)는 아닌가.
- 명시적 증거가 없이 높은 신뢰도를 부여하지 않는가.
