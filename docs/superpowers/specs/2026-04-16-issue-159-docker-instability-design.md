# 설계: 이슈 #159 — Docker Desktop 불안정 원인 규명 및 진단 모드

**상태**: 브레인스토밍 확정 (구현 전)  
**날짜**: 2026-04-16  
**이슈**: [GitHub #159](https://github.com/jee1/memento/issues/159) — Docker 실행 중 daemon/Desktop 다운 가능성

---

## 1. 배경·문제 정의

사용자 보고에 따르면 `memento`를 Docker로 띄워 둔 뒤 일정 시간이 지나면 **컨테이너 단위가 아니라 Docker Desktop 자체가 죽어서** 상태 확인이 어려운 상황이 반복된다.

현재 저장소에는 다음 요소가 이미 존재한다.

- `docker-compose.base.yml`의 `json-file` 로그 로테이션 설정
- `${HOME}/.memento/logs:/app/logs` 호스트 마운트
- 서버 부팅 시 자동 시작되는 상주성 서브시스템
  - `BatchScheduler`
  - `WalCheckpointScheduler`
  - `DatabaseLockMonitor`

추가로 사용자 관찰상:

- 재현은 **idle 상태에서도 발생**
- 마운트된 DB는 **작은 편**
- 목표는 단순 완화가 아니라 **정확한 원인 규명 후 수정**

따라서 이 이슈의 1차 목표는 구조 변경이 아니라, **Docker Desktop이 죽기 직전 Memento와 Docker 양쪽에서 무슨 일이 일어나는지 재현 가능하게 관측하는 진단 체계**를 만드는 것이다.

---

## 2. 목표·비목표

### 2.1 목표

- Docker Desktop 불안정의 원인을 **증거 기반으로 좁힐 수 있는 진단 모드**를 제공한다.
- 앱 내부 상태와 Docker 외부 상태를 **서로 다른 로그 채널**로 남겨 상호 검증 가능하게 한다.
- 상주성 서브시스템을 **독립 플래그로 차단**할 수 있게 하여 원인 범위를 실험적으로 줄인다.
- 진단 기능은 **운영 환경에서도 필요 시 켤 수 있는 정식 기능**으로 설계한다.

### 2.2 비목표

- 이번 단계에서 곧바로 배치/서버 분리를 강제하지 않는다.
- Docker Desktop 고유 버그를 코드 레벨에서 “해결”한다고 가정하지 않는다.
- 진단 결과가 나오기 전까지 원인을 특정 구현 결함으로 단정하지 않는다.

---

## 3. 원인 가설

현재 설계가 겨냥하는 가설은 다음 네 가지다.

1. **상주성 서브시스템의 메모리 누적 또는 순간 급증**
   - `BatchScheduler`가 부팅 시 여러 작업을 즉시 큐에 올림
   - `WalCheckpointScheduler`, `DatabaseLockMonitor`가 별도 루프로 동작

2. **예외 후 재시작 루프**
   - 백그라운드 작업 또는 서버 예외로 컨테이너가 반복 재시작
   - Docker Desktop 자원이 로그/메타데이터/프로세스 재생성으로 잠식됨

3. **Docker 엔진 내부 리소스 문제**
   - stdout/stderr 로그, 컨테이너 로그 파일, Desktop VM 디스크/메모리 문제

4. **네이티브/런타임 계층 문제**
   - Node 프로세스 자체가 아니라 `better-sqlite3`, `sqlite-vec`, 추론 계층 등 native 메모리 사용이 비정상적일 가능성

진단 설계는 위 가설을 **한 번의 재현 실험으로 모두 판별하려 하지 않고**, 관측 로그와 기능 차단 실험을 조합해 범위를 단계적으로 줄이는 데 초점을 둔다.

---

## 4. 설계 개요

### 4.1 이중 관측

진단 체계는 두 레이어로 구성한다.

- **앱 내부 진단 로그**
  - Memento 프로세스가 주기 샘플과 이벤트 로그를 `/app/logs/diagnostics/`에 JSONL로 기록
  - 호스트의 `${HOME}/.memento/logs`에 남으므로 Docker Desktop 장애 후에도 회수 가능

- **Docker 외부 관측 로그**
  - 호스트 측 스크립트 또는 문서화된 명령으로 `docker stats`, `docker inspect`, `docker system df`, 컨테이너 로그 파일 크기 등을 별도 파일로 수집
  - 앱이 죽기 전 상태와 Docker 엔진 상태를 분리해 해석 가능

### 4.2 기능 차단 플래그

원인 범위 축소를 위해 상주성 서브시스템을 독립적으로 끌 수 있어야 한다.

- `BatchScheduler`
- `WalCheckpointScheduler`
- `DatabaseLockMonitor`

필요 시 배치 내부 세부 기능(triple extraction batch, sleep consolidation, introspection 등)은 2차 진단 단계에서 추가 분리한다. 1차 구현에서는 **최상위 서브시스템 단위** 분리가 우선이다.

### 4.3 운영 친화성

진단 기능은 기본적으로 꺼져 있어야 하며, 활성화 시에도 서버 기능을 깨뜨리지 않아야 한다. 즉:

- 진단 실패가 서버 실패로 이어지지 않아야 함
- 로그 크기 상한 또는 순환 정책 필요
- 출력 형식은 사람이 읽을 수 있으면서 스크립트 파싱 가능한 JSONL

## 5. 구성 요소

### 5.1 진단 설정

초기 범위에서 다음 환경변수 세트를 둔다.

- `DIAGNOSTICS_ENABLED`
- `DIAGNOSTICS_INTERVAL_MS`
- `DIAGNOSTICS_LOG_DIR`

기본값은 다음 원칙을 따른다.

- 진단은 기본 `false`
- 로그 디렉토리는 기본 `/app/logs/diagnostics`
- 샘플 주기는 운영 부담이 과하지 않은 수준(예: 10초~30초)으로 시작

### 5.2 기능 차단 플래그

초기 범위에서 다음 환경변수 세트를 둔다.

- `BATCH_SCHEDULER_ENABLED`
- `WAL_CHECKPOINT_ENABLED`
- `DB_LOCK_MONITOR_ENABLED`

기본값은 모두 `true`로 하여 기존 동작을 유지한다. 진단 시에만 조합을 바꿔 실험한다.

### 5.3 앱 내부 진단 로거

역할:

- 주기 샘플 기록
- 이벤트 로그 기록
- 파일 크기 관리
- 서버 주 기능과 실패 격리

출력 파일 예:

- `app-runtime.jsonl` — 주기 샘플
- `app-events.jsonl` — 시작/종료/job 시작/job 종료/예외 등 이벤트

### 5.4 Docker 외부 관측 스크립트/가이드

역할:

- 컨테이너 메모리/CPU 추세 수집
- 재시작 여부 확인
- Docker 엔진 디스크 사용량 수집
- 컨테이너 로그 파일 크기 추적

형태는 코드 스크립트일 수도 있고, 최소한 운영 가이드 문서로도 제공해야 한다. 구현 단계에서는 저장소의 스크립트 스타일에 맞춰 결정한다.

## 6. 기록할 데이터

### 6.1 앱 내부 주기 샘플

`app-runtime.jsonl`에는 다음 필드를 남긴다.

- timestamp
- pid
- `process.uptime()`
- `process.memoryUsage()`
  - `rss`
  - `heapTotal`
  - `heapUsed`
  - `external`
  - `arrayBuffers`
- active handles 수
- active requests 수
- 배치 스케줄러 상태
  - `isRunning`
  - `activeJobs`
  - `queueSize`
  - 최근 실행 job 메타(가능한 범위)
- WAL 체크포인트 스케줄러 활성 여부
- DB lock monitor 활성 여부

핵심은 “메모리 수치”와 “당시 어떤 서브시스템이 살아 있었는지”를 같은 타임라인에 남기는 것이다.

### 6.2 앱 내부 이벤트 로그

`app-events.jsonl`에는 다음 이벤트를 남긴다.

- 서버 시작/종료
- 각 상주성 서브시스템 시작/종료
- 배치 job 시작/종료
- 배치 job 실패
- `uncaughtException`, `unhandledRejection`
- 종료 신호 수신

이벤트 로그는 재현 시점의 급격한 변화와 마지막 상태를 해석하는 데 사용한다.

### 6.3 Docker 외부 관측

호스트 관측 로그에는 다음을 남긴다.

- `docker stats` 기반 컨테이너 메모리/CPU
- `docker inspect` 기반 상태/재시작 횟수/헬스 상태
- `docker system df`
- `docker inspect <container> --format '{{.LogPath}}'`의 대상 파일 크기

이 데이터는 “앱이 메모리를 먹었는지”와 “Docker 엔진이 리소스를 잃었는지”를 분리하는 데 필요하다.

## 7. 실험 설계

재현 실험은 다음 순서로 수행한다.

1. **기준선**
   - 모든 기능 활성화
   - 진단 로그만 활성화

2. **배치 차단**
   - `BATCH_SCHEDULER_ENABLED=false`

3. **DB 모니터 차단**
   - `WAL_CHECKPOINT_ENABLED=false`
   - `DB_LOCK_MONITOR_ENABLED=false`

4. **상주 기능 전부 차단**
   - 위 세 플래그 모두 `false`

각 실험에서 동일하게 확인할 항목:

- Docker Desktop 다운 발생 여부
- 컨테이너 RSS 추세
- 재시작 횟수 증가 여부
- Docker 로그 파일 증가 속도
- 마지막 이벤트 / 마지막 실행 job

이 설계의 핵심은 **원인 규명 전에 구조 변경을 하지 않는 것**이다. 먼저 어느 서브시스템 조합에서 Desktop 다운이 멈추는지 확인한 뒤, 그 범위 안에서만 상세 수정이나 프로세스 분리를 검토한다.

---

## 8. 오류 처리와 안전장치

- 진단 로그 쓰기 실패는 절대로 프로세스를 죽이면 안 된다.
- 진단 로그는 자체 크기 제한 또는 순환 정책이 있어야 한다.
- 진단 모드가 꺼져 있을 때는 성능 오버헤드가 거의 없어야 한다.
- 기능 차단 플래그는 **시작 시점**에만 평가해 런타임 상태를 단순하게 유지한다.
- 기존 서버/도구 기능의 공개 계약(MCP/HTTP)은 변경하지 않는다.

## 9. 테스트 전략

### 9.1 단위 테스트

- 진단 설정 파싱
- 진단 로그 JSONL 포맷
- 진단 로거 실패 격리
- 기능 차단 플래그에 따른 start 경로 분기

### 9.2 통합 테스트

- `BATCH_SCHEDULER_ENABLED=false`일 때 스케줄러 시작이 생략되는지
- `WAL_CHECKPOINT_ENABLED=false`일 때 체크포인트 스케줄러 시작이 생략되는지
- `DB_LOCK_MONITOR_ENABLED=false`일 때 락 모니터 시작이 생략되는지
- 진단 모드 활성화 시 로그 파일이 생성되는지

### 9.3 수동 검증

- 작은 DB 기준 Docker 재현 실험
- 4개 프로파일별 안정성 비교
- 장애 발생 후 로그 회수 가능성 확인

## 10. 후속 의사결정 기준

진단 결과에 따라 후속 조치는 다음처럼 나뉜다.

- **배치 계열이 원인**: 배치 내부 상세 계측 추가 후, 필요 시 서버/워커 분리 검토
- **WAL/락 모니터 계열이 원인**: 해당 루프의 메모리/핸들 사용 패턴 수정
- **재시작 루프가 원인**: 예외 경로와 재시작 정책 수정
- **Docker 엔진/로그 계열이 원인**: compose/운영 가이드 조정
- **상주 기능을 모두 꺼도 재현**: 앱 바깥 요인 또는 Desktop 환경 문제로 별도 분기

즉, **프로세스 분리는 이번 설계의 기본 해법이 아니라, 진단 결과가 특정 방향을 가리킬 때 선택하는 후속 옵션**이다.

## 11. 구현 순서

구체 작업 분해는 후속 `writing-plans` 단계에서 작성한다. 본 문서의 구현 순서는 다음 원칙만 고정한다.

1. 진단 설정과 로그 경로 계약 정의
2. 앱 내부 진단 로거 추가
3. 상주성 서브시스템 차단 플래그 추가
4. Docker 외부 관측 스크립트 또는 운영 가이드 추가
5. 테스트 작성
6. 수동 재현 절차 문서화
