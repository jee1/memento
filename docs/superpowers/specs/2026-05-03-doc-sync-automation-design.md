# 설계: 문서·코드 동기화 전수 검수 및 자동화 (워크트리 격리)

**상태**: 브레인스토밍 확정 후 스펙화 (구현 계획은 별도 `plans` 문서)  
**날짜**: 2026-05-03  
**관련**: [docs/README.md](../../README.md), [AGENTS.md](../../../AGENTS.md), 저장소 루트 및 `docs/` 마크다운 전반

---

## 1. 목적

저장소의 마크다운 문서가 실제 코드·기능·운영 절차와 어긋나는 문제를 **체계적으로 줄이기** 위해, (1) 검수 범위와 문서 유형별 처리 원칙을 정하고, (2) **다른 기능 개발과 격리된 git worktree**에서 문서 작업을 수행하며, (3) **재발 방지용 자동화(CI 기계 검증 중심)** 를 단계적으로 도입한다. “전수”는 파일 범위를 넓히되, **의미 동치 검증을 CI 필수로 강제하지는 않는다**(비용·불안정성).

---

## 2. 배경

- `docs/README.md` 기준으로 공식 문서(`guides/`, `api/`, `architecture/`, `operations/` 등), 루트 가이드(`AGENTS.md` 등), 패키지 README, `docs/superpowers/` 하위 스펙·플랜이 공존한다.
- `graphify-out/` 및 일부 패키지 하위 `graphify-out/` 등은 **코드 변경 후 재생성되는 산출물**로, 본문을 수동으로 고치면 다음 재생성 시 되돌아가거나 진실 공급원이 분열된다.
- 문서 전용 브랜치·PR을 메인 워크트리와 분리하면 리뷰 단위가 명확해지고, 기능 브랜치와의 충돌이 줄어든다.

---

## 3. 합의된 범위·원칙

### 3.1 검수 파일 범위 (브레인스토밍 선택 D)

- 저장소에 포함된 **거의 모든 `.md`** 를 “목록에 올려 검토”한다.
- 예외는 **명시적으로만** 둔다(예: 벤더·서드파티 복사본, 명백히 외부 스냅샷만 있는 경로). 예외 목록은 구현 계획 단계에서 `plans`에 후보를 적고 PR에서 확정한다.

### 3.2 문서 유형별 진실 공급원(SSOT)

| 유형 | 정의 | 불일치 시 조치 |
|------|------|----------------|
| **사람 유지 문서** | 의도적으로 편집하는 마크다운: 루트 `README*`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `DEVELOPMENT_RULES.md`, `CONTRIBUTING.md`, `CHANGELOG.md`(정책에 따라), `docs/` 하 공식 문서, 패키지 README, `docs/superpowers/specs|plans` 등 | 문서 또는 코드 중 **계약이 맞는 쪽**을 기준으로 수정; 필요 시 이슈로 쪼갬 |
| **생성·파생 문서** | 스크립트·도구 출력: 예) 루트 `graphify-out/`, `packages/memento-core/graphify-out/` 등(경로는 저장소 기준으로 유지보수) | **해당 `.md` 직접 수정 최소화**; 생성 파이프라인 재실행, 템플릿·소스·설정 수정. 잘못된 서술은 **상류 이슈**로 기록 |

브레인스토밍에서 합의한 **추천안(A)** : 생성물은 재생성·파이프라인 우선. 다만 출력이 명백히 잘못된 경우 **파일만 덮어쓰지 말고** 원인(스크립트·입력)을 고친 뒤 재생성한다.

## 4. 접근 비교 및 채택

| 안 | 내용 | 채택 |
|----|------|------|
| 1 | 워크트리에서 수동 검수·체크리스트만 | 기본 작업 방식의 일부로 포함 |
| 2 | 1 + CI 기계 검증(링크, 린트, 문서 내 명령·스크립트명 존재 등) | **채택(기본)** |
| 3 | 2 + 주기적 LLM/에이전트 감사 리포트 | **선택**: 비용·품질 변동 있음, 릴리스 전·대규모 변경 후 등에 한함 |

---

## 5. 워크트리·브랜치 워크플로

1. 기준 브랜치(예: `main` 또는 팀이 정한 최신 통합 브랜치)에서 **별도 디렉터리**에 worktree 추가:  
   `git worktree add ../memento-docs-audit <기준브랜치>`
2. 해당 디렉터리에서만 브랜치 생성: 예 `docs/audit-2026-05-03` 또는 `docs/sync-<주제>`.
3. 문서 수정·생성물 재실행·커밋·푸시·PR을 **이 워크트리에서만** 진행해, 일상 기능 개발 워크트리와 충돌하지 않게 한다.
4. PR 본문에 **검수 범위**(섹션 3), **생성 명령 실행 여부**, **기계 검증 결과**를 요약한다.

---

## 6. 자동화 층 (채택 안 2)

다음은 **구현 계획(`plans`)에서 구체 스크립트·CI job 이름으로 세분화**한다.

- **링크 무결성**: 내부 앵커·상대 경로·HTTP 링크(정책에 따라 외부는 선택) 검사.
- **마크다운 품질**: 기존 린트 체인과 통합하거나, 문서 전용 규칙을 추가.
- **기계적 일치(저비용)**: 예) 문서에 등장하는 `npm run <script>` 가 루트 또는 워크스페이스 `package.json`에 존재하는지(오탐 가능성을 문서에 명시).
- **의미·API 설명 vs 코드 일치**: CI **필수 게이트로 강제하지 않음**. 사람 검수 또는 선택적 안 3.

생성 경로(`graphify-out/` 등)는 CI에서 “**수정 금지** 또는 **재생성 후 diff 없음**” 같은 정책을 둘지는 구현 단계에서 팀 합의로 정한다(저장소가 이미 생성물을 커밋하는 경우, 재생성 스텝을 PR에 포함하는 방식이 일반적이다).

---

## 7. 수동 검수 순서·완료 기준

### 7.1 권장 순서

1. 진입점·포털: 루트 `README`, `docs/README.md`
2. 에이전트·개발 규약: `AGENTS.md`, `DEVELOPMENT_RULES.md`, `CONTRIBUTING.md`
3. 사용자·연동: `docs/guides/`, `docs/api/`
4. 아키텍처·운영: `docs/architecture/`, `docs/operations/`
5. 패키지 README(`packages/*/README.md`)
6. `docs/superpowers/` 스펙·플랜(과거 결정 기록; 제품 문서와 충돌 시 제품 문서 우선)
7. 생성물: 해당 디렉터리에 대해 **재생성 명령 실행** 후 diff 검토(수동 편집 최소화)

### 7.2 완료 기준(한 번의 “전수 검수” 사이클)

- 사람 유지 문서에 대해 체크리스트 항목을 처리했거나 “의도적 보류”를 이슈로 남겼다.
- 채택한 기계 검증이 PR에서 통과한다(구현 후).
- 생성 경로는 재생성 결과만 반영하거나, 보류 사유를 명시한다.

---

## 8. 오류 처리·거버넌스

- 문서와 코드가 모순될 때: **사용자 대면 동작**을 우선하는 문서(`guides`, `api-reference`)는 빠르게 수정; 내부 스펙은 링크·상위 문서에 “대체 진실”을 표기.
- 생성물 오류: 이슈 제목에 `graphify:` 등 접두를 붙여 상류 수정을 추적.
- 대규모 삭제·이동은 별도 PR로 분리해 리뷰 부담을 줄인다.

---

## 9. 테스트·검증

- 본 설계 자체는 제품 코드 테스트를 추가하지 않는다.
- 구현 단계에서 추가되는 CI·스크립트는 **로컬 재현 명령**과 **실패 시 의미**(무엇을 고쳐야 하는지)를 `plans` 또는 `docs/operations/`에 한 줄 이상 적는다.

---

## 10. 범위 밖

- 비마크다운 문서(예: 순수 HTML 대시보드, JSDoc 전부)의 전수 동기화는 본 스펙에 포함하지 않는다(필요 시 별도 설계).
- 모든 문장을 LLM이 다시 쓰는 **전면 자동 재작성**은 포함하지 않는다(품질·라이선스·검토 부담).
