# 설계: 이슈 #78 — Triple 추출 파이프라인 고도화 (kg-gen 레퍼런스)

**상태**: 브레인스토밍 확정 (구현 전)  
**날짜**: 2026-04-15  
**이슈**: [GitHub #78](https://github.com/jee1/memento/issues/78) — kg-gen 유사 기능 보강 (청킹 / 클러스터링 / 대화 입력 / 그래프 병합)

---

## 1. 배경·목표

Memento는 LLM 기반 triple 추출과 관계 그래프가 이미 있으나, **대화형 입력**, **긴 텍스트**, **중복·유사 관계 통합**, **추출 결과 병합**이 충분히 정의되지 않아 긴 입력에서 품질 저하와 그래프 중복이 발생할 수 있다.

**목표**: [kg-gen](https://github.com/stair-lab/kg-gen/)의 장점을 참고하여, 기존 Memori 계열 기반 위에서 triple 추출·KG 파이프라인을 고도화한다.

---

## 2. 범위 결정

### 2.1 Memori 체인과의 관계 (선택 B)

내부 우선순위 문서에 따라 이슈 #78은 **단독 증분**이 아니라 **이미 병합된 Memori 기반**(`process_id` / `session_id`, 비동기 보강, `kg_triple`·dedupe) 위의 **고도화 레이어**로 설계한다. 관련 GitHub 이슈 **#87·#89·#90은 저장소 기준으로는 완료(CLOSED)**이며, 스키마에 attribution·`kg_triple` 등이 반영되어 있다.

### 2.2 입력 채널 (선택 M)

**1차 범위에 MCP로 노출**한다. 동일 계약을 **HTTP admin**에 두는 것은 권장(에이전트·스크립트 재사용)이나 필수는 아니다.

### 2.3 포함

- `messages[]`(role/content) 또는 단일 본문으로부터 triple 추출로 이어지는 **입력 정규화**
- 긴 텍스트 **청킹**, chunk별 추출, **결과 병합** 규칙
- 엔티티·관계 **클러스터링** 및 **그래프 병합**, 기존 **dedupe·배치 저장 규칙**과의 정합
- `visualize_relations` 등에 **내보내기 포맷 확장**(예: dot, html/graphviz 호환 문자열)
- `process_id` / `session_id`를 MCP 파라미터로 **선택 입력**해 저장 시 귀속

### 2.4 제외·후속

- kg-gen과의 **알고리즘 1:1 재현**은 요구하지 않는다 (레퍼런스 수준).
- **스키마 대개편** 또는 완전히 새로운 그래프 저장 엔진은 별 PR로 분리한다.
- 대시보드 **UI 대규모 개편**은 범위 밖이며, 시각화는 **툴 출력·포맷** 확장 수준으로 한정한다.

---

## 3. 아키텍처·컴포넌트

### 3.1 기존 코드와의 역할 분리

- `extract_relations`는 **기존 `memory_id` 중심**의 관계 추출 경로로 유지한다.
- 이슈 #78의 대화·청킹·triple·KG 병합은 **`TripleExtractionService`**, 배치 잡, `kg_triple` 저장과 연계되는 **triple 파이프라인**에서 다룬다.

### 3.2 제안 레이어

1. **입력 정규화**: `messages[]` → 추출용 텍스트(또는 롤을 유지한 프롬프트 블록).
2. **청킹·병합**: 길이·토큰 예산 기준 분할 → chunk별 추출 → 충돌·중복 완화를 위한 병합(순서, S/P/O 정규화 등). 배치의 chunk·락·재시도 패턴과 정책을 맞춘다.
3. **클러스터링·그래프 병합**: 문자열 단위 중복 외에 임베딩 또는 규칙 기반으로 후보를 묶고, 기존 dedupe·`RelationGraph` / `addRelationsBatch` 계열 규칙으로 수렴한다.

### 3.3 데이터 흐름

`MCP(params)` → 정규화 → [청킹] → `TripleExtractionService` → 병합 → 클러스터링·dedupe → `kg_triple`(및 필요 시 `memory_relation`) → 응답 + 선택적 시각화.

---

## 4. MCP 표면

- **`remember`에 과도한 옵션을 몰아넣기보다**, triple 파이프라인 **전용 도구 하나**를 두는 것을 권장한다 (실제 이름은 구현 단계에서 기존 네이밍과 충돌 여부를 검토한다).
- 스키마 방향:
  - `content` **또는** `messages[]` 중 하나 필수(상호 배타).
  - `chunk_size`, `chunk_overlap`, `merge_strategy` 등 옵션.
  - `process_id`, `session_id`, `persist`(저장 여부) 등.
- **`visualize_relations`**: `format` enum에 dot·html 등 **추가 값**으로 이슈의 시각화 확장을 충족한다.

---

## 5. 오류 처리·한도·관측

### 5.1 오류

- 스키마 위반(동시에 `content`와 `messages`, 빈 `messages` 등)은 **조기 거절**·명확한 오류 코드.
- chunk 단위 **부분 성공**: 성공 chunk는 반환·저장(옵션), 실패 chunk는 인덱스·사유 보고.
- LLM 실패·타임아웃은 기존 triple 경로와 동일 수준의 **재시도·실패 분류**를 따른다.
- 저장 충돌은 **문서화된 규칙**(예: 신뢰도·최신성)으로 해소한다.

### 5.2 한도·안전

- MCP 요청 크기·메시지 개수·총 문자·chunk 상한을 둔다.
- LLM 호출·chunk 수 상한으로 비용·지연을 제한한다.
- 대화 로그 입력 시 기존 **마스킹·로깅 정책**을 적용한다.

### 5.3 관측

- 구조화 로그: 요청 단위 ID, chunk 수, 성공·실패 수, 지연, attribution 유무.
- 텔레메트리는 기존 이벤트 패턴에 **도구명·결과 요약** 수준을 추가한다(본문 전체 저장은 하지 않는다).

## 6. 테스트 전략

- **단위**: 정규화, 청킹 경계, 병합, 클러스터링(또는 mock 임베딩).
- **통합**: 새 MCP 도구의 성공·부분 실패·스키마 오류.
- **회귀**: 기존 `extract_relations` 및 배치 triple 경로 동작 유지.
