# 설계: 이슈 #161 — HTTP 서버 신뢰 경계 정비

**상태**: 브레인스토밍 확정 (구현 전)  
**날짜**: 2026-04-18  
**이슈**: [GitHub #161](https://github.com/jee1/memento/issues/161) — security: HTTP 서버 신뢰 경계(대시보드 비밀 전달·도구/MCP 인증)

## 1. 배경

현재 HTTP 서버는 다음과 같은 보안 불일치를 갖고 있다.

- 브라우저 대시보드가 동작하도록 `ADMIN_API_KEY`를 클라이언트 실행 환경에 전달하는 경로가 있다.
- `/admin`·`/api`는 `ADMIN_API_KEY` 미들웨어 뒤에 있지만, `/tools`와 루트 MCP 라우터는 같은 인증 체인에 포함되지 않는다.
- 문서와 startup warning은 관리 경로가 보호된다는 인상을 주지만, 실제 도구/MCP 경로의 신뢰 경계는 별도다.

이 상태는 브라우저에 비밀을 내려주는 문제와, 운영자가 “키를 설정했으니 HTTP 관리 표면 전체가 보호된다”고 오해할 수 있는 문제를 동시에 만든다.

## 2. 목표

- 브라우저 대시보드로 `ADMIN_API_KEY`를 직접 전달하지 않는다.
- `/admin`·`/api`와 `/tools`·`/mcp`의 인증 경계를 명시적으로 분리하고, 코드·문서·경고 메시지를 일치시킨다.
- 기본 운영 모델은 안전한 로컬 루프백을 유지하되, 명시적 설정 시 원격 운영도 가능하게 한다.
- 기존 MCP/도구 클라이언트 계약은 가능한 한 유지하면서, 무인증 호출 가능 영역을 제거한다.

## 3. 비목표

- 사용자 계정 체계, 역할 기반 권한, OAuth, 외부 IdP 연동은 이번 범위에 포함하지 않는다.
- 다중 테넌트 소유권 검증(`owner_id`, `agent_id`) 전면 재설계는 후속 이슈로 둔다.
- 분산 세션, DB 영속 세션 저장소, 다중 인스턴스 세션 공유는 1차 범위에 포함하지 않는다.
- `/health` 축소, rate limiting, quota, timing-safe compare는 후속 하드닝 후보로 분류하되 핵심 deliverable은 아니다.

## 4. 접근안 비교

### 4.1 전면 통합 인증

- 브라우저, `/admin`, `/api`, `/tools`, `/mcp`를 하나의 세션 또는 통합 인증 계층으로 묶는다.

장점:

- 규칙이 가장 단순하다.
- 운영 문서가 한 문장으로 설명된다.

단점:

- MCP 클라이언트가 쿠키/세션 모델을 전제로 하지 않아 호환성 리스크가 크다.
- 구현 범위가 가장 크다.

### 4.2 이중 경계 분리 (권장)

- 브라우저 대시보드는 세션 인증을 사용한다.
- `/tools`와 `/mcp`는 명시적 헤더 인증을 유지한다.

장점:

- 브라우저 비밀 노출을 제거한다.
- MCP/도구 클라이언트 계약을 크게 깨지 않는다.
- 이슈 161의 범주 A, B를 가장 직접적으로 해결한다.

단점:

- 인증 방식이 두 가지라 문서와 테스트를 더 엄격히 맞춰야 한다.

### 4.3 원격 축소 모델

- 브라우저와 관리 API만 원격 지원하고, `/tools`와 `/mcp`는 루프백에서만 허용한다.

장점:

- 공격면이 가장 작다.

단점:

- 혼합 운영 모델과 충돌할 수 있다.
- 원격 자동화 사용성이 크게 떨어진다.

## 5. 결정

권장안인 **이중 경계 분리**를 채택한다.

- 브라우저 대시보드는 `ADMIN_API_KEY`를 서버 세션으로 교환해 사용한다.
- `/admin`과 `/api`는 브라우저 세션 쿠키를 신뢰한다.
- `/tools`와 `/mcp`는 세션 쿠키를 신뢰하지 않고, 명시적 API 인증 헤더만 신뢰한다.
- 운영 문서와 startup warning은 이 이원화된 신뢰 모델을 기준으로 재작성한다.

## 6. 아키텍처

### 6.1 브라우저 경계

- `GET /dashboard`와 정적 자산은 기존처럼 제공할 수 있다.
- 브라우저가 민감한 관리 데이터를 읽거나 조작하는 실제 경로는 `/admin/*`, `/api/*`로 한정한다.
- 브라우저는 더 이상 `memento-admin-config.js` 같은 스크립트로 관리 비밀을 받지 않는다.
- 브라우저는 로그인 시 명시적으로 관리 키를 제출하고, 이후에는 서버가 발급한 세션 쿠키를 사용한다.

### 6.2 프로그램적 경계

- `/tools/*`와 루트 MCP 라우터(`/mcp`, `/messages`, SSE 관련 엔드포인트)는 브라우저 세션을 인증 근거로 인정하지 않는다.
- 해당 경로는 `Authorization: Bearer <key>` 또는 `X-API-Key: <key>` 같은 명시적 헤더 인증만 허용한다.
- 브라우저가 쿠키만 들고 `/tools` 또는 `/mcp`를 호출하는 경우는 의도적으로 `401`을 반환한다.

### 6.3 혼합 운영 모델

- 루프백 바인딩은 기본 안전 경로로 유지한다.
- 비루프백 바인딩은 명시적 설정이 있을 때만 허용한다.
- 원격 운영을 열더라도 브라우저 경계와 프로그램적 경계의 인증 방식은 섞지 않는다.

## 7. 라우트 및 인증 흐름

### 7.1 세션 생성

- 새 인증 엔드포인트 `POST /auth/session`을 추가한다.
- 이 엔드포인트는 요청 본문이나 쿼리스트링으로 키를 받지 않는다.
- `Authorization: Bearer <key>` 또는 `X-API-Key` 헤더만 허용한다.
- 검증 성공 시 서버는 세션 쿠키를 발급한다.

### 7.2 세션 종료

- `DELETE /auth/session`을 추가한다.
- 세션 저장소에서 세션을 삭제하고, 브라우저 쿠키를 무효화한다.

### 7.3 브라우저 인증 미들웨어

- `/admin/*`, `/api/*`는 세션 검증 미들웨어 뒤에 둔다.
- 유효한 세션이 없거나 만료된 경우 `401`을 반환한다.
- 브라우저용 오류 메시지는 “세션이 없거나 만료됨”처럼 의미가 분명해야 한다.

### 7.4 프로그램적 인증 미들웨어

- `/tools/*`와 `/mcp` 계열 경로에 별도 미들웨어를 둔다.
- 이 미들웨어는 세션 쿠키를 무시하고, 명시적 헤더 인증만 검증한다.
- 키가 없거나 틀린 경우 `401`을 반환한다.
- 오류 메시지는 “도구/MCP 경로는 명시적 API 인증 필요”로 분명하게 구분한다.

### 7.5 기존 `ADMIN_API_KEY`의 역할

- 1차 범위에서는 세션 생성과 프로그램적 헤더 인증 모두 동일한 `ADMIN_API_KEY`를 사용한다.
- 내부 구현은 “브라우저 세션 발급 검증”과 “프로그램적 호출 검증”을 분리한다.
- 이후 토큰 종류를 분리하더라도 라우터 계약이 최소한만 흔들리게 한다.

## 8. 세션 모델

### 8.1 저장 위치

- 1차 구현에서는 서버 메모리 저장소를 사용한다.
- 현재 HTTP 서버가 단일 프로세스 전제를 강하게 가지므로 가장 작은 변경으로 구현할 수 있다.

### 8.2 세션 데이터

- 세션에는 최소한 다음 필드만 저장한다.
- `sessionId`
- `createdAt`
- `lastSeenAt`
- `expiresAt`

관리 키 원문이나 추가 식별 정보는 저장하지 않는다.

### 8.3 세션 만료

- `15분 idle timeout`
- `8시간 absolute timeout`

두 조건 중 하나라도 만족하면 세션은 만료된다.

### 8.4 쿠키 속성

- `HttpOnly`
- `SameSite=Strict`
- `Secure`는 HTTPS 또는 명시적 개발 예외에서만 완화
- 1차 구현의 쿠키 `Path`는 `/`로 둔다. `/auth/session`, `/dashboard`, `/admin`, `/api`를 모두 같은 세션으로 묶기 위해서다.

### 8.5 재시작 동작

- 서버 재시작 시 메모리 세션은 모두 무효화된다.
- 1차 범위에서는 허용한다.

## 9. 실패 동작 및 운영 메시지

### 9.1 fail-closed 원칙

- `ADMIN_API_KEY`가 없으면 `/admin`, `/api`, `/tools`, `/mcp`는 모두 민감 경로 접근이 불가능해야 한다.
- 기동 자체는 운영 모드에 따라 허용될 수 있으나, 민감 경로는 인증 없이는 unusable 상태여야 한다.

### 9.2 startup warning 정렬

- 현재 경고 메시지는 관리 라우트 기준으로 작성돼 있어 운영자가 전체 HTTP 표면을 오해할 수 있다.
- 경고 메시지는 다음 사실을 명시해야 한다.
- 브라우저 대시보드는 세션 인증을 사용한다.
- `/tools`와 `/mcp`는 헤더 인증만 사용한다.
- 세션과 헤더 인증은 상호 대체되지 않는다.

### 9.3 원격 바인딩

- 비루프백 바인딩과 insecure override가 허용되는 경우에도 인증 경계 분리는 그대로 유지한다.
- 즉, 브라우저는 세션, 프로그램 호출은 헤더라는 규칙은 운영 모드와 무관하게 동일하다.

## 10. 문서 변경

- 운영 문서, README, HTTP 서버 안내 문구는 다음 모델로 일관되게 설명한다.
- 브라우저 대시보드: 세션 로그인 필요
- 관리 API: 세션 필요
- Tools/MCP: `Authorization` 또는 `X-API-Key` 필요
- 단순히 “ADMIN_API_KEY를 설정하면 보호된다”가 아니라 “어떤 경로가 어떤 방식으로 보호되는지”를 명시한다.

## 11. 테스트 전략

### 11.1 미들웨어 단위 테스트

- 세션 검증 성공
- 세션 누락
- 세션 만료
- 잘못된 세션 쿠키
- 헤더 인증 성공
- 헤더 인증 누락
- 잘못된 헤더 키
- 세션 쿠키만 있는 `/tools` 또는 `/mcp` 요청이 거절되는지

### 11.2 HTTP 통합 테스트

- `POST /auth/session` 로그인 성공/실패
- `DELETE /auth/session` 로그아웃
- 세션이 있는 `/admin` 접근 성공
- 세션이 있는 `/api` 접근 성공
- 세션만 있는 `/tools` 접근 거절
- 세션만 있는 `/mcp` 접근 거절
- 헤더가 있는 `/tools` 접근 성공
- 헤더가 있는 `/mcp` 접근 성공

### 11.3 startup/security 테스트

- 루프백/비루프백 바인딩 조합
- `ADMIN_API_KEY` 유무
- insecure override 유무
- startup warning이 실제 경계와 일치하는지

## 12. 단계적 전환

### 12.1 1단계

- 브라우저 비밀 주입 경로를 제거 또는 deprecated 처리한다.
- 대시보드 로그인 흐름을 세션 모델로 교체한다.

### 12.2 2단계

- `/tools`에 프로그램적 인증 미들웨어를 추가한다.
- 루트 MCP 라우터에 동등한 인증 경계를 추가한다.

### 12.3 3단계

- 문서와 startup warning을 새 모델에 맞게 정리한다.
- 기존 브라우저 사용 흐름 변화와 CLI/MCP 사용 흐름 유지 범위를 문서화한다.

## 13. 수용 기준

- 브라우저에 `ADMIN_API_KEY` 또는 동등한 관리 비밀이 전달되지 않는다.
- `/admin`과 `/api`는 세션 기반으로만 접근된다.
- `/tools`와 `/mcp`는 세션 쿠키만으로 접근되지 않는다.
- `/tools`와 `/mcp`는 명시적 헤더 인증이 있어야 접근된다.
- startup warning, 운영 문서, 실제 라우트 보호 범위가 서로 모순되지 않는다.
- 브라우저 인증 실패와 프로그램적 인증 실패가 서로 다른 의미의 오류로 구분된다.

## 14. 후속 이슈

- `crypto.timingSafeEqual` 기반 키 비교 하드닝
- `/health` 응답 정보 축소
- rate limiting 및 abuse quota
- `owner_id` / `agent_id`의 서버 신뢰 기반 결정
- 세션 저장소 영속화 또는 분산 세션 모델
