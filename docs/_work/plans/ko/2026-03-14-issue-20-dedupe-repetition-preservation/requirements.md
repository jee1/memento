## 1. 비즈니스 목표

| 목표 | 설명 |
|------|------|
| **저장 효율** | 유사한 기억이 반복 저장될 때 물리적 행 수·저장 용량을 줄여 비용과 스캔 부담을 낮춘다. |
| **기억 효율** | 반복되어 저장되는 기억은 “자주 언급된 = 중요한” 신호로 간주하고, 회수(recall) 시 이 신호를 잃지 않도록 한다. |
| **정책 일관성** | 중복 제거·압축을 #89 비동기 Augmentation 워커 및 #90 Triples/KG dedupe와 통합할 때, “반복 = 중요도” 보존이 기본 정책이 되도록 한다. |

---

## 2. 사용자(시스템·에이전트) 여정

- **여정 1 — 기억 저장**: 에이전트/사용자가 `remember`로 유사한 내용을 여러 번 저장한다.  
  → 시스템은 즉시 기록 후, 백그라운드에서 유사 기억을 탐지·병합할 수 있어야 한다.
- **여정 2 — 병합 시**: 유사 기억 N건을 대표 1건으로 병합할 때, “N번 반복되었다”는 정보를 버리지 않고 메타데이터(`num_times`, `last_mentioned_at`)로 보존한다.  
  → 저장은 줄이되, 중요도 신호는 유지한다.
- **여정 3 — 기억 회수**: 사용자/에이전트가 `recall`로 조회할 때, 자주 반복된 기억이 랭킹에서 더 잘 노출된다.  
  → “반복 = 중요”가 회수 품질에 반영된다.
- **여정 4 — 감사·디버깅**(선택): 병합된 원본 N건을 soft-delete 또는 대표 ID 참조로 추적 가능하게 하면, 운영·분석 시 유리하다.

---

## 3. 성공 기준 (비기술)

- 유사 기억 병합 후 **물리적 행 수가 감소**한다.
- 병합된 대표 항목에 **반복 횟수·마지막 언급 시각**이 메타데이터로 남아 있다.
- recall 시 **반복 빈도가 높은 기억**이 동일 쿼리에서 더 높은 순위로 노출된다(또는 boost 후보가 된다).
- #89/#90과의 통합 시 위 정책이 명세·구현에 포함된다.

## 4. 유스케이스 개요 (명세서와의 매핑)

| ID | 유스케이스 | 주요 액터 | 결과 |
|----|------------|-----------|------|
| UC-1 | 유사 기억 탐지 및 대표 선정 | 백그라운드 워커 | 대표 1건 + 병합 대상 N건 식별 |
| UC-2 | 병합 시 반복 메타데이터 갱신 | 백그라운드 워커 | 대표의 num_times 누적, last_mentioned_at 갱신 |
| UC-3 | recall 시 반복 기반 랭킹 반영 | recall/검색 엔진 | num_times·last_mentioned 기반 boost 적용 |
| UC-4 | 병합된 원본 추적(선택) | 운영/디버깅 | soft-delete 또는 대표 ID 참조로 이력 조회 가능 |

상세 유스케이스·인터페이스·수용 조건은 [spec.md](./spec.md)에서 정의한다.
