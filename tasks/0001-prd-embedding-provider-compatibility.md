# 0001-prd-embedding-provider-compatibility.md

## Introduction/Overview

임베딩 제공자 전환 시 발생하는 데이터 호환성 문제를 해결하여, 어떤 임베딩 모델을 사용하더라도 기존에 기록된 모든 메모리 데이터를 조회할 수 있도록 하는 기능입니다. 현재 Docker 환경 변수 설정, SQLite VEC 테이블 차원 불일치, 모델 가용성 및 폴백 동작 등의 문제로 인해 임베딩 모델 전환 시 기존 데이터 접근이 불가능한 상황을 해결합니다.

## Goals

1. **기존 데이터 호환성 보장**: 어떤 임베딩 모델로 전환하더라도 기존에 저장된 모든 메모리 데이터를 조회할 수 있도록 보장
2. **자동 마이그레이션 시스템**: 모델 전환 시 수동 개입 없이 자동으로 데이터를 변환하고 호환성을 유지
3. **모든 임베딩 모델 지원**: OpenAI, Gemini, MiniLM, TF-IDF 등 모든 임베딩 제공자를 동일한 인터페이스로 지원
4. **안정적인 모델 전환**: 모델 변경이 거의 발생하지 않는 환경에서 안정성과 신뢰성 우선

## User Stories

### 개발자 관점
- **US-001**: 개발자로서 임베딩 모델을 변경해도 기존에 저장된 메모리 데이터를 모두 조회할 수 있어야 한다
- **US-002**: 개발자로서 모델 전환 시 복잡한 설정 변경 없이 자동으로 마이그레이션이 수행되기를 원한다
- **US-003**: 개발자로서 현재 어떤 임베딩 모델이 활성화되어 있는지 쉽게 확인할 수 있어야 한다

### 시스템 관리자 관점
- **US-004**: 시스템 관리자로서 Docker 환경에서 임베딩 모델을 변경할 때 환경 변수 설정이 일관되게 적용되기를 원한다
- **US-005**: 시스템 관리자로서 모델 전환 후 문제가 발생했을 때 이전 상태로 쉽게 롤백할 수 있어야 한다
- **US-006**: 시스템 관리자로서 모델 가용성 상태와 폴백 동작을 모니터링할 수 있어야 한다

## Functional Requirements

### 1. 데이터 호환성 관리
1.1. 기존 임베딩 데이터를 새로운 모델 차원에 맞게 자동 변환하는 기능
1.2. 다중 차원 벡터를 지원하는 통합 저장소 구조
1.3. 모델별 벡터 테이블과 공용 조회 인터페이스 분리
1.4. 벡터 차원 불일치 시 자동 패딩 또는 차원 축소 기능

### 2. 자동 마이그레이션 시스템
2.1. 모델 전환 시 기존 데이터 자동 변환
2.2. 마이그레이션 진행 상황 실시간 모니터링
2.3. 마이그레이션 실패 시 자동 롤백 기능
2.4. 마이그레이션 이력 및 로그 관리

### 3. Docker 환경 관리 개선
3.1. 환경 변수 기본값과 .env 파일 일관성 보장
3.2. 컨테이너 시작 시 임베딩 제공자 설정 자동 검증
3.3. 환경별 설정 템플릿 제공 (dev, staging, prod)
3.4. 설정 불일치 시 경고 및 자동 수정 제안

### 4. 모델 가용성 및 폴백 관리
4.1. 모든 임베딩 제공자의 가용성 실시간 체크
4.2. 우선순위 기반 자동 폴백 시스템
4.3. 모델 로딩 실패 시 대체 모델 자동 선택
4.4. API 키 누락 시 경고 및 대체 모델 안내

### 5. 로깅 및 모니터링
5.1. 현재 활성화된 임베딩 제공자 로깅
5.2. 모델 전환 이력 추적
5.3. 성능 메트릭 수집 (임베딩 생성 시간, 검색 성능)
5.4. 오류 및 경고 알림 시스템

### 6. 검색 호환성
6.1. 모든 모델의 임베딩을 통합하여 검색 가능
6.2. 모델별 검색 결과 정규화
6.3. 하이브리드 검색에서 다중 모델 지원
6.4. 검색 성능 최적화 (인덱스 관리)

## Non-Goals (Out of Scope)

1. **성능 최적화**: 모든 모델 지원을 위해 성능 저하 허용
2. **실시간 모델 전환**: 운영 중인 시스템에서의 실시간 모델 변경
3. **모델별 특화 기능**: 각 모델의 고유 기능 활용보다는 통합 인터페이스 우선
4. **대규모 데이터 처리**: 수백만 건 이상의 대용량 데이터 최적화
5. **클라우드 전용 기능**: 온프레미스 환경에서도 동일하게 작동해야 함

## Design Considerations

### 백엔드 아키텍처
- **통합 임베딩 서비스**: 모든 임베딩 제공자를 통합하는 단일 인터페이스
- **벡터 저장소 분리**: 모델별 벡터 테이블과 공용 조회 인터페이스 분리
- **마이그레이션 엔진**: 데이터 변환 및 호환성 보장을 위한 전용 엔진
- **설정 관리자**: 환경별 설정 일관성을 보장하는 중앙 관리 시스템

### 데이터베이스 스키마
- 모델별 벡터 테이블 (`memory_item_vec_openai`, `memory_item_vec_minilm` 등)
- 공용 조회 인터페이스 (`memory_item_vec` 뷰)
- 마이그레이션 이력 테이블 (`migration_history`)
- 모델 설정 테이블 (`embedding_models`)

## Technical Considerations

### SQLite 호환성
- VEC 테이블 차원 동적 관리
- 다중 차원 벡터 지원을 위한 스키마 설계
- 마이그레이션 시 데이터 무결성 보장

### Docker 환경
- 환경 변수 우선순위 명확화 (Compose > .env > 기본값)
- 컨테이너 시작 시 설정 검증
- 모델 프리페치를 위한 빌드 단계 최적화

### 마이그레이션 전략
- 점진적 마이그레이션 (기존 데이터 보존)
- 롤백 가능한 마이그레이션 설계
- 데이터 변환 시 검증 및 검증 실패 시 복구

### 성능 고려사항
- 다중 모델 지원으로 인한 메모리 사용량 증가
- 검색 시 모델별 인덱스 최적화
- 배치 처리로 마이그레이션 성능 향상

## Success Metrics

1. **호환성 지표**
   - 기존 데이터 조회 성공률: 100%
   - 모델 전환 후 데이터 손실률: 0%

2. **마이그레이션 지표**
   - 자동 마이그레이션 성공률: 95% 이상
   - 마이그레이션 완료 시간: 평균 30분 이내
   - 롤백 성공률: 100%

3. **운영 안정성 지표**
   - 모델 전환 후 서비스 중단 시간: 5분 이내
   - 설정 불일치로 인한 오류 발생률: 0%
   - 모니터링 알림 정확도: 95% 이상

4. **사용자 만족도**
   - 개발자 설정 변경 시간 단축: 80% 이상
   - 시스템 관리자 수동 개입 필요성: 90% 감소

## Open Questions

1. **운영 환경별 대응**: 개발/스테이징/프로덕션 환경에서 각각 다른 마이그레이션 전략이 필요한가?
2. **롤백 계획**: 모델 전환 후 문제 발생 시 어떤 수준까지 롤백해야 하는가? (데이터만? 설정만? 전체?)
3. **성능 임계값**: 다중 모델 지원으로 인한 성능 저하의 허용 가능한 수준은?
4. **데이터 보존 정책**: 마이그레이션 후 기존 벡터 데이터를 얼마나 오래 보존해야 하는가?
5. **모니터링 범위**: 어떤 수준의 모니터링과 알림이 필요한가?
