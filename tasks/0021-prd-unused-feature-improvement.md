# PRD: 기능 미활용 개선 (Phase 3)

## 1. Introduction/Overview

Memento 프로젝트는 MCP(Model Context Protocol) 서버로서 복잡한 메모리 관리 시스템을 구현하고 있습니다. 현재 코드베이스에서 이미 구현된 기능들이 제대로 활용되지 않는 문제가 발견되었으며, 이를 개선하여 코드 품질과 유지보수성을 향상시켜야 합니다.

**발견된 주요 기능 미활용:**
1. **중앙화된 로깅 시스템 미활용**: `src/shared/utils/logger.ts`가 존재하나 `console.log`가 여전히 광범위하게 사용됨
2. **재시도(Retry) 전략의 파편화**: `src/infrastructure/scheduler/retry-manager.ts`가 존재하나 각 서비스가 개별적으로 재시도 로직을 구현
3. **설정(Config) 값의 하드코딩**: `config/ranking-weights.toml`이 존재하나 코드 내부에 매직 넘버가 하드코딩됨
4. **레거시 스크립트의 잔재**: `scripts/simple-migrate.js`, `scripts/simple-update.js` 등이 정식 마이그레이션 시스템을 우회

**목표**: 중앙화된 로깅 시스템을 강제하고, 재시도 전략을 통일하며, 설정 값을 하드코딩에서 분리하고, 레거시 스크립트를 정리하여 코드 품질과 유지보수성을 향상시킵니다.

## 2. Goals

1. **로깅 시스템 통일**: 프로젝트 전체에서 `console.log` 사용을 금지하고 중앙화된 Logger를 사용하도록 강제
2. **재시도 전략 통일**: 모든 외부 API 호출이 `RetryManager`를 통해 실행되도록 통일
3. **설정 값 분리**: 모든 매직 넘버를 설정 파일이나 상수로 이동
4. **레거시 스크립트 정리**: 레거시 스크립트를 제거하거나 정식 마이그레이션 시스템을 호출하는 래퍼로 변경
5. **코드 품질 향상**: 일관된 패턴 사용으로 코드 품질과 유지보수성 향상

## 3. User Stories

### 3.1 개발자 관점

**As a** 백엔드 개발자  
**I want** 모든 로깅이 중앙화된 Logger를 통해 이루어짐  
**So that** 로그 레벨 관리와 PII 마스킹이 일관되게 적용됩니다.

**As a** 개발자  
**I want** 재시도 로직을 직접 구현하지 않아도 됨  
**So that** `RetryManager`를 사용하여 일관된 재시도 전략을 적용할 수 있습니다.

**As a** 개발자  
**I want** 설정 값을 코드에서 하드코딩하지 않음  
**So that** 설정 변경 시 코드 수정 없이 환경 변수나 설정 파일만 수정하면 됩니다.

**As a** 개발자  
**I want** 레거시 스크립트가 정리됨  
**So that** 어떤 스크립트를 사용해야 하는지 명확하게 알 수 있습니다.

### 3.2 유지보수 담당자 관점

**As a** 유지보수 담당자  
**I want** 로깅이 일관됨  
**So that** 로그 분석과 디버깅이 쉬워집니다.

**As a** 유지보수 담당자  
**I want** 재시도 전략이 통일됨  
**So that** 외부 API 호출 실패 시 일관된 처리가 이루어집니다.

**As a** 유지보수 담당자  
**I want** 설정 값이 중앙화됨  
**So that** 설정 변경 시 한 곳만 수정하면 됩니다.

### 3.3 시스템 관점

**As a** 시스템  
**I want** 모든 로깅이 표준화됨  
**So that** 로그 레벨 관리와 PII 마스킹이 일관되게 적용됩니다.

**As a** 시스템  
**I want** 재시도 전략이 통일됨  
**So that** 외부 의존성 실패 시 일관된 복구 전략을 적용할 수 있습니다.

## 4. Functional Requirements

### 4.1 로깅 시스템 통일

**FR-1.1**: ESLint 규칙으로 `console.log` 사용 금지
- 현재 상태: `src/shared/utils/logger.ts`가 존재하나 `console.log`가 여전히 광범위하게 사용됨
- 요구사항:
  - ESLint `no-console` 규칙을 `error` 레벨로 설정
  - 테스트 파일(`*.spec.ts`, `test-*.ts`)과 CLI 스크립트(`scripts/`)는 예외 처리
  - 핵심 모듈(`src/server/`, `src/services/`)에서 `console.log` 사용 금지

**FR-1.2**: 기존 `console.log`를 Logger로 전환
- 대상 파일:
  - `src/server/` 디렉토리의 모든 파일
  - `src/services/` 디렉토리의 모든 파일
  - `src/domains/` 디렉토리의 핵심 서비스 파일
- 요구사항:
  - `console.log` → `logger.info`
  - `console.error` → `logger.error`
  - `console.warn` → `logger.warn`
  - `console.debug` → `logger.debug`

**FR-1.3**: Logger 의존성 주입
- 모든 서비스 클래스에서 Logger를 의존성 주입받아 사용
- 생성자에서 Logger를 주입받거나, 정적 메서드에서 공통 Logger 사용

**FR-1.4**: 로깅 필드 스키마 통일
- 모든 로깅이 구조화된 메타데이터 객체를 사용
- 공통 필드: `agentId`, `slot`, `memoryId`, `traceId` 등
- 로깅 형식: ISO 8601 타임스탬프 + 레벨 + 메시지 + JSON 메타데이터

### 4.2 재시도 전략 통일

**FR-2.1**: RetryManager 사용 강제
- 현재 상태: `src/infrastructure/scheduler/retry-manager.ts`가 존재하나 각 서비스가 개별적으로 재시도 로직 구현
- 대상 서비스:
  - `src/domains/embedding/providers/` 내부의 모든 임베딩 제공자
  - 외부 API를 호출하는 모든 서비스
- 요구사항:
  - 모든 외부 API 호출이 `RetryManager`를 통해 래핑되어 실행
  - 개별 `try-catch`와 `setTimeout`을 사용한 재시도 로직 제거

**FR-2.2**: RetryManager 인터페이스 표준화
- `RetryManager.retry<T>(fn: () => Promise<T>, options?: RetryOptions): Promise<T>` 메서드 사용
- 재시도 옵션(최대 시도 횟수, 지연 시간, 지수 백오프 등)을 설정 파일로 관리

**FR-2.3**: 재시도 전략 통일
- 모든 외부 API 호출에 동일한 재시도 전략 적용
- 실패 시 로깅 및 에러 처리 통일

### 4.3 설정 값 분리

**FR-3.1**: 매직 넘버 추출
- 현재 상태: `config/ranking-weights.toml`이 존재하나 코드 내부에 매직 넘버가 하드코딩됨
- 대상 파일:
  - `src/domains/search/algorithms/search-ranking.ts`
  - `src/domains/search/algorithms/vector-search-engine.ts`
  - 기타 매직 넘버가 하드코딩된 모든 파일
- 요구사항:
  - 모든 매직 넘버를 `src/shared/config/constants.ts` 또는 설정 파일로 이동
  - 설정 파일이 로드되지 않았을 때의 폴백(Fallback) 값도 상수 파일로 관리

**FR-3.2**: 설정 파일 로더 통일
- `src/shared/config/` 디렉토리의 설정 로더 사용
- TOML, JSON, 환경 변수 등 다양한 설정 소스 지원

**FR-3.3**: 설정 값 검증
- 설정 값이 유효한 범위 내에 있는지 검증
- 잘못된 설정 값에 대한 명확한 에러 메시지 제공

### 4.4 레거시 스크립트 정리

**FR-4.1**: 레거시 스크립트 식별
- 현재 상태: `scripts/simple-migrate.js`, `scripts/simple-update.js` 등이 정식 마이그레이션 시스템을 우회
- 대상 스크립트:
  - `scripts/simple-migrate.js`
  - `scripts/simple-update.js`
  - 기타 정식 마이그레이션 시스템을 우회하는 스크립트
- 요구사항:
  - 각 스크립트의 사용 여부 확인
  - 사용되지 않는 스크립트는 제거
  - 사용 중인 스크립트는 정식 마이그레이션 시스템을 호출하는 래퍼로 변경

**FR-4.2**: 정식 마이그레이션 시스템 확인
- `src/infrastructure/database/sqlite/migration/` 디렉토리의 마이그레이션 시스템 확인
- 마이그레이션 시스템 인터페이스 문서화

**FR-4.3**: 레거시 스크립트 래퍼화
- 사용 중인 레거시 스크립트를 정식 마이그레이션 시스템을 호출하는 래퍼로 변경
- 기존 스크립트 인터페이스는 유지 (하위 호환성)

**FR-4.4**: 레거시 스크립트 제거
- 사용되지 않는 레거시 스크립트 제거
- Git 히스토리 보존 (삭제만 수행)

## 5. Non-Goals (Out of Scope)

1. **로깅 시스템 재설계**: 기존 `logger.ts`를 활용하며, 새로운 로깅 시스템 구축은 제외
2. **재시도 전략 재설계**: 기존 `RetryManager`를 활용하며, 새로운 재시도 전략 구축은 제외
3. **설정 시스템 재설계**: 기존 설정 시스템을 활용하며, 새로운 설정 시스템 구축은 제외
4. **전체 코드베이스 리팩토링**: 이번 작업은 발견된 기능 미활용에 집중하며, 다른 리팩토링은 별도 작업으로 진행
5. **성능 최적화**: 이번 작업의 주요 목표는 코드 품질 개선이며, 성능 최적화는 별도 작업으로 진행

## 6. Design Considerations

### 6.1 로깅 시스템

- **중앙화된 Logger**: `src/shared/utils/logger.ts`의 `logger` 객체 사용
- **의존성 주입**: 서비스 클래스에서 Logger를 주입받아 사용
- **구조화된 로깅**: 메타데이터 객체를 사용한 구조화된 로깅

### 6.2 재시도 전략

- **중앙화된 RetryManager**: `src/infrastructure/scheduler/retry-manager.ts` 사용
- **설정 기반 재시도**: 재시도 옵션을 설정 파일로 관리
- **일관된 에러 처리**: 재시도 실패 시 일관된 에러 처리

### 6.3 설정 관리

- **중앙화된 설정**: `src/shared/config/` 디렉토리의 설정 로더 사용
- **타입 안전성**: TypeScript 타입 시스템을 활용한 설정 타입 검증
- **환경 변수 지원**: 환경 변수를 통한 설정 오버라이드 지원

### 6.4 레거시 스크립트

- **래퍼 패턴**: 레거시 스크립트를 정식 시스템을 호출하는 래퍼로 변경
- **하위 호환성**: 기존 스크립트 인터페이스 유지
- **점진적 마이그레이션**: 사용 중인 스크립트부터 순차적으로 마이그레이션

## 7. Technical Considerations

### 7.1 의존성

- 기존 TypeScript, Node.js 버전 유지
- 기존 라이브러리 의존성 유지
- ESLint 플러그인 추가 설치 필요 (`eslint-plugin-security`는 Phase 1에서 설치)

### 7.2 마이그레이션 전략

- **점진적 적용**: 파일별로 순차적으로 기능 미활용 개선 적용
- **하위 호환성 유지**: 기존 API는 유지하며 내부 구현만 개선
- **테스트 우선**: 각 변경사항에 대한 테스트 케이스 먼저 작성

### 7.3 성능 영향

- 로깅 시스템 통일은 성능에 거의 영향 없음
- 재시도 전략 통일은 재시도 로직이 중앙화되어 성능에 약간의 영향 있을 수 있음
- 설정 값 분리는 초기 로드 시 약간의 오버헤드 있을 수 있음
