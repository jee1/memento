# 0004-prd-consolidation-score-system.md

## Introduction/Overview

기억 통합 점수(Consolidation Score) 시스템은 Memento MCP 서버에 **동적 기억 강화 및 점진적 망각(graceful degradation)** 메커니즘을 도입하는 기능입니다.

현재 Memento는 TTL 관리 및 고정된 망각 정책을 사용하지만, 이 기능은 **회상 빈도(Recall Frequency)**, **경과 시간(Time Elapsed)**, **문맥적 관련성**을 모두 고려하는 동적 모델을 도입하여, 사용되지 않는 기억은 배경으로 물러나 검색될 확률이 낮아지도록 합니다. 이는 파괴적인 삭제(DELETE) 없이 인간과 유사한 '점진적 망각' 효과를 달성합니다.

**핵심 문제**: 에이전트가 모든 정보를 무한히 기억할 경우, 결국 관련성이 없는 정보의 홍수에 압도됩니다. 따라서 효율적인 메모리 시스템은 인간처럼 중요한 정보를 강화하고(Consolidation) 덜 중요한 정보를 점진적으로 '망각(Forgetting)'하는 동적 메커니즘을 갖추어야 합니다.

**목표**: Hou et al.의 연구에 기반한 정규화된 회상 확률 공식을 사용하여, 검색 대상 메모리에 대한 동적 통합 점수를 계산하고, 이를 검색 랭킹에 반영하여 더 현실적이고 효율적인 메모리 검색을 실현합니다.

## Goals

1. **동적 기억 통합 점수 계산**: 회상 빈도와 경과 시간을 기반으로 `consolidation_score`를 동적으로 계산
2. **검색 랭킹 개선**: 벡터 유사도와 통합 점수를 가중 합하여 최종 검색 점수 계산
3. **메타데이터 추적**: 모든 주요 메모리 테이블에 `recall_count`, `last_accessed_at`, `consolidation_score` 필드 추가
4. **실시간 업데이트**: 검색 성공 시 `recall_count` 증가 및 `last_accessed_at` 갱신
5. **배치 재계산**: 주기적 배치 작업을 통한 `consolidation_score` 재계산 및 최적화
6. **성능 최적화**: 인덱스, 배치 처리, 캐싱을 통한 대량 데이터 처리 성능 보장
7. **백워드 호환성**: 기존 MCP 클라이언트와의 호환성 유지 (선택적 기능, 기본 OFF)

## User Stories

### AI 에이전트 관점
- **US-001**: AI 에이전트로서 자주 사용하는 중요한 기억이 검색 결과 상위에 유지되어 빠르게 접근하고 싶다
- **US-002**: AI 에이전트로서 오래되었지만 계속 활용하는 기억이 최신성만으로 인해 검색 결과에서 밀려나지 않기를 원한다
- **US-003**: AI 에이전트로서 사용하지 않는 오래된 기억이 검색 결과 후순위로 밀려나 노이즈를 줄이고 싶다
- **US-004**: AI 에이전트로서 맥락적 중요도를 반영한 검색 결과를 받아 더 정확하고 현실적인 정보를 활용하고 싶다

### 시스템 관리자 관점
- **US-005**: 시스템 관리자로서 파괴적 삭제 없이 점진적 성능 저하를 통해 메모리 시스템의 효율성을 관리하고 싶다
- **US-006**: 시스템 관리자로서 검색 품질과 성능을 모니터링하고 가중치 파라미터를 조정하여 최적화하고 싶다
- **US-007**: 시스템 관리자로서 기존 데이터를 손실 없이 새로운 메타데이터 필드로 마이그레이션하고 싶다

## Functional Requirements

### 1. 스키마 수정

1.1. `episodic_memory` 테이블에 다음 필드 추가:
   - `recall_count` (INTEGER, NOT NULL, DEFAULT 0): 해당 기억이 성공적으로 검색되어 활용된 횟수
   - `last_accessed_at` (TIMESTAMP): 해당 기억이 마지막으로 접근된 시간 (NULL 허용)
   - `consolidation_score` (REAL): 동적 기억 통합 점수 (0.0 ~ 1.0 범위, NULL 허용)
   - `g_value` (REAL): 감쇠 상수 g_n의 현재 값 (성능 최적화용, NULL 허용)

1.2. `semantic_memory` 테이블에 동일한 필드 추가 (1.1과 동일)

1.3. `procedural_memory` 테이블에 동일한 필드 추가 (1.1과 동일)

1.4. 각 테이블에 다음 인덱스 생성:
   - `CREATE INDEX idx_[table]_last_accessed ON [table](last_accessed_at DESC)`
   - `CREATE INDEX idx_[table]_consol_desc ON [table](consolidation_score DESC)`
   - `CREATE INDEX idx_[table]_consol_active ON [table](consolidation_score) WHERE consolidation_score > 0.2` (SQLite partial index)

### 2. MCP 읽기/검색 연산 수정

2.1. **'성공적인 검색'의 정의**:
   - **v1 (초기 버전)**: `memento.recall`, `memento.search`, `memento.memory_injection` 등을 통해 메모리가 검색 결과로 반환될 때를 '성공적인 검색'으로 간주
   - **고려사항**: 에이전트가 검색 결과로 메모리를 보기만 하고 실제로 사용하지 않는 경우에도 `recall_count`가 증가할 수 있음 (웹사이트의 '노출수'와 '클릭수'의 차이와 유사)
   - **v1 전략**: 현재 설계대로 진행하되, 이 현상을 인지하고 모니터링. 대부분의 경우 검색 결과 상위 노출은 사용으로 이어질 가능성이 높으므로 초기 버전으로는 합리적
   - **v2 (장기 고려)**: 에이전트가 검색된 메모리를 후속 작업에서 실제로 활용했음을 나타내는 피드백 루프 추가. 예를 들어, 검색된 `memory_id`가 다음 `memento.write`나 다른 도구 호출에 인자로 사용될 때 카운트를 올리는 방식

2.2. `memento.recall` 또는 `memento.search`를 통해 특정 메모리를 성공적으로 검색하여 반환할 때:
   - 해당 레코드의 `recall_count`를 1 증가
   - `last_accessed_at`을 현재 시간으로 갱신
   - `g_value` 업데이트: 기존 `g_value` (또는 `g_{n-1}`)를 읽어와 `g_n = g_{n-1} + S(t)` 계산 후 저장 (성능 최적화)
   - (옵션) 즉시 `consolidation_score` 재계산 또는 이벤트 큐에 적재

2.3. `memento.memory_injection`을 통해 메모리가 프롬프트에 주입될 때도 2.2와 동일하게 처리

2.4. **신규 메모리 생성 시 초기화**:
   - `memento.write` (또는 `memento.remember`)로 새 메모리가 생성될 때:
     - `recall_count = 1` (생성을 첫 번째 '접근'으로 간주)
     - `last_accessed_at = created_at` (생성 시각으로 초기화)
     - `g_value = 1` (초기값 `g_0 = 1`)
   - 이렇게 하면 방금 생성된 중요한 정보가 `recall_count = 0`인 오래된 정보보다 약간의 우선순위를 가질 수 있음

2.5. 모든 검색 관련 MCP 도구에 동일한 업데이트 로직 적용

2.6. 업데이트 실패 시 검색 결과는 정상 반환하되, 에러 로그 기록

### 3. 동적 점수 계산

3.1. **Hou et al. 정규화 회상 확률 공식** 구현:
   - 기본 공식: `p_n(t) = (1 - exp(-r * e^(-t/g_n))) / (1 - e^(-1))`
   - 감쇠 상수: `g_n = g_{n-1} + S(t)`, `S(t) = (1 - e^(-t)) / (1 + e^(-t))`, `g_0 = 1`
   - 변수 설명:
     - `n`: 회상 횟수 (`recall_count`)
     - `t`: 경과 시간 (시간 단위, `now - last_accessed_at` 또는 `now - created_at`)
     - `r`: 초기 회상 확률 상수 (기본값 0.5, 타입별 조정 가능)
     - `g_n`: 감쇠 상수 (회상 횟수에 따라 완화됨)

3.2. **g_n 계산 최적화**:
   - **문제**: `g_n = g_{n-1} + S(t)`는 점화식 형태로, 배치 작업에서 `recall_count`가 매우 높은 메모리의 경우 n번의 반복 계산이 필요하여 연산 부하가 발생할 수 있음
   - **해결책**: `g_value` 필드를 스키마에 추가하여 최적화
     - `recall_count`가 업데이트될 때, 기존 `g_value` (또는 `g_{n-1}`)를 읽어와 `g_n = g_{n-1} + S(t)` 계산을 한 번만 수행하고 결과를 `g_value` 필드에 저장
     - 배치 작업에서는 저장된 `g_value`를 바로 사용하여 `p_n(t)`를 계산하므로 연산 비용이 크게 줄어듦
   - **초기값**: `g_value = 1` (`g_0 = 1`)

3.3. 점수 계산 시 고려사항:
   - `recall_count = 0`일 때: `g_0 = 1` 사용 (또는 `g_value = 1`)
   - `last_accessed_at`이 NULL일 때: `created_at` 사용
   - `g_value`가 NULL일 때: `recall_count`를 기반으로 처음부터 계산 (마이그레이션된 기존 데이터 처리)
   - 계산 결과는 0.0 ~ 1.0 범위로 클램핑

3.4. 타입별 초기값 설정:
   - `procedural_memory`: `r_base = 0.6` (절차 기억은 더 오래 유지)
   - `episodic_memory`: `r_base = 0.5` (기본값)
   - `semantic_memory`: `r_base = 0.5` (기본값)

3.5. 핀 고정 메모리 처리:
   - `pinned = true`인 메모리는 최소 바닥값(예: 0.25) 보장

### 4. 검색 로직 통합

4.1. 최종 검색 점수 계산:
   - `Final_Score = w1 * vector_similarity + w2 * consolidation_score`
   - 기본 가중치: `w1 = 0.8`, `w2 = 0.2`

4.2. 검색 프로파일별 가중치 설정:
   - `recent`: `w1 = 0.9`, `w2 = 0.1` (최신성 중시)
   - `balanced`: `w1 = 0.8`, `w2 = 0.2` (기본값)
   - `memory`: `w1 = 0.7`, `w2 = 0.3` (기억 강화 중시, 상한 0.4)

4.3. 동적 가중치 조정 (선택적):
   - 검색 의도/쿼리 타입에 따라 `w2`를 0.1~0.3 범위에서 자동 조절
   - **상한 제한**: `w2`의 상한은 0.4로 제한
     - **근거**: 의미적 유사도(`w1`)가 항상 최소 60%의 영향력을 갖도록 보장하여, 아무리 자주 사용되었더라도 관련 없는 내용이 최상위에 노출되는 것을 방지
     - 이는 검색 품질을 유지하면서 기억 강화 효과를 균형있게 적용하기 위한 방어 장치

4.4. 모든 검색 관련 MCP 도구에 동일한 점수 계산 로직 적용:
   - `memento.recall`
   - `memento.memory_injection`
   - 기타 유사 검색 도구

### 5. 배치 재계산 작업

5.1. **시간당 증분 재계산**:
   - 최근 1~12시간 내 갱신된 레코드만 대상
   - Changed-since 인덱스를 활용한 효율적 처리

5.2. **야간 전체 스윕**:
   - 하루 1회 전체 레코드 재계산
   - 바닥값/상한 재적용
   - 캐시 리프레시

5.3. 배치 작업 실패 시:
   - 에러 로그 기록
   - 다음 주기에서 재시도
   - 전체 시스템 중단 없이 계속 운영

### 6. 성능 최적화

6.1. **쓰기 결합(Write Coalescing)**:
   - `last_accessed_at`의 실시간 쓰기를 초당 1회로 코얼레싱
   - 메모리 버퍼 → 주기적 flush

6.2. **캐싱 전략**:
   - 상위 K(예: 2000) 메모리의 `(id, consolidation_score)`를 타입별 Redis ZSET에 유지 (선택적)
   - 쿼리 시 ANN 결과 Top-N ∩ 캐시 상위를 우선 랭킹

6.3. **WAL 모드 및 배치 upsert**:
   - SQLite WAL 모드 활용
   - 배치 upsert로 I/O 최소화

### 7. 기존 데이터 마이그레이션

7.1. **로그 기반 복원** (가능한 경우):
   - 접근/검색 로그가 있으면 집계하여 초기 `recall_count`와 `last_accessed_at` 복원

7.2. **스크립트 기반 초기화** (로그 없는 경우):
   - **정책 결정**: 기존 메모리는 생성 시점을 기준으로 초기화
     - `recall_count = 0` (또는 정책에 따라 1로 설정 가능, 신규 메모리와의 일관성 고려)
     - `last_accessed_at = created_at`
     - `g_value = 1` (초기값 `g_0 = 1`)
   - `consolidation_score`는 Hou식 정규화 회상확률로 1회 산출:
     - `n = 0` (=> `g_0 = 1`)
     - `t = now - created_at` (시간 단위)
     - `r_base = 0.5` (초기 중립값, 타입별 조정 가능)
   - **참고**: 신규 메모리는 `memento.write` 시 `recall_count = 1`로 초기화되므로, 기존 데이터와의 정책 일관성을 고려하여 마이그레이션 정책을 결정해야 함

7.3. 마이그레이션 절차:
   - 드라이런(dry-run) 실행
   - 실제 반영
   - 배포 후 1주일 모니터링 (상·하위 5% outlier 점검)

### 8. 기능 활성화/비활성화

8.1. **기본 상태**: 기능 비활성화 (기존 동작 유지)

8.2. **활성화 방법**:
   - 서버 설정 파일에서 `consolidation_score_enabled = true`
   - 또는 쿼리 파라미터로 활성화 (향후)

8.3. 기능 비활성 시:
   - 스키마는 마이그레이션되지만 필드 미사용
   - 기존 점수식만 사용 (벡터 유사도만)

## Non-Goals (Out of Scope)

1. **자동 메모리 삭제**: 이 기능은 점진적 망각을 통한 검색 순위 조정만 수행하며, 실제 데이터 삭제는 수행하지 않음
2. **실시간 점수 재계산**: 모든 검색 시마다 실시간 재계산은 성능상 제외 (읽기 시점 업데이트 + 배치 병행)
3. **다중 에이전트 지원**: 초기 버전에서는 단일 에이전트 환경만 고려
4. **UI/대시보드**: 점수 시각화나 관리 UI는 별도 기능으로 분리
5. **자동 가중치 최적화**: 가중치 자동 조정 알고리즘은 Phase 2에서 고려
6. **분산 캐시**: Redis 등 외부 캐시 시스템 통합은 선택적 기능으로 분리

## Design Considerations

### 스키마 설계
- 기존 테이블에 필드 추가 방식으로 마이그레이션 부담 최소화
- NULL 허용 필드로 기존 데이터와의 호환성 보장
- 인덱스는 검색 성능과 배치 작업 효율성을 고려하여 설계

### 알고리즘 설계
- Hou et al.의 정규화 회상 확률 공식을 기본으로 하되, 프로젝트 특성에 맞게 조정 가능
- 지수 감쇠 모델을 백업 옵션으로 제공 (일반 지수 감쇠: `p(t) = e^(-λt)`)

### 성능 설계
- 실시간 업데이트는 비동기 처리 또는 버퍼링을 통해 성능 영향 최소화
- 배치 작업은 증분 처리로 부하 분산
- 인덱스와 캐싱을 통한 쿼리 성능 최적화

## Success Metrics

### 검색 품질 지표
1. **정성적 평가**: 휴먼 평가로 "의도에 맞는 상위 노출률" 변화 측정 (페어와이즈 비교 200샘플 이상)
2. **정량적 랭킹 지표**:
   - `Recall@k` (k=5, 10): 상위 k개 결과 중 관련 메모리 포함률
   - `MRR` (Mean Reciprocal Rank): 평균 역순위
   - `nDCG@k` (k=5, 10): 정규화된 할인 누적 이득
   - 출시 전후 A/B 테스트

### 성능 지표
1. **응답 시간**: p95 응답시간 증가 < 10%
2. **리소스 사용량**: CPU/디스크 IOPS 모니터링
3. **배치 작업 시간**: 재계산 잡 실행 시간 추적

### 안정성 지표
1. **데이터 무결성**: 극저/극고 빈도 데이터에서의 캡·바닥값 준수
2. **재현성**: 동일 입력 → 동일 랭킹 보장
3. **에러율**: 검색 실패율 < 0.1%

### 사용 패턴 지표
1. **회상 빈도 분포**: `recall_count` 분포 모니터링
2. **점수 분포**: `consolidation_score` 분포 모니터링 (정규 분포 확인)
3. **상위 노출 기억**: 자주 회상되는 기억이 실제로 상위에 노출되는지 확인
